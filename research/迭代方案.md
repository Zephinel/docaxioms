## 一、结论

- **定位**：三份调研报告的判断基本一致，也都成立。docaxioms 是本地、确定性的文档完整性门禁；和规格驱动框架（Spec Kit、OpenSpec、Kiro）是上下游关系；和 AI 托管文档（Mintlify、Dosu、DeepWiki）在 A0 上立场相反。
- **全流程系统可行；“文档一定正确”不可行。**
  - 能硬保证的：配置被正确解释；每条必需规则都有明确的终态，零匹配、出错和降级都会显出来；证据对应被验收的那棵树和那个环境；记录没有被改写；必需的批准确实发生过；关闭不完整的任务会被拒绝。
  - 证明不了的：散文与行为语义一致；依赖登记齐全；owner 的原意被正确理解（A0、A6）。
- **“门槛不够硬”的主因不是门禁太少，而是三处漏水：**
  1. 门禁本身会静默失效或被绕过。第一批修复已经堵上 profile 拼错、history 绕过、链接越界等（第二节）；还剩零匹配不显示（缺陷 11）、被 gitignore 的目标（缺陷 13）、log glob 漏排除（缺陷 16）、Git 调用失败被当成空差异（缺陷 17），以及扩展返回空结果被当成通过（缺陷 18）。
  2. 没有东西强制它运行。README 原话：nothing calls it for you。
  3. 被检查的候选可以在同一次变更里改掉检查本身，包括 profile、豁免和 workflow。
- **最终门槛可以留在本地，而且对个人仓库比免费的远端更硬。** 强制力来自权限和发布路径的封闭，跟机器在本地还是远端无关。具体做法是一个本地闸门程序：
  - 闸门运行在一个独立的系统用户下；
  - 推送由它的接收端钩子在不可变的提交上验收；
  - 能写受保护分支的凭据只有它持有，开发者用户下的凭据要降权；
  - owner 的批准用硬件密钥签名，由验签端强制要求物理触摸。

  远端可以完全不要，也可以只做薄验签（第三节）。
- **“改一处、自动带动相关文档”能做一半。** 沿已登记的依赖找到所有受影响的段落，可以做得精确；能自动更新的只有能从源头重算的内容，散文最后都要有人或 agent 确认（第四节）。它不需要等闸门，可以先做成只读的影响报告。
- **接入交给 agent，由检查收口。** `init` 把项目原有的入口、阶段卡、索引和计划另存为 `.project.md`，再放入模板；新的只读命令 `docaxioms onboard` 列出还不符合的地方，agent 改到它通过为止（第七节第 5 条）。它只能做到机械验收：迁移后的内容对不对，仍要人抽查。前提是先补上一个缺口：现在的默认 profile 管得太窄时，检查也会全部通过（缺陷 20）。
- **会话恢复的核心是“每次启动都从 Git 和任务页重新核对”，** 不是“退出时记得收尾”——中断恰恰发生在收尾之前。这个核对不依赖任何本地状态，也就不会把会话锁死。
- **主流 Agent 可以适配，但要按四种能力分别承诺**：发现入口、导入内容、阻断操作、恢复会话。适配和闸门程序全部放在 `core/` 之外（AD-2）。
- **AD-7 只约束本仓库自己的阻断面**（[决策](../docs/decisions.md)），不控制消费项目的 gate。
  - 新谓词在消费项目里按 M2 处理：谓词就是性质本身且精确的，直接做 gate；否则先做 aid，实测后再议。
  - 闸门让检查“无法被绕过”，但不改变“哪些检查该阻断”。这两件事要分开决定。
- **调研报告里的事实错误**：三份报告各有一些（第十四节），引用时以本文为准。A 列为 P0 的“`src/index.mjs` 缺失”不成立：8336bed 上文件存在，打包后独立安装可以 import，共 19 个导出（[日志](fact-check/codex-lab/logs/consumer-import.txt)）；d840742 的源码仍是 19 个导出，独立安装没有重新验证。

## 三、门槛加硬：本地终审

### 1. 三个问题都答清，才叫硬门禁

1. **谓词精确吗？** 例如“这个链接的目标，在被验收的树里存在”。
2. **检查真的执行了吗？** 有没有拼错的配置、零匹配、运行出错、降级。
3. **结果能被绕过吗？** 失败之后还能不能进入权威分支、能不能发布。

当前实现在第 2、3 问上都有缺口。只修第 1 问，等于给漏水的桶加盖子。

### 2. 本地各种机制能做到多硬

| 机制 | 守住 | 没守住（A6） |
|---|---|---|
| L0 文本：入口文件、GUIDE、技能 | 要求可达 | 读没读、懂没懂、守没守 |
| L1 Agent 钩子 | 在支持该事件的产品上尽早拦截 | 不支持钩子的工具；只拦编辑、放行 shell；钩子出错或超时时放行；用户关掉钩子 |
| L2 客户端 Git 钩子（pre-commit、pre-push） | 提前反馈，防手滑 | `--no-verify`；改钩子路径；用底层命令直接改引用 |
| 同一系统用户下的闸门仓库（bare 仓库加接收端钩子） | 接收端钩子不受 `--no-verify` 影响 | 同一个用户可以改钩子、改引用，或者绕过闸门直接推到托管平台。只防手滑，而防手滑用 L2 就够，所以不做成产品档位 |
| **L3 跨系统用户的闸门** | 开发者和 Agent 的进程改不了闸门的仓库、钩子、策略和检查器，读不到它的密钥，也拿不到推往托管平台的凭据 | root 或管理员；闸门服务本身被攻破；开发者用户下仍然留着的其他发布或管理凭据（见第 5 条） |
| **L4 签名与硬件批准** | 结果可以跨进程、跨机器验证；指定的硬件密钥，对指定的批准内容签名，并满足验签端强制的用户在场条件 | 签名不证明检查标准充分，也不证明签发者诚实；用户在场不证明 owner 看到的就是被签的内容，更不证明认真读过 |
| 文件监听守护进程 | 缓存失效、钩子快速判断、补充恢复简报 | 三个平台的内核事件都会合并或溢出丢失，也看不到命令和退出码。**不能作为证据，也不能作为写入锁的依据** |
| 沙箱、容器、虚拟机运行候选代码 | 候选代码接触不到宿主的凭据和签名接口 | 只读挂载不等于完整隔离；把全部源码设为只读会破坏编辑器和工具链，所以只用于检查运行器，不用于编辑 |

最低的可信组合是：**跨用户的接收端、不可变快照验收、受保护的策略和检查器、唯一的发布凭据。** 签名让结果能被别处消费，守护进程改善体验，但都代替不了这四项。

### 3. 推荐架构：本地闸门程序

**三个权限域，外加一个辅助组件**

| 组件 | 身份 | 权限与职责 |
|---|---|---|
| 开发者、Agent、客户端 | 普通用户 | 编辑工作区，做普通提交，请求验收。没有闸门文件的写权限、签名权限，也没有能写受保护分支或管理仓库的远端凭据 |
| 闸门服务 | 专用系统用户，禁止交互登录 | 拥有权威的 bare 仓库、证据库和转发队列；读取已批准的策略和检查器；决定接收、签发和转发。程序、运行时、依赖和治理配置都装在开发者无法替换的位置 |
| 检查运行器 | 与闸门不同的低权限身份，或者虚拟机 | 读取闸门导出的候选快照，写临时产物，断网运行。不能读密钥、不能改闸门的引用、不能调用签名接口 |
| 监听进程（可选） | 普通用户 | 维护缓存、给钩子提供快速判断、补充恢复简报。它的事件不构成任何通过凭据 |

**一次推送的数据流**

```text
工作区 → 普通提交 C → 本机受控入口（切换到闸门身份）
                         ↓
         pre-receive：确定基线 B、候选树 T、适用的策略 P
                         ↓
         从隔离区导出 T 的快照，交给运行器断网跑 check 与必需验证
                         ↓
         闸门核对结果、批准、输入身份；不通过则拒绝，引用不变
                         ↓
         仍在 pre-receive 里：把检查记录和签好的凭据写进证据库
         签不出来（密钥不可用）就拒绝，引用不变
                         ↓
         引用更新；post-receive 标记“已接收”，写 notes，唤醒转发队列
                         ↓
         可选：用独占凭据转发远端；离线则排队
```

**接收端契约**

1. **入口必须真正切换到闸门身份。** 不能直接推送到共享目录里的仓库路径：本地文件协议用的是推送者自己的身份。`safe.directory` 有显式例外，不能当权限边界。
   - 首版用 Git 远程助手，经本机 Unix 套接字连接闸门。套接字显式设权限，闸门在内核层核验对端的 UID（Linux 用 `SO_PEERCRED`，macOS 用 `getpeereid`）。这样不用打开 sshd。Node 的 `node:net` 没有暴露这两个接口，所以 macOS 和 Linux 上也需要一个很薄的原生桥接；在 macOS 上，它同时负责用 `launch_activate_socket` 领取 launchd 预先建好的套接字。不想要原生代码时，退一步：不用 launchd 的 `Sockets`，由常驻服务自己建套接字，放进一个由服务或管理员持有、授权组只能进入、不能写的目录，靠目录权限守住。这样只能核验组，核验不了具体用户。
   - 不用 `git daemon`：它启用 receive-pack 后没有任何身份认证，只监听本机也不等于认证了用户。
   - 本机 SSH forced command 只作备选。sshd 会经账号的登录 shell 执行命令，shell 设成 `nologin` 时它根本跑不起来；所以要换成受限 shell 或专用包装器，并禁用密码登录、转发、PTY 和用户 rc，严格解析原始命令。
2. **读取完整的 (old, new, ref)。** 默认拒绝未登记的引用、删除和非快进更新。首版一次只更新一个受保护引用。
3. **B 取自闸门保存的权威状态，T 取自新提交 C。** 不用开发者的 HEAD、工作树或可变的远程跟踪分支。同一仓库的事务串行处理；提交引用之前，再核对一次旧 OID、策略代次和批准绑定。
   - 首次接入时还没有 B：初始信任来自管理员安装时的显式引导，owner 批准初始策略和检查器，不由候选自己声明。
4. **直接读 Git 对象。** 闸门自己用 `ls-tree` 枚举路径、类型和 mode，用 `cat-file` 读原始 blob；不经过检出时的换行转换、过滤器和符号链接。关闭 replacement refs。
   - 隔离区里的新对象只对闸门身份可读。要交给运行器时，由闸门按 Git 对象逐个导出：遍历 `ls-tree -r -z`，按 NUL 解析路径、按 OID 请求 blob、按返回长度读取内容，用 `cat-file --batch` 写出普通文件，保留可执行位（`100644` 写成只读，`100755` 写成只读可执行），核对路径、mode 和 blob 摘要，放进运行器的只读输入目录。不用 `git archive`：它保留符号链接，还会按候选自带的 `.gitattributes` 删文件（`export-ignore`）、改内容（`export-subst`），候选加一行就能让失败的测试从快照里消失。符号链接、子模块等不支持的对象按策略拒绝，不能删掉之后仍声称验收了 T。
   - 子模块、LFS 和生成物的输入要有明确合同，取不到必需输入时返回 blocked。
5. **治理文件由旧策略识别。** 分两套范围：
   - 闸门自身的执行闭包：检查器及其导入的依赖、解释器和运行时版本、监督运行的程序。它们装在系统目录里，由文件权限保护，不随候选变化。
   - 候选仓库里的治理文件：`docaxioms.json` 和其中的策略、`docaxioms/`、允许签名者名单、`.github/workflows/` 整个目录（启用 Actions 验签时；同名 job 就能冒充必需检查），以及策略里显式登记的验证入口。业务依赖锁、普通的 npm 脚本不算，否则每次装包都要 owner 批准（A7）。
   - 没改治理文件：用基线策略验收。
   - 改了治理文件：旧策略判定“谁有权批准这次迁移”；批准通过后，用新策略和新检查器验收整棵 T。批准绑定 B、C、新策略摘要和检查器摘要，候选一变，批准即失效。
   - 不要求“只改治理文件”。升级检查器时，往往要在同一个提交里修掉新暴露的违规。
6. **候选代码不以闸门身份运行。** 被测的代码和测试来自 C；监督运行的程序来自已批准的版本。候选的 npm 脚本、插件和 projectChecks，只在无凭据的运行器里执行。闸门记录实际启动了什么命令、输入是什么、退出状态如何；客户端提交的“PASS JSON”一律不认。“命令退出码为零”只说明命令成功，不说明测试充分。
7. **必需规则只能有明确的终态**，见第 6 条。
8. **“检查通过”“本地已接收”“远端已送达”是三个不同的状态。**
   - 签名必须在引用更新之前完成：pre-receive 返回之后，失败就再也拦不住这次接收。pre-receive 里不能写 notes（新对象还在隔离区），但可以写仓库外的证据库。
   - 接收后由 post-receive 确认“已接收”，再写 notes、唤醒转发队列。post-receive 不是回滚点。
   - 崩溃恢复：重启时比对证据库和权威引用。签过名、引用却没更新的凭据，标记为孤立凭据，不生效；引用已更新、notes 还没写的，补写。
   - 本地接收和远端转发是两次事务。转发失败时保留“本地已接收、远端待送达”，不回滚本地。
9. **验收粒度：** 默认只承诺进入权威分支的最终 C 合规。要承诺“新引入的每个提交都合规”，就得逐个检查它们（A1、A6）。发布制品另立合同：提交验收不证明最终发布的字节经过了验收。
10. **资源和可用性**：pack 大小、对象数、运行器的时间和内存都要设上限，超限即拒绝；磁盘满、运行器卡死时返回 blocked，不当作通过。

**签名与证据**
- **格式**：一种采用 in-toto Statement 结构的自定义凭据，不自称兼容 in-toto Envelope（Envelope 要求签入 payloadType，并支持多签）。载荷是 JSON，只在签发前规范化一次，然后用 SSHSIG 做分离签名，namespace 固定（例如 `docaxioms-gate@v1`）。这样本机、别的机器和远端都只要 `ssh-keygen -Y verify` 一条命令，再加上第 3 条 owner 批准里的用户在场检查。
- **承载**：一条 note 存两段，逐字节写入和读取（写入时不能经过会清理空白的路径）。第一行是载荷的字节长度（十进制，以 `\n` 结尾），接着是恰好这么多字节的载荷，其余是 SSHSIG 的装甲块。验签端按长度切出载荷，原样送进标准输入，不解析后再规范化，消费的就是被签的那份字节：

  ```sh
  ssh-keygen -Y verify -f allowed_signers -I gate \
    -n docaxioms-gate@v1 -s payload.sig < payload
  ```

  `-f` 用的允许签名者名单取自基线 B 或受保护的远端配置，`-I` 的身份必须在名单里。
- **绑定内容**：
  - 对象：仓库 ID、目标 ref、B、C、T、哈希算法；
  - 策略：策略摘要、治理代次、必需规则集合（哪些阻断、哪些只报告）、批准记录摘要；
  - 执行：检查器制品摘要、扩展和依赖摘要、环境清单、各结果和日志的摘要；
  - 签发：签发身份、协议版本、请求 ID。
- **存放位置**：
  - 签好的凭据本体只有几 KB，写进 `refs/notes/docaxioms`，随 Git 同步。这样别的机器和远端验签不需要访问本机的证据库。
  - 触发了 G12 的提交，凭据里还要带上批准载荷原文和 owner 的硬件签名本体（约 1 KB），以及批准者的身份标识，远端才能独立检查用户在场标志和多成员批准。闸门自己的签名和批准摘要代替不了这份签名。验证用的公钥名单一律取自基线 B 或受保护的远端配置，绝不采信凭据或候选自带的公钥。
  - 闸门的证据库保存完整的检查记录和日志，凭据里只记它们的摘要；仓库之外另有备份。本机对账和补写以证据库为准；别的机器和远端只认验签通过、并且绑定的仓库、ref、C 和治理代次都对得上的凭据。
  - notes 可以被改、被删，普通 clone 也不会自动携带，所以消费方必须验签；找不到凭据，就判 blocked。
  - 普通用户的启动核对，经闸门的只读查询接口读取证据，不直接读闸门的目录。
  - 不用 commit trailer：它会改变 commit OID，形成自引用。
- **签名接口只接受两种请求**：“验收这个候选”，以及 Windows 上的连接认证（见平台做法）。不提供“签任意字节”，否则私钥即使不可导出，服务也会沦为任人调用的签名工具。连接认证的载荷由服务端构造成固定结构，客户端只提供限长的随机数，并用独立的 namespace（例如 `docaxioms-ipc@v1`），签出来的东西不可能被当成验收凭据。
- **环境清单只是闸门的声明**，不是硬件证明。没有测量启动或远程证明时，不能说“硬件证明了执行环境”。
- **防回滚**：只绑定 old 和 new 防不住引用回退后的重放。需要严格防重放时，额外维护一条签名的引用状态链（参考 gittuf 的 RSL）。但这条链本身也能被整体回退，首次接入的人只拿到旧链时发现不了截断；所以还需要可信的外部检查点，或者由消费方记录自己消费过的最新状态。判断先后用单调递增的代次或序号，不用本机时钟。

**owner 批准**
- **触发**：只由精确的路径谓词触发：治理文件、公理锁文件、决策记录、ownership、requirements，以及策略里显式登记的路径。新建任务页不触发。
- **流程**：
  1. 候选先推到闸门的待审引用（例如 `refs/for/<分支>`）。待审入口有自己的合同：只接收数据、跑预审、生成影响报告；不要求还没取得的批准，不签发 G22，不转发，不更新权威分支；允许覆写，过期自动清理。只看 T 的预审结果，在 T、策略摘要、检查器制品摘要、环境身份和外部输入都一致时才能复用；依赖 B→C 差异的规则，一律按正式验收时的基线重新判定。预审只用于需要批准或显式请求的情况，普通变更直接推送一次。
  2. owner 在批准界面里看差异、策略变化和影响报告，然后用 FIDO2 硬件密钥（OpenSSH 的 `ed25519-sk`）签名。
  3. 再推送更新权威分支，闸门核对批准和检查记录后接收。批准绑定的是最终的权威 ref，不是待审引用。
- **批准内容**：签名的载荷写明仓库、ref、B、C、策略摘要和批准用途；候选一变，批准即失效。批准界面一次只展示并签署一个明确指定的请求，不能批量签；待审引用的个数不设限。
- **批准界面要受保护**：从开发者不能改的路径启动（不经过用户的 PATH 和 shell 配置），并回显 C 的短哈希供 owner 比对。否则 Agent 可以让屏幕上显示良性的候选，送去签名的却是另一个。
- **验签端强制用户在场**：OpenSSH 的允许签名者名单没有控制触摸的选项；`ssh-keygen -Y verify` 只记录硬件签名的标志，不据此拒绝（9.9p2 和 10.6p2 的源码都是这样）。所以闸门和任何远端验签脚本，在验签通过后必须自己检查：拒绝用户在场标志为 0 的签名、缺少硬件签名信息的签名，以及普通软件密钥的签名。
- **它保证什么**：指定的硬件密钥，对指定的批准内容签了名，签名时有人触摸了密钥。它能把“终端里的 Agent”和“键盘前的 owner”分开，但不证明 owner 认真读过；单人仓库也不会因此多出第二位审查者。
- 没有硬件密钥时能否退回到系统管理员口令，留给 owner 决定（第十二节第 3 项）。决定之前，G12 只认硬件签名。如果采用，G12 改为认策略允许的批准方式，并记录实际用了哪种方式和认证证据；口令不等价于硬件批准，不能静默降级。

**平台做法**（官方文档已核实；部署细节需要实测）

| 平台 | 服务与入口 | 闸门密钥 |
|---|---|---|
| macOS | 系统级 launchd 任务，用 `UserName` 指定专用账号；用 `Sockets` 创建本机 Unix 套接字，`getpeereid` 核验对端 | 首版是软件密钥，放在闸门用户的私有目录里。Secure Enclave 本方案选用 P-256，原型走 CryptoKit 直接创建和恢复密钥的路线（无登录的 daemon 用不了的是 Data Protection Keychain）；Apple 开发者技术支持说过 daemon 经 CryptoKit 使用它可以工作，但没有确认正式支持，而且默认的访问条件在首次登录之前可能失败。登录前、锁屏后、普通后台三种场景要分别原型验证 |
| Linux | system 级 systemd 服务，`User=` 指定专用账号（普通的 user service 不构成跨用户边界）；pathname Unix 套接字，显式设置权限，`SO_PEERCRED` 核验对端 | `LoadCredentialEncrypted=` 只保护静态凭据，启动后仍是明文；要让私钥一直留在硬件里，可以经 PKCS#11 或 TPM2-TSS 的 FAPI 使用 TPM 或硬件 token |
| Windows | SCM 服务加虚拟服务账号；Named pipe 不能用默认描述符（它向 Everyone 和匿名账户授予读权限；Node 的 `node:net` 用的就是默认描述符），需要一个原生辅助程序：显式 DACL、只给最小访问权（不要给客户端 `FILE_GENERIC_WRITE`，它包含创建管道实例的权限）、`PIPE_REJECT_REMOTE_CLIENTS` 拒绝远程客户端，并核验客户端身份。`FILE_FLAG_FIRST_PIPE_INSTANCE` 只在创建第一个管道实例时使用（后续实例带它会报 `ERROR_ACCESS_DENIED`）；它只能让闸门在名字已被占用时创建失败，防不住抢注：攻击者先占名时，客户端照样会连上假服务。所以闸门检测到占名就拒绝启动，客户端也要认证服务端：连接后客户端发一个随机数，闸门按上面的连接认证格式签名，客户端用系统只读目录里的闸门公钥核验，不依赖服务端 PID（有复用的竞态）。客户端同样需要原生辅助程序：普通的 Node 客户端会请求 `GENERIC_WRITE`，拿掉写权限后建不成所需的双向连接，可能退成只读；所以要以最小权限调用 `CreateFile`，并指定 `SECURITY_SQOS_PRESENT | SECURITY_IDENTIFICATION`，否则认证完成之前，假服务就可能模拟客户端的身份 | CNG 的平台加密提供者（TPM）；DPAPI 的本机作用域在这里不够用 |

密钥不可用时，正式验收返回 blocked，不能悄悄降级成另一把软件密钥。

### 4. 与远端的关系

三种模式不互斥，薄验签和复验可以叠加：

| 模式 | 适用范围与边界 |
|---|---|
| 本地权威（可选单向镜像） | 闸门仓库就是权威仓库，可以离线完成检查、批准和接收；接收后由闸门用独占凭据单向推到镜像。只有当远端没有其他写入者、bypass 或开发者用户下的写入、管理凭据时，才能说发布路径是封闭的。**首版推荐这一种** |
| 本地验收，远端薄验签 | 远端只验签：签发者已授权、策略代次对、对象绑定一致。不再重跑文档检查。远端必须只允许快进 |
| 本地验收，远端复验 | 需要独立环境或跨平台矩阵时使用（A1） |

**远端必须只允许快进。** 两台机器各自验过 C_A 和 C_B，远端把它们合并成 T_AB，这棵合并树没有经过任何检查。落后的一方必须在本地 rebase 或 merge，让闸门对最终组合出的树重新验收并签名，然后才能快进推上去。

**多机时要分清四样东西**：检查基线 B（本机闸门的权威状态）、远端目标引用的旧值、提交的验收凭据、本次发布的许可。离线接收或多机之后，B 可能不等于远端的旧值。首版只设一个权威发布者；发布时按远端旧值做条件更新（例如 `--force-with-lease=<ref>:<旧值>`），旧值不匹配就回到本地重新判断。这个参数本身允许非快进推送，所以闸门推送前先在本地确认远端旧值是 C 的祖先；远端有“只允许快进”的规则时，再多一道保险。

**GitHub.com 上的事实**（官方文档已核实）：
- 免费账号只有公开仓库能用 rulesets；个人私有仓库要 Pro 等付费套餐。
- 传统分支保护里“限制谁能推送”只对组织仓库开放。个人仓库要用 rulesets 的“限制更新”，并把部署密钥加进 bypass。
- bypass 里的 `DeployKey` 是一类角色（API 里 `actor_id` 为空），放行的是仓库所有的部署密钥，不能指定某一把。要做到只有闸门能推，仓库只能有这一把带写权限的部署密钥；GitHub App 能给出更明确的发布身份。
- bypass 会豁免整条 ruleset 里的全部规则。所以“限制更新（给闸门 bypass）”和“只允许快进、必需检查（不给任何 bypass）”要拆成两条 ruleset。
- 原生的“要求签名提交”只要求签名经过验证，不能指定只认闸门这个签名者，也不验证自定义的凭据。

**GitHub.com 上的薄验签**（需要原型验证）：
1. 本地闸门验收最终的 C，签发凭据，写进 notes；
2. 推到一个暂存分支，连同 notes，让 C 在远端可见；
3. 一个必需检查为这个精确的 C 验签（`ssh-keygen -Y verify` 核验 notes 里的凭据，再检查批准签名的用户在场标志），报告结果；
4. 闸门按旧值条件更新权威引用。

必需检查可以是无状态的 Actions 工作流，不用常驻服务；但必需检查只按检查名匹配，来源选 GitHub Actions 也分不出是哪个工作流，任何工作流里同名的 job 都能冒充。所以整个 `.github/workflows/` 都要列为治理文件（第 3 条）。别的写入者也能改工作流的多人仓库，要把检查来源固定到一个独立的 GitHub App；组织的 required workflow 能固定来源仓库，但它约束的是 PR 合并，不能直接用于本文的直推流程。网页上的 merge、squash、rebase 会产生新的 C′，要么回到本地重新验收，要么禁用这些合并方式。

### 5. 本地方案守不住的

| 缺口 | 本地的上限 | 能否补上 |
|---|---|---|
| 开发者用户下留着能写受保护分支或管理仓库的凭据（`gh` 登录态、经典 PAT、SSH 密钥、浏览器里的登录） | Agent 可以绕过闸门直接推送；有管理权限时，还能临时改掉远端规则、推完再改回来 | “远端只认闸门签名”补不上：管理凭据能改规则，免费的个人私有仓库也开不了规则。“Agent 沙箱的网络白名单”也补不上：拉依赖本来就要放行托管平台的域名，分不出拉包还是推送；沙箱外的进程、浏览器和其他工具也不受它约束。**唯一有效的补法是凭据降权**：开发者用户下只留只读凭据，或者受服务端规则约束、写不了受保护分支的写凭据（细粒度 PAT 只按仓库和权限授权，没有分支范围，不能靠 token 本身隔离分支）；受保护分支的推送权只交给闸门 |
| root 或管理员 | 能控制服务、配置和执行环境 | 签名若来自被控制的签发器，纯验签无法识别 |
| owner 自己 | 可以改信任根、规则和托管权限 | owner 同时控制远端时补不上（A0：owner 本来就是最终权威） |
| 密钥泄露，或签名服务被滥用 | 可以伪造获授权的声明 | 撤销之后可以拒绝；撤销之前，单靠验签区分不出来 |
| 直接在托管平台上修改 | 本地感知不到 | 受保护的验签规则能挡住普通写入者，管理员除外 |
| 批准界面被替换（所见非所签） | 屏幕上显示的候选和送去签名的不是同一个 | 受保护的启动路径加哈希回显能缓解，见第 3 条 |
| 工作区的 `origin` 被改指别处 | Agent 可以推到假入口，再声称“已过闸门”；权威分支没被污染，但会误导收尾判断 | 启动核对和收尾检查都核对 `origin` 指向受控入口，并向闸门查询凭据 |
| 本机时钟被回拨或漂移 | 影响密钥有效期和豁免时间窗 | 先后顺序改用代次或序号；确实需要时限的授权（例如密钥有效期）要用可信时间，没有可信时间就不设时限，改用显式撤销 |
| 整机快照回滚（Time Machine、磁盘快照） | 工作区、闸门仓库和证据库一起回到旧状态，已撤销的密钥或决策会复活，单机自己察觉不到 | 联网后与远端引用和外部检查点对账 |
| 本地证据被删除或回滚 | 签名能发现内容被伪造，但不能保证证据还在、列表完整 | 独立归档和外部检查点可以补强 |
| 未受管的出口：没登记的 ref、标签、发布 API、包仓库；制品被替换 | 闸门只守它登记的引用；提交验收不证明发布的字节 | 发布凭据同样只交给闸门；制品绑定另立合同 |
| 可用性：磁盘满、密钥丢失、测试卡死、恶意的大 pack、缓存污染、恢复失败 | 闸门不可用时就推不了，也发布不了 | 资源上限、恢复流程和备份写进 operations |
| 多台机器 | 每台机器有自己的设备密钥，由共同的授权根登记（允许签名者名单属于治理文件）。“任何登记过的机器签名都接受”，意味着最弱的那台机器也能决定结果 | 多人仓库可以要求治理变更有多个不同成员的签名 |
| 文档语义、测试是否充分、owner 原意 | 仍要靠人判断 | 补不上 |

离线时，可以用缓存的工具链、依赖、策略和公钥完成本地验收。但确认不了最新的远端基线、撤销状态或在线批准时，只能声明“本地通过、待同步”，恢复连接后重新核对。

### 6. 验收器契约

**结果状态**
- 结果分五种：
  - pass、fail；
  - blocked：应该检查，但无法完成；
  - not-applicable：适用条件算出来为假；
  - disabled：没有启用，并且要显示出来。
- 必需规则的 blocked 和 disabled，一律不算成功。
- 每条结果都带对象计数和适用原因：
  - 声明“必须存在”的目标匹配到零个：失败；
  - 本次确实没有对象：属于合法空集，照常通过，但要写出原因（A7）。
- 正式验收的 blocked 是新语义：现行 GUIDE 规定，检查无法按配置比较时只给出 note，不导致失败。消费项目要用正式验收，得作为一种新模式另行批准。

**输入绑定**：每次验收绑定仓库、B、T、策略摘要、检查器制品摘要和环境身份。同一棵源码树换了工具链或外部输入，旧证据不能沿用（A1、A2）。

**独立性**
- 由第 3 条的接收端契约保证：基线策略、治理迁移、运行器隔离、签名接口受限。
- 每条扩展结果的规则 ID、计数和终态都要核对；进程提前退出、返回非法 JSON，都不能算绿。
- **阻断和报告分开**：策略里只有获授权的阻断集合决定接收与否；只报告的规则照常运行，发现写进完整结果，不影响接收（本仓库就是这样，见 AD-7）。运行出错一律失败。
- 不能只凭 `--report` 或 CLI 的退出码认定通过；完整的机器结果可以作为证据。

- **原 G18（本地恢复凭据）删除**，理由见第五节。
- **G12 从“只认平台事件”改为本地硬件签名的批准**；有远端时，平台审批可以作为额外一层。
- **G17 不再是“没有平台 API 就 blocked”**，而是“缺少配置的可信运行器才 blocked”。证据仍然存放在被验收的树之外。任务的关闭记录只列出应该跑哪些验证的 ID，不写回验收结果。
- **G21 改为可选。**

**G16 的范围和处置合同**
- **范围**：只覆盖策略里显式登记的契约路径。机器不知道什么算“公开接口”，没登记的就报不出来，这个盲区要写明（A6）。
- **与 G09 的分工**：pin 住的切片照样要有处置。只靠 G09 的话，改了代码、刷新摘要就能通过，留不下任何处置。所以 G09 管摘要相等，G16 管登记路径上的每项变更都有处置，在启用了 G16 的契约路径上两者同时适用。没有启用时，只刷新 pin，靠影响报告单列“刷新了摘要但正文没改”的条目（第四节第 6 条）。
- **处置**：按接口或变更组登记，不逐文件填表。二选一：关联到已核对的文档段落；或者写明“无需改文档”及理由。
- **绑定**：处置写明责任人，并绑定差异摘要；差异一变，处置即失效。责任人确认即可，只有治理变更或策略明确规定的才要 owner 批准。
- **观察**：首期先做报告，观察它是否沦为例行填表，再决定是否阻断。
- **与 `codeToDocs` 的区别**：“代码改了文档没动”是启发式提醒，继续做 aid；“每项受管变更都有绑定差异的处置”是精确的流程门禁；“处置一定正确”，谁也保证不了。

**始终只能做 aid 或人工审计的**：散文与行为是否一致；某次改码是否必须改文档；演化措辞；理由是否充分；owner 的话是否被理解对了。LLM 可以提出带出处的 finding，但不能做阻断语义的门禁（A7、M2）。

## 四、文档依赖图与反射式更新

### 1. 设想与边界

**owner 的设想**：把文档组织成一棵树或一张图。一个阶段或任务完成时，只更新最基础的一份文档，工具就沿着图找到与这次改动相关的文件，做相应的更新，像生物的反射：刺激发生，就地反应，事后再报告给大脑。

**结论**：
- **能做，但要分两半。** “找到相关的地方”可以做得精确，前提是依赖已经登记；“自动更新”只适用于能从源头重算的内容。散文的改动最后都要有人或 agent 确认（A0、A6）。
- **它是图，不是树。** 一份文档常常依赖好几个来源。边表示“我的内容依赖你”，不是链接：链接只说明能走过去。
- **没有唯一的根。** 变动有三个独立源头：代码（软件实际怎么做）、owner 的决策（应该怎么做）、任务（做到哪一步）。“只改一处”只在同一类事实及其机械派生物里成立（M3），例如任务状态改一次，任务索引和计数由它生成。任务关闭可以作为把三类变动收在一起处理的入口，但推不出设计文档该怎么改，也不能自动决定阶段焦点。
- **不另起一套机制。** 依赖边从现有的 pin、决策落点、研究与任务的挂接、生成器输入里来；检查和命令沿用现有的。

### 2. 依赖图

**边从哪里来**。文档里写的引用和 pin 是“下游指向源头”；引擎在内存里反过来建索引，得到“源头 → 下游”的传播方向。

| 边 | 含义 | 精度 | 用途 |
|---|---|---|---|
| 文档 pin | 段落内容依赖 | 高：钉住的切片一变就知道 | 传播的主干。现有 pin 已能钉 Markdown 文件的整文件或行段；按 `#标题`、`<a id>` 钉段落是新增 |
| code pin（已有） | 代码片段 → 文档段落 | 高 | 传播的起点之一 |
| 决策落点（已有） | 决策 → 落地段落 | 高 | 决策变化时找到要改的段落 |
| 研究 → 任务 | 生命周期绑定 | **现在不精确**：是文件名子串匹配（缺陷 8），修好后才能当精确的边 | 任务关闭时找到可以退役的研究 |
| 生成器输入（新增，G20） | 源 → 生成物 | 高 | 自动重算 |
| `codeToDocs`（已有） | 代码 glob → 文档 | 低：改注释也会触发，文档改一个字就消警 | 只做提醒，是 G16 的候选来源 |
| 普通链接（已有） | 可达 | 作断链检查很准；作“需要更新”的依据极不准 | **不参与传播**，只服务可达性、断链和退役时改链接。README 链到全仓，用链接传播会把整张图标脏（A7） |

**节点的粒度要先定。** 现有 pin 只知道“哪个文件哪一行的注释依赖哪个源切片”，没有记录这条 pin 属于下游的哪一段。按整个文件建图，两份文档里互不相干的段落互相 pin 时，会被误判为成环。建议：一条 pin 属于它所在的最小段落（最近的标题段，或它所在的 `<a id>` 块），节点就是这些段落。

**锚点要先补的合同**：
- 独立成行的 `<a id>` 后隔空行时，只取到标签本身（缺陷 12）；
- 锚点必须唯一：重复的 id、标题锚点与显式 id 冲突，都要报错，不能静默取第一个；
- `<a id>` 块到哪里结束要写明：只到紧接的一块，还是到下一个锚点或标题；
- 显式锚点的支持范围要写明：继续只认 `<a id>`、`<a name>`，还是也认 `span`、`h3` 等其他带 id 的标签；
- 段落摘要**不含标题行和 `<a id>` 标签本身**，只算正文。否则标题一改，摘要必变，“改名后按同一摘要找回原段落”就永远不会命中；
- pin 的路径规则和链接相反：pin 从仓库根算，`./`、`../` 才相对所在文档，并拒绝 `/` 开头；链接从所在文档的目录算，`/` 开头才是仓库根。是否让 pin 也接受 `/` 开头，由 owner 定（第十二节第 16 项）。

**环**：
- 导航链接成环很正常，可达性检查已经去重。
- 依赖子图（文档 pin 与生成器）里的环，首版一律拒绝：检查报出完整的环路径，作为 gate。生成子图必须无环才能按顺序重算；散文 pin 成环，说明同一件事在两处转述，违背 M3。将来如果确有需要，再改为把整个环当一组复核。

**找不到的**：没有登记成边的隐含关联，任何图算法都找不到，例如某个返回值的含义变了，另一篇文档用散文提过，但既没有 pin 也没有配 `codeToDocs`。这一块只能靠定期的 garden 审计，以及第 5 条第 5 项从历史推荐的候选边。

### 3. 反射弧：哪些自动做，哪些交给人

| 反射弧 | 文档系统 |
|---|---|
| 感受器：察觉刺激 | 变化检测：pin 摘要、Git 差异、决策状态变化、任务关闭 |
| 传入神经 | 依赖边 |
| 反射中枢（脊髓） | 规则引擎：沿依赖图求受影响的集合，按先后顺序排列 |
| 传出神经与效应器 | 动作：生成物重算落盘；散文标为待复核，可交 agent 起草 |
| 事后上报大脑 | 报告：自动做了什么、还剩什么要确认 |

**分界判据**：一个动作要同时满足下面五条，才能交给“脊髓”自动执行；缺一条，就只生成待办清单或候选补丁，交给人或 agent 判断。
1. 同一个仓库状态下，结果唯一确定；
2. 不新增或改变散文的含义；
3. 没有歧义：有多种可能就停下上报（如 pin 的 `ambiguous-move`）；
4. 能从源头重算，也不静默改写历史记录（A5）；
5. 写入范围已获授权，结果能机械验证。

“链接目标以外的文本没变”（`withoutLinkTargets` 比较相等）**不能**证明第 2 条：把 `[policy](policy-v1.md)` 改成 `[policy](policy-v2.md)`，比较结果相等，指的却是另一份规范。所以自动改链只限“同一个对象从旧位置搬到新位置”的映射，而且这个映射已获授权、没有歧义。

**比喻要修正的三处**：
- **只在离散时刻反应。** 不做实时的后台改写，否则会与正在进行的编辑冲突，留下半成品状态。只在执行命令或提交前触发，而且所有写入都发生在形成最终候选之前（第 7 条）。
- **遇到散文节点要停。** 传播经过一段散文时，必须等这一段处理完，才能决定要不要继续往下传。
- **“习惯化”不能落到检查本身。** 检查不能因为常报就自动降级放行（违背 A6）。工具要减少假刺激，免得人习惯化（A7）：
  - 同一根因只报一条，下游折叠为“另有 N 处等待上游”；
  - 下游处理后内容没变，就不再往下传（提前截断，见第 6 条）；
  - 用 Git 历史统计每条提醒规则报出的地方后来是否改了散文。这只是候选信号：无关的润色也会计入，正确的“无需改文档”反而没有改字。所以它只用来提出收窄、删除或升格的建议，由 owner 决定，不能自动升格，也不能代替 AD-7 要求的“值得改文档的发现”。

### 4. 第一阶段：建边与只读报告

全部长在现有代码上，不必等闸门。

| 项 | 做什么 | 级别 | 复用 |
|---|---|---|---|
| 1. 按锚点钉段落 | 先补第 2 条的锚点合同；pin 支持 `#标题` 与 `<a id>`；摘要只算正文、去掉切片里的 pin 注释、统一换行，并标上新摘要版本；同文件内唯一同摘要的段落改了名，判为 `moved`，由 `pin --relocate` 修正；检查名和 CLI 提示里写死的“code pins”改成同时适用于代码和文档的说法 | 锚点不存在、不唯一、格式错误、成环：gate。新增的“锚点段落内容变了”：由 owner 决定（第十二节第 13 项） | `src/pins.mjs`、`src/markdown.mjs` 的 `passage`、`htmlComments` |
| 2. 影响报告 | 以相对基线的代码差异、决策变化、任务变化为起点，沿依赖图按先后顺序列出：直接失效的、等待上游的、多个上游的原因、同一根因折叠后的下游，以及没有登记依赖的范围；单列“刷新了摘要但正文一字没改”的条目 | aid | `inspectPins`、`decisionRows`、`changedFiles`、`codeToDocs`；起点依赖缺陷 17 修好 |

**生成物的排除范围要分两类**：产品入口这类生成物（如 `CLAUDE.md`、各产品的规则文件），从链接、路径、命令、决策引用、演化措辞、pin、可达性和 garden 中排除；导航索引类生成物（如决策索引），仍参与断链检查，也是可达性的跳板，只从散文类检查和 garden 中排除。

### 5. 第二阶段：从报告走到“一个动作走完整条链”

依赖第一阶段的边和数据。

1. **任务收尾作为统一入口。** 关闭任务时，把这次的代码差异、决策变化和任务状态收在一起，按依赖顺序：
   - 自动完成满足第 3 条判据的部分：研究移入 history（条件见第 7 条）、补横幅、改链接、重算索引和计数；
   - 列出待办：阶段卡、受影响的描述段落；在承诺 G19 完整关闭的项目里，必需的散文处置要在关闭之前做完，不能留到关闭之后；
   - 事后报告：自动做了什么、还剩什么。
   这些改动与代码放进同一个候选，再验收（第五节第 4 条）。
2. **agent 按顺序起草，逐段停下确认。** 人发起复核后，影响报告交给 agent，从最上游开始一段一段起草；每到一个散文节点停下，确认后再往下走；处理后没变就截断。这是受控的交互辅助，不是第九节第 3 条禁止的后台改写。
3. **通用生成器。** 允许登记多个生成物，按依赖顺序重算，内容不变不重写，统一由 G20 校验。
4. **用数据提出规则调整的建议。** 见第 3 条“习惯化”。
5. **从历史推荐候选边。** 统计哪些文件总是一起改，提示“这里可能缺一个 pin”，只做提醒，由人决定加不加。
6. **处置记录（按需）。** 只有要承诺“已处置”时才做，与 G16 是同一套：绑定当前差异、下游段落和依赖定义，写明谁处理的、结论、不改文档的理由；差异一变即失效。它证明的是有人声明处置过，不证明判断正确。不需要这个承诺的项目不做。

### 6. 提前截断与复核证据

**提前截断**（借鉴 Bazel Skyframe 和构建系统的 early cutoff）：
- 现在的 pin 摘要对原始切片计算（`hashSourceSlice`），切片里的 pin 注释也算进去。刷新中间一份文档的 pin，会让依赖它的下游全部失效。所以新的锚点摘要去掉其中的 pin 注释。
- 去掉注释之后，必须另外比较**依赖定义**：中游的某一段删掉、增加或改指向一条 pin，正文摘要可以不变；而 `inspectPins()` 只列出还在的注释，看不到被删的依赖。所以要分别比较基线和候选两侧的正文摘要和依赖定义集合。依赖定义变了，只触发这一段自己的处理，不改变它对下游的摘要。
- 影响报告用三种状态：
  - 中游还没处理：下游标为“等待上游”，不能当作已截断；
  - 中游处理完且正文没变：截断这条边；
  - 下游有多个上游：任一上游还没处理，它就仍待处理。

**复核证据**：
- `pin --write` 只是刷新摘要，证明不了有人看过。
- 不做处置记录时，工具只能说“摘要一致”和“影响候选”，不能说“已复核”，也不能据此承诺整条链已经截断；影响报告里要保留“语义复核靠注意力”的边界（A6）。日常散文不设“复核声明表单”：同一个身份下，填表和直接刷新一样容易，等于没有证据（A6、A7）。改为在影响报告里单列“刷新了摘要但正文没改”的条目，让审阅的人重点看。
- 要承诺“已处置”时，用第 5 条第 6 项的处置记录；高风险边界（K2、治理变更）用第三节的硬件签名批准。

### 7. 写入的边界

- **所有写入都在形成最终候选之前完成**：工作树里的命令完成写入和必要的处置 → 形成最终的 C 和 T → 正式验收只读，只重算、比较和签发。G20 不一致时拒绝或返回待修，不修改已绑定的候选。
- **退役一份文档之前**：
  - 它不再有开放的依赖。研究被几个开放任务共用时，关闭其中一个只解除这次的关联；没有剩余的开放任务、仍有效的内容已迁给负责它的文档之后，才能退役。
  - 迁移的文件自身的相对链接和相对 pin 都要改写。移进 history 后，现有的链接和 pin 检查不再扫描它，所以要有迁移专项验收：核对迁移前后入链、出链、锚点和 pin 的目标身份，不能拿现有门禁代表“全仓引用正确”。
  - 指向它的链接：入口路由、现行决策的落地点和其他现行文档，不能自动改指到 history；有指定的接替文档时列成待人确认的改动。只有 K1 记录里的追溯链接，可以无歧义地改指到 history 里的新位置。
  - pin 注释不在 G13“可以改链接 URL”的例外里。现行文档里的 pin 怎样重定向，K1 记录里的 pin 怎样保留和解释，要分别写明，不能统一批改。
- **写入命令的协议**：预览优先，没有 TTY 时只给预览（借鉴 Dosu CLI 的 `--confirm`，`pin --write` 也适用）；写入范围显式授权；输入绑定；失败可恢复；存在降级 note 时拒绝写入，也不和增量模式混用（借鉴 DocGuard 写基线前的两道守卫）。确认协议仍不能证明语义已复核。

## 五、会话重启与中断恢复

### 1. 恢复的是“可以安全接着干的公开状态”

| 状态 | 位置 | 类别 | 谁写、何时写 |
|---|---|---|---|
| 任务目标、范围、完成条件、开放步骤、待 owner 决定的问题、未验证项 | 任务页（每个任务一页，入库） | 分段标注 K4、K3，引用的规范是 K2 | 领任务、范围变化、遇到阻塞、暂停时写；可由命令代写，经验收 |
| 项目层面的焦点、优先顺序、冻结期、全局阻塞 | `CURRENT.md`（手写，入库） | 分段标注 K3、K4 | 这些事实变化时写 |
| 未提交的改动、分支、HEAD | 不落文档，随时从 Git 查 | 现场观测 | Git |
| 已签名的验收记录 | 闸门证据库 | K1（闸门监督运行并签名） | 闸门 |
| 当前任务指针；本会话跑过的命令 | 本地、可丢弃，不入库 | 本机运行态，不进 M1 的分类，任何文档都不能拿它当依据 | 领任务时写；有成对钩子的 Agent 自动写 |

### 2. 核心机制：每次启动都做无状态核对

新启动、原生 resume、压缩后重新接管、换 Agent、换人，都走同一条命令。会话开始钩子会调用它；没有钩子的 Agent，由 AGENTS.md 要求手动调用。步骤：

1. 从 Git 现算 HEAD、暂存区、工作树和相关未跟踪文件的清单：记录路径和内容摘要，而不是 `git status` 的文字输出。
2. 读 `CURRENT.md` 和当前任务页。
3. 配了闸门时，查闸门证据库：哪些提交已经验收过；当前这棵树和最近一次验收相比改了什么。没配闸门时跳过这一步，简报里写明“没有验收记录”。
4. 生成二十行左右的简报注入上下文：任务和下一步、差异摘要、待 owner 决定的问题、未验证项、项目焦点。

**判定中断的信号**：
- 工作树有改动，但任务页里没有暂停记录；
- 或者任务页写着“进行中”，却找不到对应的改动。

出现这两种情况时，简报的第一项就是“先对账：继续、回滚还是收尾”，由人或 Agent 决定。

**恢复只做观察和归因**，绝不自动 reset、覆盖脏工作树，也不无条件重跑命令。

### 3. 裁决与理由

- **不用“写前事件日志 + 恢复凭据拦截写入”。** shell、持久终端、Ctrl+C、钩子超时都会让日志不完整；用它拦截写入会造出假中断，进而锁死会话，逼人关掉钩子（A7）。
- **文件监听守护进程也不改变这个结论。** 三个平台的内核事件都会丢失，看不到命令，也看不到退出码。它只能做缓存，以及在发现事件缺口时让缓存失效、重新扫描。
- **闸门签名的验收记录可以当依据**（G17），因为它是闸门监督运行的，而且针对不可变的提交。Agent 自己的日志和文件事件只能补充信息。
- **任务状态的唯一所有者是任务页（M3）。**
  - `CURRENT.md` 只写项目层面的事实，不列任务。full 档为它提供新模板，分段标注 K3、K4。
  - 冻结期这类没有代码可以 pin 的事实，靠复核日期加 garden 防止过时（A2）。
- **任务页本身也可能陈旧。** 这一点由启动核对和 G19 兜底。

### 4. 关闭任务的顺序

关闭记录、把任务页移进 history，以及收尾命令完成的研究归档、改链接、重算索引和计数，这些改动都要和代码放在同一个候选里，再验收这个最终候选：配了闸门时由闸门正式验收，没配时对它跑普通验证。否则验收的 T₁ 和最终落地的 T₂ 不是同一棵树。验收本身只读，不在验收过程中生成或迁移（第四节第 7 条）。具体顺序见第七节第 4 条的“准备关闭”。

### 2. 适配器的组织

**位置**：`adapters/<产品>/`，与 `templates/` 并列，不进 `core/`。`package.json` 的 `files` 白名单要同步更新，并用打包测试验证。

**manifest**：每个产品一份，声明：
- 产品、形态和版本范围；
- 入口路径和导入方式；
- 技能的发现路径；
- 实际支持的事件，以及拒绝、出错、超时时的行为；
- 信任模型；
- 哪些能力查过文档，哪些在安装版上探测过；
- 已知缺口。

**四种能力分别探测**：发现入口、导入内容、阻断操作、恢复会话。模型回答“我读过了”不算证据。

**防止副本（A4）**，按优先级选择：
1. 原生读 `AGENTS.md`：不生成副本。
2. 能可靠导入：生成一行桥接。
3. 只能按路径或按需加载：生成规则文件，并写明加载条件。
4. 以上都不行：从同一来源生成限长内容。

生成的文件都登记在 profile 里，由 G20 校验；排除范围分两类（第四节第 4 条）：产品入口这类生成物从链接、路径、命令、决策引用、演化措辞、pin 检查、可达性和 garden 中排除；导航索引类生成物仍参与断链检查和可达性。现在只有模板里的 `CLAUDE.md` 从 garden 中豁免了，其他检查照样会扫它。

**钩子只做转发**，转给 `docaxioms hook <事件>`：
- fail-closed，总是输出合法结果；
- 用 matcher 只挂在写文件和 shell 工具上；
- 先走快速路径：优先查监听进程的缓存，其次做零依赖的文件判断，与受保护文件无关就立即退出；
- 直接调用本地安装的 CLI，不经过 `npx`；
- 一个产品加载另一个产品的钩子时，按调用 ID 去重。

**钩子在本地终审下的定位**：钩子只负责提前提醒。即使所有钩子都被绕过，坏提交也进不了权威分支，因为最后一道是闸门。

**按需规程**：工作、审计、恢复三个技能，按各产品的发现路径生成，并受检。只有通过加载探测的产品，才把 GUIDE 改为按需读取。`AGENTS.md` 保留几条底线：验证命令、禁止事项、启动核对；配了闸门时再加“只能经闸门推送”。

**分级**：
- Tier 1，有契约测试：Claude Code、Codex CLI、Cursor、Copilot（只限本地 IDE 和 CLI 形态，云端 agent 连不上本机闸门）、Gemini CLI；
- Tier 2：只提供模板；
- 已归档的产品标为旧版。

**接入与升级**：`init` 遇到已有的入口、阶段卡、索引和计划时，按第七节第 5 条另存并替换；`update` 迁移适配器，并提示需要重新信任的钩子。

**供应链**：克隆来的仓库自带的钩子也可能是恶意的。闸门只运行基线中已经受信任的扩展。

## 七、文档体系

### 1. 两档预设

- **minimal**：保留现有 9 个模板。必读链缩短，决策前缀改为 `D-`，本地运行态加入忽略规则。`CURRENT.md`、`plan.md`、`log.md` 照现行 GUIDE 手写。闸门可选。
- **full**：下表全部。`requirements.md`、`operations.md`、`ownership.md` 按需启用。

文档档位和闸门是两个独立的选择：minimal 也可以配闸门，full 也可以不配。下表中与闸门有关的内容（设备登记、允许签名者名单、只经闸门推送）只在配了闸门时适用。

单一仓库是默认场景；monorepo 下的嵌套作用域还没有设计。

### 2. full 档文档清单

原则：
- 高频、并行改动的事实（任务、研究、审计），一事一文件，状态由所在目录表达，不维护汇总表。
- 低频的决策，保留一份入库的薄索引。

固定文档（路径相对项目根）：

| 文档 | 类别 | 唯一负责 | 谁读、何时读 |
|---|---|---|---|
| README.md | K3 | 项目是什么、怎么用、支持范围 | 人首次接触时 |
| AGENTS.md | K2 路由 | 必读顺序、验证命令、禁止事项、启动核对；配了闸门时加上只经闸门推送 | Agent 每次启动，≤100 行 |
| CURRENT.md | 分段标注 K3、K4 | 项目层面的焦点、优先顺序、冻结期、全局阻塞 | 每次接手，≤45 行 |
| docs 下的 README.md | K3 | 现行文档和各条目目录的总索引 | 找文档时 |
| docs 下的 requirements.md | K2 | 已接受的行为要求及验收 ID | 需求、实现、审查时 |
| docs 下的 architecture.md（超预算时拆到 design/） | 分段标注 K2、K3 | 结构、边界、不变量、接口，带 code pin | 改相关模块之前 |
| docs 下的 limits.md | K3 | 已知限制、不支持的场景 | 设计、使用、验收时 |
| docs 下的 operations.md | 分段标注 K2、K3 | 构建、验证、发布、回滚；协作流程；闸门的安装、恢复和设备登记 | 发布、接入时 |
| docs 下的 ownership.md | K2 | 角色、授权身份、批准规则、接替规则；允许签名者名单由它生成 | 批准、交接、权限变更时 |
| docs 下的 decisions/README.md | 生成的索引 | 每条决策的 ID、标题、当前状态 | 追溯理由、核对规范时 |
| docs 下的 history/README.md | 路由 | 历史入口和阅读边界 | 追溯时 |
| docaxioms/ 下三份 core 文件 | K2 | 公理、指南、审计协议 | 接入时；其余按需 |

项目侧固定 11 份（其中决策索引是生成的），core 副本 3 份，另有 core 许可证。

项目自己的生命周期差异（批准角色、合法转换、关闭条件）：机器可读的部分放在 profile，说明放在 operations 和 ownership。GUIDE 只写一份通用流程。

**条目目录**（都在 docs 下，每条一个文件）

条目 ID 带类型前缀和日期，例如 `D-20261126-cache-ttl`、`T-20261126-pin-crlf`。前缀必须保留，原因是现在的决策引用检查靠“前缀加数字”来识别引用。这条匹配规则要相应改写，并且同时识别 legacy 文件里登记的旧 ID。

| 目录 | 类别 | 规则 |
|---|---|---|
| decisions/ | 授权记录是 K1，规范效力是 K2 | 写完就永不再改。推翻、部分推翻或撤回时，新增一条记录，写明替代谁、作用范围多大，它是替代关系的唯一权威（M3）。索引里的当前状态由生成器算出，经 G20 校验。改公理的决策，按锁文件和 AD-6 的规定引用 owner 原话。未发布的决策能否删除，交给 owner 决定 |
| tasks/ | K4 | 在这个目录里，就代表任务是开放的。关闭时写入关闭记录，再移到 history/tasks/；完成日志就是 history/tasks/ 本身 |
| research/ | K4 | 必须有真实链接指向开放任务。方向与 minimal 档“计划链向研究”相反，见缺陷 8 |
| reviews/ | K1 | 带日期的 garden 审计报告及其处置 |
| history/ | K1 | 退役文档、关闭的任务和研究 |

**引擎改动**
- **可达性**：目录链接现在：可达性检查把它展开成目录下的 README.md；链接检查只要目录存在就放行，带锚点时按目录的 README.md 核对；落地点不能是目录（缺陷 9 已修）。改为：只有登记过、受 schema 校验的条目目录，才算“链接目录即视为目录下的文件可达”，而且每个文件都要通过条目结构校验。决策目录另外接纳生成的 README.md 和登记过的 legacy 文件，两者都不当作单条决策校验；整个决策目录不算描述文档。
- **单文件假设**：决策表解析、描述文档集合、落地检查、garden 等多处假设“一类东西就一个文件”，需要同时兼容两种模式。

**M1 按段标注**：同一份文档里同时有 K2 契约和 K3 现状时，分段标出。garden 只审 K3 段，不能拿代码现状去覆盖 K2。

### 4. 生命周期：每一步动哪份文档、由谁守

下表按配了闸门写。没配闸门时，预审、审查、推送三步退回本地 check 加远端 PR 流程，G17、G22 没有强制保证。

### 5. 接入：由 agent 迁移，由检查收口

owner 在 2026-11-28 定下方向：接入以后（新项目和已有项目都一样），文档主要由 agent 维护，所以接入本身也交给 agent 做。docaxioms 只做两件确定的事：`init` 做机械的替换；一个只读的验收命令列出还不符合的地方，agent 改到它通过为止。本条经 codex、agy 各复审一轮后修订（[codex](design/codex-onboard.md)、[agy](design/agy-onboard.md)）。

**现在的情况**：Claude 在临时目录里建了一个故意不规范的项目，实跑当前 CLI：
- 根目录 `AGENTS.md` 152 行，原有的 `CURRENT.md` 62 行。`init` 不动它们，结果预算检查和阶段卡检查都是 gate 失败；agent 读到的还是旧的 `AGENTS.md`，不会被引到 GUIDE（缺陷 19）。
- `frontend/docs/`、`backend/docs/` 下没人链接的文档，以及 132 行的 `frontend/AGENTS.md`，在默认 profile 下一个都没报（缺陷 20）。agent 只看到全部 ok，就会以为接入完成了。

#### 1. `init` 的替换规则

- **替换哪些**：只换入口、阶段卡、索引和计划这 5 个模板文件：`AGENTS.md`、`CLAUDE.md`、`CURRENT.md`，以及 docs 下的 `README.md`、`plan.md`。项目里已有同名文件时，先把它在**同一目录**改名（`.md` 换成 `.project.md`，如 `AGENTS.md` → `AGENTS.project.md`），再放入模板。
- **不替换记录**：docs 下的 `decisions.md`、`log.md` 是 K1 记录，决策的编号、状态、授权和落地点都要保留，不能改名后退役（A5）；`history/README.md` 在 history 目录里，改名会让它失去横幅豁免，退役时还会和别的归档撞名。这 3 个文件已有时保留原样，不放模板；格式与 GUIDE 不符时怎么办，见第十二节第 21 项。
- **`CLAUDE.md` 的特例**：原文去掉空白后正好是 `@AGENTS.md`，就保留，不生成 `CLAUDE.project.md`。
- **入口的约束力不能变弱**。`AGENTS.md` 会被 agent 自动加载，链接出去的文件只有被主动去读才生效。所以替换时，`init` 在新的 `AGENTS.md` 里写一段“接入过渡”，把本次产生的全部 `.project.md` 列为最先必读，包括 `CLAUDE.project.md`（只读 `AGENTS.md` 的产品也要看到它）。新的 `CLAUDE.md` 写成 `@AGENTS.md`；产生了 `CLAUDE.project.md` 时，再加一行 `@CLAUDE.project.md`。这段过渡同时让过渡文件从入口可达。
- **链接**：改名不改目录，所以相对路径的基准不变。但几个被替换的文件互相链接时（如 docs 下旧的 `README.md` 链到 `plan.md#task`），链接会落到新模板上，锚点也没了。所以 `init` 只改写过渡文件内部指向另一个被替换文件（包括指向自己、带锚点）的链接目标，改成对应的 `.project.md`；其他现行文档指向被替换路径的链接不动，列进 `onboard` 的建议，由 agent 判断该指新模板还是过渡文件。
- **嵌套的入口不动**：`frontend/AGENTS.md`、`frontend/CLAUDE.md` 这类按目录生效，只纳入预算和 `@` 导入检查（第 3 项）的范围。
- **先预检，有一处不行就整个拒绝、什么都不写**。用 `lstat` 逐项检查 `docaxioms/`、`docaxioms.json`、docs 目录、history 目录、全部模板目标和改名目标：
  - 任何符号链接，包括悬空的、以及父目录是符号链接的（常见的是 `CLAUDE.md` 链到 `AGENTS.md`）；
  - 父路径不是真实目录，或目标是目录；
  - 改名目标已经存在；
  - 只差大小写的同名文件（如 `agents.md`）：在不区分大小写的文件系统上，它和 `AGENTS.md` 是同一个文件，而 Git 和 picomatch 都区分大小写。

  拒绝时说明原因，由人或 agent 处理后再接入。已有 `docaxioms/` 目录时照旧拒绝；`init` 现在写死这个目录名，`check` 和 `update` 已经认 `core.dir`，`init` 也应能指定（第十节第零批）。
- **记一笔替换记录**：`init` 把本次改名的文件列表写进 profile 的一个独立顶层键（和 `core` 一样由 docaxioms 写，不手改）。不放在 `core` 下面：`update` 会整块重写 `core`，独立的键它原样保留。`onboard` 靠它区分“迁移留下的过渡文件”和项目自己恰好叫 `foo.project.md` 的文件，也靠它发现过渡文件被直接删掉。
- **之后到迁移完之前，`check` 仍可能失败**：过渡文件是现行文档，它们的内容会被路径、命令、决策号等检查扫到。这正是迁移要处理的东西；这段时间可以用 `check --report`。
- 这改变了 `init` 现在“项目自己的文件永不覆盖”的承诺（写在 `src/manage.mjs` 开头和 README）。内容一字不丢，只是换了文件名，但仍是契约变更：本仓库要新增一条决策，同步 README 和测试。

#### 2. 过渡文件的去向

每个过渡文件都是待退役的文档，agent 按 GUIDE 的“退役文档”流程和第四节第 7 条处理：
- 硬性约束（构建和验证命令、禁止事项）收回新的 `AGENTS.md`，作为底线。超出预算时**先精简**：细节放进专门的文档，入口只留链接。放宽预算要 owner 同意。
- 其余内容按 GUIDE 的“哪份文档负责什么”表分给各自的所有者：现状进描述文档，未完成的进计划。原文里像“决定”的内容，只有 owner 确实做过的才能进决策表（A0）；拿不准的列给 owner。
- 删掉 `AGENTS.md` 里的“接入过渡”段和 `CLAUDE.md` 里对它的导入，**不能改指到 history**：入口一旦链到 history，旧全文会在每次会话里照旧当成现行指令加载。
- 把它移进 `<history 目录>/onboarding/<过渡文件的相对路径>`，保留 `.project.md`，如 history 目录下的 `onboarding/docs/README.project.md`。不能还原成 `README.md`：history 下以 `/README.md` 结尾的文件，横幅检查和不可改写检查都会跳过。加上横幅；目标已存在时停下，不覆盖。移动后改写它自身的相对出链和相对 pin：移进 history 后，现有的链接和 pin 检查不再扫描它。

#### 3. 验收命令：`docaxioms onboard`

只读：不写文件，不保存状态，每次都从仓库重新计算，可以反复运行。退出 0 只表示**机械验收通过**；**接入完成**还要 owner 确认了放宽的差异，并抽查迁移后的内容（第 4 项）。输出分四部分，每条都附一句该怎么改：

- **未通过**（有一条就退出 1）：
  1. 日常 check 的 gate 发现，以及运行出错。
  2. 过渡文件：替换记录里的文件，还有不在 history 的；或者既不在原位、也不在 history 的归档位置（被直接删掉了）。
  3. 入口：根目录的 `AGENTS.md` 没有链到规范副本里的公理和 GUIDE；根目录有 `CLAUDE.md` 时，它没有导入 `AGENTS.md`；任一 `CLAUDE.md` 的 `@` 导入指向不存在的文件、history 或过渡文件；过渡文件全部退役后，任何现行文档还链到或导入过渡文件或 onboarding 归档，日志和 history 的 README 除外（追溯来源写在日志里）。不只限入口文件：`AGENTS.md` → 某份现行文档 → 归档，同样会把旧规则当成现行指令加载。这一项都是新的：现有的链接检查只核对目标存在和锚点，也不解析 `@` 导入。
  4. 覆盖缺口：文件清单里的 `.md`，既不在 `reachable` 范围内、也不能从入口走到，并且不属于下列任何一类：core 副本、history、ignore、profile 点名的角色文件（阶段卡、日志、决策、计划）、各级 `AGENTS.md` 和 `CLAUDE.md`。仓库元数据（如 `.github/` 下的模板、`CHANGELOG.md`）的默认归属见第十二节第 24 项。
  5. 预算：任何名为 `AGENTS.md` 或 `CLAUDE.md` 的文件（不区分大小写），不在任何一条实际生效的预算里（匹配了 `files`、又没被 `exempt` 排除）。
- **建议**（不影响退出码）：
  - 从仓库推出来的 profile 取值：`codeExtensions`（按扩展名计数）、`commands`（`package.json` 的 scripts、`Makefile` 等）、`pathPrefixes`、`history.base`（远端的默认分支）、`entries`。取代原第三批第 6 项的“init 只读探测”。哪些扩展名算代码，没有精确的判据（同后缀的数据文件、没有扩展名的脚本），所以只做建议，不做未通过（A7、M2）。
  - 文档里看起来像命令、却没有对应 `commands` 规则的行内代码。同样不精确，只给人看。
  - 其他现行文档里指向被替换路径的链接（第 1 项）。
- **已启用的项目配置**（不影响退出码）：相对模板新增、使检查更严的设置，如新增的 `codeExtensions`、`commands`、`pathPrefixes`。列出来让人知道检查管到了哪里。
- **待 owner 确认**（不影响退出码）：相对 docaxioms 当前钉住版本的模板 profile，**放宽**了的设置：删掉或调大预算和阶段卡上限、新增 ignore 和各类豁免、删掉命令规则、改了 `reachable`（正则看不出是放宽还是收紧，一律列出）。生成元数据（`core`、替换记录）不比较；替换记录另在输出开头固定打一行摘要（替换了哪几个文件、各自现在在哪），它被删掉或改短，只能靠这一行和 Git 差异审阅看出来。agent 最省事的过关办法就是放宽规则，所以单独列出；怎么记录 owner 已确认，见第十二节第 23 项。

完整的迁移步骤由 `docaxioms onboard --guide` 打印。指南要点名 `AGENTS.md`、`CLAUDE.md` 这些产品文件，不能进 core（AD-2）；也不复制进项目，否则它自己又成了一份要维护的现行文档。所以它随包发布，由命令输出。

**模板同步修改**（缺陷 20）：`templates/docaxioms.json` 的 `reachable` 改为 `(^|/)docs/`，预算的 `files` 改为 `**/AGENTS.md` 和 `**/CLAUDE.md`。否则接入完成以后，日常 check 照样漏掉子目录。

#### 4. 边界

- 机械验收通过只说明结构和配置符合预设，不说明迁移后的内容是对的（A6）。内容有没有被曲解、事实有没有丢，仍要 owner 抽查，或者接入后跑一次 garden。把过渡文件原样搬进一份新的现行文档再链上，在机械上与认真拆分无法区分。
- 没配闸门时，agent 也能直接改掉判据，比如改 profile、删掉替换记录。“待 owner 确认”、输出开头的替换记录摘要和 Git 差异审阅只能让这些被看见，挡不住（第三节第 5 条）。
- 新项目同样适用：`init` 之后 `onboard` 应当直接通过，只剩建议。第零批要有一条测试固定这一点。
- 覆盖缺口用的是文件清单。不是 Git 仓库的目录照旧退回文件扫描（`init` 不要求 Git）；已确认在 Git 仓库里、清单命令却失败时，才报错，不能当成“没有文件”（缺陷 17）；`onboard` 会运行项目检查，扩展返回空结果也不能当成通过（缺陷 18）。
- 接入以后的日常维护也由 agent 接手。check 抓不到的遗漏（没写日志、`CURRENT.md` 过时、该加的计划条目没加、没有 pin 的描述过时），在这种用法下影响更大，所以第六节第 2 条的按需技能、缩短必读链，优先级相应提高。

## 八、人类阅读与审查

**文档影响报告**：配了闸门时，闸门每次验收都生成一份，本地批准界面和远端 PR 评论共用；没配闸门时，由本地 check 生成，只是报告，没有签名。它还没有实现：现在的 `garden --json` 只是清单（pin 数量、映射路径、大小）。内容按顺序：
1. 规范变化：谁批准、影响范围；
2. 行为与描述变化：源码差异、决策变化、任务关闭对应哪些声明；依赖图给出直接失效、等待上游、多个上游的原因、同一根因折叠后的下游，以及没有登记依赖的范围（第四节第 4 条）；
3. pin 变化：只是行号平移，还是内容变了（内容变了要核对旁边的散文）；单列“刷新了摘要但正文一字没改”的条目；
4. 验证证据：针对哪棵树、哪个环境，哪些没跑；
5. 机器守不住的部分；
6. 本次批准绑定的是哪份差异。

**降噪**：
- 生成物默认折叠；
- 刷新 pin 时禁止顺手格式化整份文档；
- 一事一文件。

**三问清单**：人只回答机器回答不了的三件事。
1. K2 的变化是不是 owner 的意思？
2. 被点名的 K3 描述与这次 diff 的行为一致吗？
3. 有没有把历史混进现状、把别处的事实再抄一遍？

**批准记录可信**：
- 批准记录是 owner 硬件密钥的签名，绑定仓库、ref、B、C、策略摘要和用途；作者自己写的 `reviewed: true` 只算声明。
- 候选一变，批准即失效。
- Agent 拿不到批准密钥：验签端强制要求签名时物理触摸。但 Agent 仍可能替换批准界面，让 owner 签错候选，所以批准界面要受保护（第三节第 3 条）。
- 有远端时，平台审批是额外的一层。CODEOWNERS 的一条规则列了多个人时，其中任一人批准即算通过；“两类角色都批准”须由闸门另行检查。
- AD-6 的隐私边界保留：只记录授权来源和摘要。

**延续性**：
- 权限分给可接替的角色，不绑定个人；设备密钥的登记和撤销都是治理变更。
- 交接包由这几样组成：ownership、`CURRENT.md`、tasks/、最近的审计报告，以及闸门的设备登记和恢复说明（写在 operations 里）。即使没有 CLI，在网页上浏览仓库也能看全。
- 新人阅读路径的总量受预算约束。
- 写下“为什么”（A8）有外部证据支持（2608.11095，见第十三节）。

## 九、检查的自发性

### 1. 触发矩阵

| 时机 | 自动做什么 | 绕过面 |
|---|---|---|
| 开机 | 闸门服务和监听进程随系统启动 | 服务停止时无法推送或发布，但工作区照常可以编辑 |
| 接入、升级 | 接入：`init` 另存并替换已有的入口、阶段卡、索引和计划，`onboard` 列出没完成的迁移（第七节第 5 条）。升级：检查策略、适配器版本、生成物，提示需要重新信任的钩子 | 当前 `init` 只跳过已有文件，`update` 也不做这些 |
| Agent 启动、resume、压缩后 | 启动核对，注入简报 | 钩子没启用或没被信任；这时只能靠 AGENTS.md |
| 文件变化 | 监听进程让缓存失效，并做快速检查 | 事件丢失时重新扫描，不影响正式验收 |
| 写文件和 shell 工具调用前 | 拦截对受保护文件的修改 | shell 和持久终端；钩子超时放行。最后仍有闸门兜底 |
| 推送到闸门 | 正式验收（G22），签名，转发 | 只能通过第三节第 5 条列出的缺口绕过 |
| 发布 | 闸门签名，绑定身份 | 同上 |
| 定时（launchd、systemd timer、计划任务） | 统计受管契约面自上次审计以来的变更；按配置提醒，或登记审计义务 | 离线也能跑，没有托管平台“60 天不活动即停用”的问题 |
| 重启、唤醒、监听事件缺口 | 对账：转发队列、缓存、证据库 | — |

### 2. 审计的自发性，分两档

- **默认档**：受管契约面在上次审计之后有了实质变更，就提醒责任角色。有远端时，同时更新一条去重的漂移 issue。不阻断。
- **可选档（G21）**：审计登记为义务，过期时闸门拒绝签发发布许可，也可以配置为拒绝接收。
  - 到期按受管契约面的变更代次计量，不按日历算；“实质变更”要先定成精确谓词，满足 M2 之后才谈阻断；
  - 热修有一个受审计的豁免，按次数计，不按时间窗（A7）。
  - 首版只提醒。

“该审了”不等于“文档错了”。

### 3. 三类写入，只允许前两类自动发生

自动执行的前提是第四节第 3 条的五条判据；所有写入都在形成最终候选之前完成（第四节第 7 条）。

1. **确定性生成**：决策索引、产品入口和钩子、允许签名者名单、CODEOWNERS。由 G20 校验；内容没变不重写文件。
2. **显式触发的脚手架命令**：领任务、关任务、新增决策、退役、`pin --relocate`（包括同摘要的锚点改名后的重定位）。由人或 Agent 调用，按第四节第 7 条的写入协议，结果经闸门验收；没配闸门时，经普通的 check 和评审。机器人能自发提议的只有一种：内容摘要不变的 `pin --relocate`，并以待审补丁的形式提出。自动改链只用已授权、无歧义的迁移映射，不能自动选择新的规范依据。
3. **后台自发改写语义散文**：一律禁止（A0）。人发起复核后，agent 按依赖顺序逐段起草、每段停下等确认，属于受控的交互辅助，不在此列（第四节第 5 条）。

## 十、迭代路线

第一批修复合入、加入文档依赖图之后，三方一致的排序。每一项要落地，都要由 owner 决定，并按 AD-7 的节奏推进。

### 第零批：接入链

owner 在 2026-11-28 定下方向，排在第一批之前。它要把第一批里的几个最小合同一起提前：缺陷 17（Git 失败与空结果分开）、缺陷 18（扩展结果校验），以及第一批第 5 项里“退役时改写迁移文件自身的出链和 pin”这一部分。其余第一批内容照旧。

1. `init` 的替换规则（第七节第 5 条第 1 项），以及本仓库改 `init` 契约的那条决策；`init` 可以指定 core 目录；替换记录的键加进 `src/profile.mjs` 的 schema，并同步 GUIDE 的 profile 键表（用通用措辞，不点名文件，守 AD-2）。测试要覆盖：5 个文件撞名时都被改名，记录文件不动；过渡文件之间的链接被改写；预检里任何一项不过都整个拒绝，什么都不写；新项目 `init` 之后 `onboard` 直接通过，分别覆盖不是 Git 仓库的目录和还没有提交的 Git 仓库。
2. `templates/docaxioms.json` 的 `reachable` 和预算改为覆盖子目录（缺陷 20）。
3. `docaxioms onboard`：先做开头的替换记录摘要、“未通过”和“待 owner 确认”；“建议”和“已启用的项目配置”可以后补。
4. 接入指南，随包发布，由 `onboard --guide` 输出。
5. 缩短必读链：`templates/AGENTS.md` 改为按需读 GUIDE 的相应部分，但保留指向公理和 GUIDE 的链接（`onboard` 要求有）。第二批第 6 项相应收窄。
6. 在两三个真实的已有项目上让 agent 走一遍，记录：循环了几轮，哪些判据误报，agent 有没有靠放宽规则过关。可以顺带开始第二批第 7 项的外部实证。

### 第一批：补齐输入、引用和摘要的合同

依赖图和正式验收都以这些为前提。

1. 缺陷 8：研究与任务的真实链接关联；先定 minimal 和 full 两档的关联方向与任务身份。
2. 缺陷 12：锚点切片，连同锚点唯一、冲突处理、节点粒度和 pin 的所属段落（第四节第 2 条）。
3. 缺陷 17、11、18：Git 失败与空结果分开；零匹配给 note 和对象计数；扩展结果校验字段。一并做**结构化输出**：给 `--json` 的每条 finding 加稳定的 code 字段，能定位时再加 file/line；全局检查的结果没有单一行号；SARIF 等出现真实的集成需求再做。对象计数只能用来发现空跑，不能当作 AD-7 的分母（AD-7 要的是 10 次相关变更）。影响报告共用同一套结果结构。
4. 缺陷 7：换行契约，以及摘要规范化和版本（不暗改现有 pin）。
5. 退役的前置条件与迁移范围（第四节第 7 条），写入命令的协议。
6. 缺陷 14、16、6：整文件和锚点 pin 的预览；log glob 的范围；默认决策前缀改 `D-`，附迁移说明。决策退役的规则待 owner 决定（第十二节）。
7. 缺陷 15：低成本小修，不阻塞别的。

### 第二批：只读、可验证的小闭环

1. 用现有的文件和行段 pin 建少量依赖边。
2. 影响报告：直接失效、等待上游、没有登记的范围（第四节第 4 条第 2 项）；退役预览（第四节第 4 条第 4 项）。
3. 锚点合同补完后，加入按锚点钉段落。
4. 一个试点生成物：生成并校验，落实最小 G20。
5. **可选参数 `--require-base`**：缺比较基线时把 note 变成失败，默认行为不变。三方都认为它与 A6、A7 不冲突，但不能借它绕过 AD-7，也不能代替正式验收的显式 B 和 C。要写明它的边界：在主分支上 push 时 base 等于 HEAD，仍然没有可比较的内容。
6. **缩短必读阅读链的其余部分**：改模板的阅读指令已提前到第零批第 5 项。这里剩下：可选的按需 SKILL.md；拆 GUIDE 末尾约 2.5 KB 的 profile 字典往后排，收益要用真实会话做 A/B 实测。影响报告能减少一次任务要读的量，但解决不了入口加载的合同。
7. **AD-7 外部实证**：在另一个真实项目里以报告模式至少跑 10 次相关变更，拿到 3 条值得改文档的发现。这是所有门禁升格的前提，也是目前最缺的数据；同时记录依赖图提醒的有效发现和维护成本。

### 第三批：有了合同再扩写入和部署

1. 显式的退役、关闭任务命令，以及多生成物的通用生成命令，按第四节第 7 条的协议实现（预览、授权范围、输入绑定、失败恢复、最终候选）。
2. full 档结构（第七节）、目录式决策、适配器（第六节）、按需规程。**目录式决策**（参考 log4brains 的“日期-slug”单文件）可以减少并行时撞行，但独立文件仍可能撞 ID、争抢索引页和落地点，冲突频率目前没有数据。
3. 正式的提交快照、跨用户闸门、签名和平台验收，按第三节的路线推进。
4. 依赖图第二阶段的其余部分：agent 逐段起草、历史候选边、按需的处置记录（第四节第 5 条）。通用生成器见第 1 项。
5. 日志防删改：日志属于 K1 记录，受 A5 约束；并入 G13，覆盖 minimal 档的日志和决策表、full 档的记录集合，不另造独立机制。
6. 等需求或数据再做：
   - **源码里的命名区域 pin**（参考 mdBook 的 `ANCHOR:` / `ANCHOR_END:`）：Markdown 的命名段落已由第四节解决；源码里的命名区域等证明行段 `--relocate` 不够用再做。可选启用，区间内容一变照样失败。**不要默认剥除行尾空白**：codex 实跑出反例，Python 多行字符串里的行尾空白是数据。
   - **薄 GitHub Action**：降低非 JS 仓库的接入成本。先验证有人要，再评估单二进制。单二进制可以照抄 OpenSpec 和 markdown-magic 的 `bun build --compile` 流程；但 docaxioms 读资源依赖 `import.meta.url`，projectChecks 又是动态 import，打包后能否正常工作还没验证。
   - **demo 故障样本**：可以复用依赖图试点的样本。原来同一项里的“init 只读探测”已并入第零批的 `onboard` 建议。

### 不建议做

- **常驻 MCP Server**（A 的 P2、C 的候选 8）：本地 CLI 加上代理自带的 shell 已经够用，常驻工具描述会占用每次会话的上下文（OpenSpec #319 有讨论）。同为本地 CLI 的 OpenSpec 也没做；提供 MCP 的主要是没有本地文件系统的云端 SaaS。
- **照搬 DocGuard**：数十个与框架绑定的校验器、成熟度评分、`diagnose --auto` 自动改文档。会违背 A7（误报面变大）和 A0（迎合代码）。
- **任何由代码驱动、自动改写散文的闭环**（Mintlify Autopilot、Dosu Auto-Accept、Swimm Auto-sync 一类）：违背 A0。显式的机械迁移和确定性生成不在此列。
- **让门禁因为常报而自动降级**：违背 A6（第四节第 3 条）。
- **恢复已删除的 G10、G18**：不借“复核证据”重建逐声明的账本，也不借恢复状态重新引入会话写入锁。

## 十二、待 owner 决定的问题

第 1 至 12 项来自全流程方案，第 13 至 16 项来自文档依赖图，第 17 至 20 项来自调研校验，第 21 至 25 项来自接入链。

1. **闸门的保护对象。** 闸门只做跨用户一种，需要一次管理员安装；同一用户下的闸门仓库不做成产品档位，防手滑用客户端钩子。要定的是：只保护权威分支，还是同时保护发布制品？是否检查新引入的全部历史提交？建议首版只验收权威分支的最终 C，制品和逐提交另立合同。
2. **打包边界（AD-4）。** 主包保持纯 JS 的 npm CLI；闸门和平台辅助程序拆成独立、可选的配套包，特权安装由用户显式执行。AD-4 只规定了 CLI 形态和代码锚定方式，没有决定配套程序的形态，所以这需要一条新的决策。依赖图在 CLI 内扩展，不影响这一项。
3. **密钥。** 建议首版闸门用隔离的软件密钥，owner 批准默认用 FIDO2。没有硬件时能否退回到系统管理员口令？退回时它不等价于硬件批准，G12 要改为认策略允许的批准方式，并记录实际方式。哪些操作必须由人确认？依赖图的处置记录不等于硬件批准。
4. **远端的去留。** 可选的模式有：本地权威（可选镜像）、薄验签、复验，后两者可以叠加。建议首版用单一权威闸门加受限镜像。多台机器的设备密钥如何登记和撤销？
5. **平台优先级。** 建议首期先做 macOS，再做 Linux，Windows 放到第二期；WSL2 不能代替原生 Windows 的验收。
6. **full 档的结构。** 任务和研究一事一文件、状态由目录表达；决策一事一文件，加一份生成的索引。这要改 GUIDE 里关于决策表、log、plan、阶段卡的操作规则，不改公理。GUIDE 只写抽象的操作语义：不在 core 里出现工具和路径（AD-2），也不写门禁编号。一并要定的还有：
   - 一份 GUIDE 如何同时描述两档；
   - 依赖图的节点粒度、K1 记录里依赖的冻结方式，以及迁移合同；
   - 从 minimal 迁到 full 时，旧的决策表和 log 怎么办。建议在切换日冻结它们，旧内容不改写（A5）：旧 log 整体转为 history；旧决策表里仍然有效的决策不能进 history（history 下的文件必须带过期横幅，会误标现行规范），整表冻结为决策目录下的一份 legacy 文件，由 G13 锁住原文，保留原 ID，在新的决策索引里链接，照常参与授权和引用解析。冻结时在文件开头加一行说明：表内状态是切换日的快照，现行状态以决策索引为准；之后旧决策被替代，由新的决策记录表达，G11 按替代关系判定，不改旧表。
   - 首个生成物不必等这一项（见第 15 项）。
7. **条目 ID 的格式**，以及决策引用匹配规则怎么改写。当前的解析仍要求数字型的决策号。
8. **G16。** 是否新增；契约路径怎么登记；“无需改文档”由谁批准；哪些文档依赖边也纳入受管范围。建议首期先只报告，处置按接口或变更组登记，责任人确认即可；与依赖图的处置记录是同一套（第四节第 5 条第 6 项），不做两套确认。
9. **适配器。** 是否正式维护 `adapters/`，以及 Tier 1 的名单。
10. **冷启动必读。** 是否改为“公理、`CURRENT.md`、AGENTS 底线”，GUIDE 改为按需读取。
11. **G21。** 是否提供，默认阻断发布，还是同时阻断接收。建议首版只提醒，实证后再考虑只阻断发布。依赖图的变化统计只能辅助定义“实质变更”的谓词。
12. **本仓库自己是否改用 full 档和闸门。** 建议本仓库保持轻量，另选一个外部试验项目，同时完成 AD-7 的实证、full 档的验证、闸门的原型和依赖图的试点。无论选哪条路，新门禁都要按 AD-7 逐项升格。
13. **“锚点段落内容变了”首版是 gate 还是 aid。** codex 认为它与现有 pin 同构、谓词精确，应为 gate；agy 认为散文改个标点也会让摘要变，下游往往不必改，应先做 aid、量误报。Claude 倾向 agy。两边都同意：锚点不存在、不唯一、格式错误、成环是 gate；传递影响永远是 aid；本仓库是否阻断另由 AD-7 决定。选 aid 时，要写明它与现有 G09“摘要失配即 gate”的区别。

**外部证据怎么用、用到哪为止**（均已核对原文）：

- **上下文文件的成本**：
  - Gloaguen 等，arXiv 2602.11988，作者 5 人，当前为 v3：含冗余概览的上下文文件让步数增加 2.45 到 3.92，成本增加 19% 到 23%，差异显著；成功率没有显著变化。
  - Lulla 等，arXiv 2601.20404：精炼的 AGENTS.md 让中位耗时下降 28.64%，中位输出 token 下降 16.58%（p<0.05）。
  - 两篇合看：精简有效，冗余有成本。但测的都是一次性任务，不能直接换算成 docaxioms 的成本。
- **路径和指令过期**：
  - Ghimire 与 Damian，arXiv 2611.29916：代码移动后，39% 的陈旧路径长期没人修；而在未命中的路径里，只有 2.2% 是真错误。路径门禁有必要，豁免和降噪同样重要。
  - Mehtiyev 等，arXiv 2611.09802：只测了 3 条过期指令，其中 1 条有显著开销。只能从机制上说明价值。
- **文档漂移**：De Michele 与 Tantithamthavorn，arXiv 2610.27381：63.2% 的 AI PR 改了代码却没动文档。后续修复率高 8.6% 到 11.7%，这是相对增幅，绝对差只有 1.2 到 1.7 个百分点；论文只主张相关，不主张因果。
- **理由的价值**：Chakrabarti，arXiv 2608.11095：CLAUDE.md 会持续膨胀，增幅达 226%。给指令写上理由后，安全删减率从 6.0% 升到 17.1%，合规率高 6.6 个百分点（p=0.003）。支持 A8。
- **审查不能交给 LLM**：Yang、He 与 Zhou：超过 70% 的指令文件 PR 没有实质性的人工审查，AI 自动审查只召回了人类关注点的 1.3% 到 3.9%。
- **误报门槛**：Christakis 与 Bird（2016）：90% 的开发者只接受不超过 5% 的误报率。支撑 A7。

### 2. 对全流程方案上一轮总结的更正（各方都提出，已核实）
