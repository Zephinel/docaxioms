## 一、结论

- **全流程系统可行；“文档一定正确”不可行。**
  - 能硬保证的：配置被正确解释；每条必需规则都有明确的终态，零匹配、出错和降级都会显出来；证据对应被验收的那棵树和那个环境；记录没有被改写；必需的批准确实发生过；关闭不完整的任务会被拒绝。
  - 证明不了的：散文与行为语义一致；依赖登记齐全；owner 的原意被正确理解（A0、A6）。
- **“门槛不够硬”的主因不是门禁太少，而是三处漏水：**
  1. 门禁本身会静默失效或被绕过：缺陷 4、11、2、3、13，以及 Git 调用失败被当成空差异。
  2. 没有东西强制它运行。README 原话：nothing calls it for you。
  3. 被检查的候选可以在同一次变更里改掉检查本身，包括 profile、豁免和 workflow。
- **最终门槛可以留在本地，而且对个人仓库比免费的远端更硬。** 强制力来自权限和发布路径的封闭，跟机器在本地还是远端无关。具体做法是一个本地闸门程序：
  - 闸门运行在一个独立的系统用户下；
  - 推送由它的接收端钩子在不可变的提交上验收；
  - 能写受保护分支的凭据只有它持有，开发者用户下的凭据要降权；
  - owner 的批准用硬件密钥签名，由验签端强制要求物理触摸。

  远端可以完全不要，也可以只做薄验签（第二节）。
- **会话恢复的核心是“每次启动都从 Git 和任务页重新核对”，** 不是“退出时记得收尾”——中断恰恰发生在收尾之前。这个核对不依赖任何本地状态，也就不会把会话锁死。
- **主流 Agent 可以适配，但要按四种能力分别承诺**：发现入口、导入内容、阻断操作、恢复会话。适配和闸门程序全部放在 `core/` 之外（AD-2）。
- **AD-7 只约束本仓库自己的阻断面**（[决策](../docs/decisions.md)），不控制消费项目的 gate。
  - 新谓词在消费项目里按 M2 处理：谓词就是性质本身且精确的，直接做 gate；否则先做 aid，实测后再议。
  - 闸门让检查“无法被绕过”，但不改变“哪些检查该阻断”。这两件事要分开决定。

## 二、门槛加硬：本地终审

### 1. 三个问题都答清，才叫硬门禁

1. **谓词精确吗？** 例如“这个链接的目标，在被验收的树里存在”。
2. **检查真的执行了吗？** 有没有拼错的配置、零匹配、运行出错、降级。
3. **结果能被绕过吗？** 失败之后还能不能进入权威分支、能不能发布。

当前实现在第 2、3 问上都有缺口。只修第 1 问，等于给漏水的桶加盖子。

### 2. 本地各种机制能做到多硬

| 机制 | 守住 | 没守住（A6） |
|---|---|---|
| L0 文本：入口文件、GUIDE、技能 | 要求可达 | 读没读、懂没懂、守没守 |
| L1 Agent 钩子 | 在支持该事件的产品上尽早拦截 | 不支持钩子的工具；只拦编辑、放行 shell；钩子出错或超时时放行；用户关掉钩子 |
| L2 客户端 Git 钩子（pre-commit、pre-push） | 提前反馈，防手滑 | `--no-verify`；改钩子路径；用底层命令直接改引用 |
| 同一系统用户下的闸门仓库（bare 仓库加接收端钩子） | 接收端钩子不受 `--no-verify` 影响 | 同一个用户可以改钩子、改引用，或者绕过闸门直接推到托管平台。只防手滑，而防手滑用 L2 就够，所以不做成产品档位 |
| **L3 跨系统用户的闸门** | 开发者和 Agent 的进程改不了闸门的仓库、钩子、策略和检查器，读不到它的密钥，也拿不到推往托管平台的凭据 | root 或管理员；闸门服务本身被攻破；开发者用户下仍然留着的其他发布或管理凭据（见第 5 条） |
| **L4 签名与硬件批准** | 结果可以跨进程、跨机器验证；指定的硬件密钥，对指定的批准内容签名，并满足验签端强制的用户在场条件 | 签名不证明检查标准充分，也不证明签发者诚实；用户在场不证明 owner 看到的就是被签的内容，更不证明认真读过 |
| 文件监听守护进程 | 缓存失效、钩子快速判断、补充恢复简报 | 三个平台的内核事件都会合并或溢出丢失，也看不到命令和退出码。**不能作为证据，也不能作为写入锁的依据** |
| 沙箱、容器、虚拟机运行候选代码 | 候选代码接触不到宿主的凭据和签名接口 | 只读挂载不等于完整隔离；把全部源码设为只读会破坏编辑器和工具链，所以只用于检查运行器，不用于编辑 |

最低的可信组合是：**跨用户的接收端、不可变快照验收、受保护的策略和检查器、唯一的发布凭据。** 签名让结果能被别处消费，守护进程改善体验，但都代替不了这四项。

### 3. 推荐架构：本地闸门程序

**三个权限域，外加一个辅助组件**

| 组件 | 身份 | 权限与职责 |
|---|---|---|
| 开发者、Agent、客户端 | 普通用户 | 编辑工作区，做普通提交，请求验收。没有闸门文件的写权限、签名权限，也没有能写受保护分支或管理仓库的远端凭据 |
| 闸门服务 | 专用系统用户，禁止交互登录 | 拥有权威的 bare 仓库、证据库和转发队列；读取已批准的策略和检查器；决定接收、签发和转发。程序、运行时、依赖和治理配置都装在开发者无法替换的位置 |
| 检查运行器 | 与闸门不同的低权限身份，或者虚拟机 | 读取闸门导出的候选快照，写临时产物，断网运行。不能读密钥、不能改闸门的引用、不能调用签名接口 |
| 监听进程（可选） | 普通用户 | 维护缓存、给钩子提供快速判断、补充恢复简报。它的事件不构成任何通过凭据 |

**一次推送的数据流**

```text
工作区 → 普通提交 C → 本机受控入口（切换到闸门身份）
                         ↓
         pre-receive：确定基线 B、候选树 T、适用的策略 P
                         ↓
         从隔离区导出 T 的快照，交给运行器断网跑 check 与必需验证
                         ↓
         闸门核对结果、批准、输入身份；不通过则拒绝，引用不变
                         ↓
         仍在 pre-receive 里：把检查记录和签好的凭据写进证据库
         签不出来（密钥不可用）就拒绝，引用不变
                         ↓
         引用更新；post-receive 标记“已接收”，写 notes，唤醒转发队列
                         ↓
         可选：用独占凭据转发远端；离线则排队
```

**接收端契约**

1. **入口必须真正切换到闸门身份。** 不能直接推送到共享目录里的仓库路径：本地文件协议用的是推送者自己的身份。`safe.directory` 有显式例外，不能当权限边界。
   - 首版用 Git 远程助手，经本机 Unix 套接字连接闸门。套接字显式设权限，闸门在内核层核验对端的 UID（Linux 用 `SO_PEERCRED`，macOS 用 `getpeereid`）。这样不用打开 sshd。Node 的 `node:net` 没有暴露这两个接口，所以 macOS 和 Linux 上也需要一个很薄的原生桥接；在 macOS 上，它同时负责用 `launch_activate_socket` 领取 launchd 预先建好的套接字。不想要原生代码时，退一步：不用 launchd 的 `Sockets`，由常驻服务自己建套接字，放进一个由服务或管理员持有、授权组只能进入、不能写的目录，靠目录权限守住。这样只能核验组，核验不了具体用户。
   - 不用 `git daemon`：它启用 receive-pack 后没有任何身份认证，只监听本机也不等于认证了用户。
   - 本机 SSH forced command 只作备选。sshd 会经账号的登录 shell 执行命令，shell 设成 `nologin` 时它根本跑不起来；所以要换成受限 shell 或专用包装器，并禁用密码登录、转发、PTY 和用户 rc，严格解析原始命令。
2. **读取完整的 (old, new, ref)。** 默认拒绝未登记的引用、删除和非快进更新。首版一次只更新一个受保护引用。
3. **B 取自闸门保存的权威状态，T 取自新提交 C。** 不用开发者的 HEAD、工作树或可变的远程跟踪分支。同一仓库的事务串行处理；提交引用之前，再核对一次旧 OID、策略代次和批准绑定。
   - 首次接入时还没有 B：初始信任来自管理员安装时的显式引导，owner 批准初始策略和检查器，不由候选自己声明。
4. **直接读 Git 对象。** 闸门自己用 `ls-tree` 枚举路径、类型和 mode，用 `cat-file` 读原始 blob；不经过检出时的换行转换、过滤器和符号链接。关闭 replacement refs。
   - 隔离区里的新对象只对闸门身份可读。要交给运行器时，由闸门按 Git 对象逐个导出：遍历 `ls-tree -r -z`，按 NUL 解析路径、按 OID 请求 blob、按返回长度读取内容，用 `cat-file --batch` 写出普通文件，保留可执行位（`100644` 写成只读，`100755` 写成只读可执行），核对路径、mode 和 blob 摘要，放进运行器的只读输入目录。不用 `git archive`：它保留符号链接，还会按候选自带的 `.gitattributes` 删文件（`export-ignore`）、改内容（`export-subst`），候选加一行就能让失败的测试从快照里消失。符号链接、子模块等不支持的对象按策略拒绝，不能删掉之后仍声称验收了 T。
   - 子模块、LFS 和生成物的输入要有明确合同，取不到必需输入时返回 blocked。
5. **治理文件由旧策略识别。** 分两套范围：
   - 闸门自身的执行闭包：检查器及其导入的依赖、解释器和运行时版本、监督运行的程序。它们装在系统目录里，由文件权限保护，不随候选变化。
   - 候选仓库里的治理文件：`docaxioms.json` 和其中的策略、`docaxioms/`、允许签名者名单、`.github/workflows/` 整个目录（启用 Actions 验签时；同名 job 就能冒充必需检查），以及策略里显式登记的验证入口。业务依赖锁、普通的 npm 脚本不算，否则每次装包都要 owner 批准（A7）。
   - 没改治理文件：用基线策略验收。
   - 改了治理文件：旧策略判定“谁有权批准这次迁移”；批准通过后，用新策略和新检查器验收整棵 T。批准绑定 B、C、新策略摘要和检查器摘要，候选一变，批准即失效。
   - 不要求“只改治理文件”。升级检查器时，往往要在同一个提交里修掉新暴露的违规。
6. **候选代码不以闸门身份运行。** 被测的代码和测试来自 C；监督运行的程序来自已批准的版本。候选的 npm 脚本、插件和 projectChecks，只在无凭据的运行器里执行。闸门记录实际启动了什么命令、输入是什么、退出状态如何；客户端提交的“PASS JSON”一律不认。“命令退出码为零”只说明命令成功，不说明测试充分。
7. **必需规则只能有明确的终态**，见第 6 条。
8. **“检查通过”“本地已接收”“远端已送达”是三个不同的状态。**
   - 签名必须在引用更新之前完成：pre-receive 返回之后，失败就再也拦不住这次接收。pre-receive 里不能写 notes（新对象还在隔离区），但可以写仓库外的证据库。
   - 接收后由 post-receive 确认“已接收”，再写 notes、唤醒转发队列。post-receive 不是回滚点。
   - 崩溃恢复：重启时比对证据库和权威引用。签过名、引用却没更新的凭据，标记为孤立凭据，不生效；引用已更新、notes 还没写的，补写。
   - 本地接收和远端转发是两次事务。转发失败时保留“本地已接收、远端待送达”，不回滚本地。
9. **验收粒度：** 默认只承诺进入权威分支的最终 C 合规。要承诺“新引入的每个提交都合规”，就得逐个检查它们（A1、A6）。发布制品另立合同：提交验收不证明最终发布的字节经过了验收。
10. **资源和可用性**：pack 大小、对象数、运行器的时间和内存都要设上限，超限即拒绝；磁盘满、运行器卡死时返回 blocked，不当作通过。

**签名与证据**
- **格式**：一种采用 in-toto Statement 结构的自定义凭据，不自称兼容 in-toto Envelope（Envelope 要求签入 payloadType，并支持多签）。载荷是 JSON，只在签发前规范化一次，然后用 SSHSIG 做分离签名，namespace 固定（例如 `docaxioms-gate@v1`）。这样本机、别的机器和远端都只要 `ssh-keygen -Y verify` 一条命令，再加上第 3 条 owner 批准里的用户在场检查。
- **承载**：一条 note 存两段，逐字节写入和读取（写入时不能经过会清理空白的路径）。第一行是载荷的字节长度（十进制，以 `\n` 结尾），接着是恰好这么多字节的载荷，其余是 SSHSIG 的装甲块。验签端按长度切出载荷，原样送进标准输入，不解析后再规范化，消费的就是被签的那份字节：

  ```sh
  ssh-keygen -Y verify -f allowed_signers -I gate \
    -n docaxioms-gate@v1 -s payload.sig < payload
  ```

  `-f` 用的允许签名者名单取自基线 B 或受保护的远端配置，`-I` 的身份必须在名单里。
- **绑定内容**：
  - 对象：仓库 ID、目标 ref、B、C、T、哈希算法；
  - 策略：策略摘要、治理代次、必需规则集合（哪些阻断、哪些只报告）、批准记录摘要；
  - 执行：检查器制品摘要、扩展和依赖摘要、环境清单、各结果和日志的摘要；
  - 签发：签发身份、协议版本、请求 ID。
- **存放位置**：
  - 签好的凭据本体只有几 KB，写进 `refs/notes/docaxioms`，随 Git 同步。这样别的机器和远端验签不需要访问本机的证据库。
  - 触发了 G12 的提交，凭据里还要带上批准载荷原文和 owner 的硬件签名本体（约 1 KB），以及批准者的身份标识，远端才能独立检查用户在场标志和多成员批准。闸门自己的签名和批准摘要代替不了这份签名。验证用的公钥名单一律取自基线 B 或受保护的远端配置，绝不采信凭据或候选自带的公钥。
  - 闸门的证据库保存完整的检查记录和日志，凭据里只记它们的摘要；仓库之外另有备份。本机对账和补写以证据库为准；别的机器和远端只认验签通过、并且绑定的仓库、ref、C 和治理代次都对得上的凭据。
  - notes 可以被改、被删，普通 clone 也不会自动携带，所以消费方必须验签；找不到凭据，就判 blocked。
  - 普通用户的启动核对，经闸门的只读查询接口读取证据，不直接读闸门的目录。
  - 不用 commit trailer：它会改变 commit OID，形成自引用。
- **签名接口只接受两种请求**：“验收这个候选”，以及 Windows 上的连接认证（见平台做法）。不提供“签任意字节”，否则私钥即使不可导出，服务也会沦为任人调用的签名工具。连接认证的载荷由服务端构造成固定结构，客户端只提供限长的随机数，并用独立的 namespace（例如 `docaxioms-ipc@v1`），签出来的东西不可能被当成验收凭据。
- **环境清单只是闸门的声明**，不是硬件证明。没有测量启动或远程证明时，不能说“硬件证明了执行环境”。
- **防回滚**：只绑定 old 和 new 防不住引用回退后的重放。需要严格防重放时，额外维护一条签名的引用状态链（参考 gittuf 的 RSL）。但这条链本身也能被整体回退，首次接入的人只拿到旧链时发现不了截断；所以还需要可信的外部检查点，或者由消费方记录自己消费过的最新状态。判断先后用单调递增的代次或序号，不用本机时钟。

**owner 批准**
- **触发**：只由精确的路径谓词触发：治理文件、公理锁文件、决策记录、ownership、requirements，以及策略里显式登记的路径。新建任务页不触发。
- **流程**：
  1. 候选先推到闸门的待审引用（例如 `refs/for/<分支>`）。待审入口有自己的合同：只接收数据、跑预审、生成影响报告；不要求还没取得的批准，不签发 G22，不转发，不更新权威分支；允许覆写，过期自动清理。只看 T 的预审结果，在 T、策略摘要、检查器制品摘要、环境身份和外部输入都一致时才能复用；依赖 B→C 差异的规则，一律按正式验收时的基线重新判定。预审只用于需要批准或显式请求的情况，普通变更直接推送一次。
  2. owner 在批准界面里看差异、策略变化和影响报告，然后用 FIDO2 硬件密钥（OpenSSH 的 `ed25519-sk`）签名。
  3. 再推送更新权威分支，闸门核对批准和检查记录后接收。批准绑定的是最终的权威 ref，不是待审引用。
- **批准内容**：签名的载荷写明仓库、ref、B、C、策略摘要和批准用途；候选一变，批准即失效。批准界面一次只展示并签署一个明确指定的请求，不能批量签；待审引用的个数不设限。
- **批准界面要受保护**：从开发者不能改的路径启动（不经过用户的 PATH 和 shell 配置），并回显 C 的短哈希供 owner 比对。否则 Agent 可以让屏幕上显示良性的候选，送去签名的却是另一个。
- **验签端强制用户在场**：OpenSSH 的允许签名者名单没有控制触摸的选项；`ssh-keygen -Y verify` 只记录硬件签名的标志，不据此拒绝（9.9p2 和 10.6p2 的源码都是这样）。所以闸门和任何远端验签脚本，在验签通过后必须自己检查：拒绝用户在场标志为 0 的签名、缺少硬件签名信息的签名，以及普通软件密钥的签名。
- **它保证什么**：指定的硬件密钥，对指定的批准内容签了名，签名时有人触摸了密钥。它能把“终端里的 Agent”和“键盘前的 owner”分开，但不证明 owner 认真读过；单人仓库也不会因此多出第二位审查者。
- 没有硬件密钥时能否退回到系统管理员口令，留给 owner 决定（第八节第 3 项）。决定之前，G12 只认硬件签名。如果采用，G12 改为认策略允许的批准方式，并记录实际用了哪种方式和认证证据；口令不等价于硬件批准，不能静默降级。

**平台做法**（官方文档已核实；部署细节需要实测）

| 平台 | 服务与入口 | 闸门密钥 |
|---|---|---|
| macOS | 系统级 launchd 任务，用 `UserName` 指定专用账号；用 `Sockets` 创建本机 Unix 套接字，`getpeereid` 核验对端 | 首版是软件密钥，放在闸门用户的私有目录里。Secure Enclave 本方案选用 P-256，原型走 CryptoKit 直接创建和恢复密钥的路线（无登录的 daemon 用不了的是 Data Protection Keychain）；Apple 开发者技术支持说过 daemon 经 CryptoKit 使用它可以工作，但没有确认正式支持，而且默认的访问条件在首次登录之前可能失败。登录前、锁屏后、普通后台三种场景要分别原型验证 |
| Linux | system 级 systemd 服务，`User=` 指定专用账号（普通的 user service 不构成跨用户边界）；pathname Unix 套接字，显式设置权限，`SO_PEERCRED` 核验对端 | `LoadCredentialEncrypted=` 只保护静态凭据，启动后仍是明文；要让私钥一直留在硬件里，可以经 PKCS#11 或 TPM2-TSS 的 FAPI 使用 TPM 或硬件 token |
| Windows | SCM 服务加虚拟服务账号；Named pipe 不能用默认描述符（它向 Everyone 和匿名账户授予读权限；Node 的 `node:net` 用的就是默认描述符），需要一个原生辅助程序：显式 DACL、只给最小访问权（不要给客户端 `FILE_GENERIC_WRITE`，它包含创建管道实例的权限）、`PIPE_REJECT_REMOTE_CLIENTS` 拒绝远程客户端，并核验客户端身份。`FILE_FLAG_FIRST_PIPE_INSTANCE` 只在创建第一个管道实例时使用（后续实例带它会报 `ERROR_ACCESS_DENIED`）；它只能让闸门在名字已被占用时创建失败，防不住抢注：攻击者先占名时，客户端照样会连上假服务。所以闸门检测到占名就拒绝启动，客户端也要认证服务端：连接后客户端发一个随机数，闸门按上面的连接认证格式签名，客户端用系统只读目录里的闸门公钥核验，不依赖服务端 PID（有复用的竞态）。客户端同样需要原生辅助程序：普通的 Node 客户端会请求 `GENERIC_WRITE`，拿掉写权限后建不成所需的双向连接，可能退成只读；所以要以最小权限调用 `CreateFile`，并指定 `SECURITY_SQOS_PRESENT | SECURITY_IDENTIFICATION`，否则认证完成之前，假服务就可能模拟客户端的身份 | CNG 的平台加密提供者（TPM）；DPAPI 的本机作用域在这里不够用 |

密钥不可用时，正式验收返回 blocked，不能悄悄降级成另一把软件密钥。

### 4. 与远端的关系

三种模式不互斥，薄验签和复验可以叠加：

| 模式 | 适用范围与边界 |
|---|---|
| 本地权威（可选单向镜像） | 闸门仓库就是权威仓库，可以离线完成检查、批准和接收；接收后由闸门用独占凭据单向推到镜像。只有当远端没有其他写入者、bypass 或开发者用户下的写入、管理凭据时，才能说发布路径是封闭的。**首版推荐这一种** |
| 本地验收，远端薄验签 | 远端只验签：签发者已授权、策略代次对、对象绑定一致。不再重跑文档检查。远端必须只允许快进 |
| 本地验收，远端复验 | 需要独立环境或跨平台矩阵时使用（A1） |

**远端必须只允许快进。** 两台机器各自验过 C_A 和 C_B，远端把它们合并成 T_AB，这棵合并树没有经过任何检查。落后的一方必须在本地 rebase 或 merge，让闸门对最终组合出的树重新验收并签名，然后才能快进推上去。

**多机时要分清四样东西**：检查基线 B（本机闸门的权威状态）、远端目标引用的旧值、提交的验收凭据、本次发布的许可。离线接收或多机之后，B 可能不等于远端的旧值。首版只设一个权威发布者；发布时按远端旧值做条件更新（例如 `--force-with-lease=<ref>:<旧值>`），旧值不匹配就回到本地重新判断。这个参数本身允许非快进推送，所以闸门推送前先在本地确认远端旧值是 C 的祖先；远端有“只允许快进”的规则时，再多一道保险。

**GitHub.com 上的事实**（官方文档已核实）：
- 免费账号只有公开仓库能用 rulesets；个人私有仓库要 Pro 等付费套餐。
- 传统分支保护里“限制谁能推送”只对组织仓库开放。个人仓库要用 rulesets 的“限制更新”，并把部署密钥加进 bypass。
- bypass 里的 `DeployKey` 是一类角色（API 里 `actor_id` 为空），放行的是仓库所有的部署密钥，不能指定某一把。要做到只有闸门能推，仓库只能有这一把带写权限的部署密钥；GitHub App 能给出更明确的发布身份。
- bypass 会豁免整条 ruleset 里的全部规则。所以“限制更新（给闸门 bypass）”和“只允许快进、必需检查（不给任何 bypass）”要拆成两条 ruleset。
- 原生的“要求签名提交”只要求签名经过验证，不能指定只认闸门这个签名者，也不验证自定义的凭据。

**GitHub.com 上的薄验签**（需要原型验证）：
1. 本地闸门验收最终的 C，签发凭据，写进 notes；
2. 推到一个暂存分支，连同 notes，让 C 在远端可见；
3. 一个必需检查为这个精确的 C 验签（`ssh-keygen -Y verify` 核验 notes 里的凭据，再检查批准签名的用户在场标志），报告结果；
4. 闸门按旧值条件更新权威引用。

必需检查可以是无状态的 Actions 工作流，不用常驻服务；但必需检查只按检查名匹配，来源选 GitHub Actions 也分不出是哪个工作流，任何工作流里同名的 job 都能冒充。所以整个 `.github/workflows/` 都要列为治理文件（第 3 条）。别的写入者也能改工作流的多人仓库，要把检查来源固定到一个独立的 GitHub App；组织的 required workflow 能固定来源仓库，但它约束的是 PR 合并，不能直接用于本文的直推流程。网页上的 merge、squash、rebase 会产生新的 C′，要么回到本地重新验收，要么禁用这些合并方式。

### 5. 本地方案守不住的

| 缺口 | 本地的上限 | 能否补上 |
|---|---|---|
| 开发者用户下留着能写受保护分支或管理仓库的凭据（`gh` 登录态、经典 PAT、SSH 密钥、浏览器里的登录） | Agent 可以绕过闸门直接推送；有管理权限时，还能临时改掉远端规则、推完再改回来 | “远端只认闸门签名”补不上：管理凭据能改规则，免费的个人私有仓库也开不了规则。“Agent 沙箱的网络白名单”也补不上：拉依赖本来就要放行托管平台的域名，分不出拉包还是推送；沙箱外的进程、浏览器和其他工具也不受它约束。**唯一有效的补法是凭据降权**：开发者用户下只留只读凭据，或者受服务端规则约束、写不了受保护分支的写凭据（细粒度 PAT 只按仓库和权限授权，没有分支范围，不能靠 token 本身隔离分支）；受保护分支的推送权只交给闸门 |
| root 或管理员 | 能控制服务、配置和执行环境 | 签名若来自被控制的签发器，纯验签无法识别 |
| owner 自己 | 可以改信任根、规则和托管权限 | owner 同时控制远端时补不上（A0：owner 本来就是最终权威） |
| 密钥泄露，或签名服务被滥用 | 可以伪造获授权的声明 | 撤销之后可以拒绝；撤销之前，单靠验签区分不出来 |
| 直接在托管平台上修改 | 本地感知不到 | 受保护的验签规则能挡住普通写入者，管理员除外 |
| 批准界面被替换（所见非所签） | 屏幕上显示的候选和送去签名的不是同一个 | 受保护的启动路径加哈希回显能缓解，见第 3 条 |
| 工作区的 `origin` 被改指别处 | Agent 可以推到假入口，再声称“已过闸门”；权威分支没被污染，但会误导收尾判断 | 启动核对和收尾检查都核对 `origin` 指向受控入口，并向闸门查询凭据 |
| 本机时钟被回拨或漂移 | 影响密钥有效期和豁免时间窗 | 先后顺序改用代次或序号；确实需要时限的授权（例如密钥有效期）要用可信时间，没有可信时间就不设时限，改用显式撤销 |
| 整机快照回滚（Time Machine、磁盘快照） | 工作区、闸门仓库和证据库一起回到旧状态，已撤销的密钥或决策会复活，单机自己察觉不到 | 联网后与远端引用和外部检查点对账 |
| 本地证据被删除或回滚 | 签名能发现内容被伪造，但不能保证证据还在、列表完整 | 独立归档和外部检查点可以补强 |
| 未受管的出口：没登记的 ref、标签、发布 API、包仓库；制品被替换 | 闸门只守它登记的引用；提交验收不证明发布的字节 | 发布凭据同样只交给闸门；制品绑定另立合同 |
| 可用性：磁盘满、密钥丢失、测试卡死、恶意的大 pack、缓存污染、恢复失败 | 闸门不可用时就推不了，也发布不了 | 资源上限、恢复流程和备份写进 operations |
| 多台机器 | 每台机器有自己的设备密钥，由共同的授权根登记（允许签名者名单属于治理文件）。“任何登记过的机器签名都接受”，意味着最弱的那台机器也能决定结果 | 多人仓库可以要求治理变更有多个不同成员的签名 |
| 文档语义、测试是否充分、owner 原意 | 仍要靠人判断 | 补不上 |

离线时，可以用缓存的工具链、依赖、策略和公钥完成本地验收。但确认不了最新的远端基线、撤销状态或在线批准时，只能声明“本地通过、待同步”，恢复连接后重新核对。

### 6. 验收器契约

**结果状态**
- 结果分五种：
  - pass、fail；
  - blocked：应该检查，但无法完成；
  - not-applicable：适用条件算出来为假；
  - disabled：没有启用，并且要显示出来。
- 必需规则的 blocked 和 disabled，一律不算成功。
- 每条结果都带对象计数和适用原因：
  - 声明“必须存在”的目标匹配到零个：失败；
  - 本次确实没有对象：属于合法空集，照常通过，但要写出原因（A7）。
- 正式验收的 blocked 是新语义：现行 GUIDE 规定，检查无法按配置比较时只给出 note，不导致失败。消费项目要用正式验收，得作为一种新模式另行批准。

**输入绑定**：每次验收绑定仓库、B、T、策略摘要、检查器制品摘要和环境身份。同一棵源码树换了工具链或外部输入，旧证据不能沿用（A1、A2）。

**独立性**
- 由第 3 条的接收端契约保证：基线策略、治理迁移、运行器隔离、签名接口受限。
- 每条扩展结果的规则 ID、计数和终态都要核对；进程提前退出、返回非法 JSON，都不能算绿。
- **阻断和报告分开**：策略里只有获授权的阻断集合决定接收与否；只报告的规则照常运行，发现写进完整结果，不影响接收（本仓库就是这样，见 AD-7）。运行出错一律失败。
- 不能只凭 `--report` 或 CLI 的退出码认定通过；完整的机器结果可以作为证据。

**删除与改写**
- **原 G10（声明级证据账本）删除。** 即便做成可选，它的摩擦也很大，而且工具链一升级就会成片失效（A7）。需要锚定依赖时，用 G09 pin 住依赖锁、配置里的关键行。
- **原 G18（本地恢复凭据）删除**，理由见第三节。
- **G12 从“只认平台事件”改为本地硬件签名的批准**；有远端时，平台审批可以作为额外一层。
- **G17 不再是“没有平台 API 就 blocked”**，而是“缺少配置的可信运行器才 blocked”。证据仍然存放在被验收的树之外。任务的关闭记录只列出应该跑哪些验证的 ID，不写回验收结果。
- **G21 改为可选。**

**G16 的范围和处置合同**
- **范围**：只覆盖策略里显式登记的契约路径。机器不知道什么算“公开接口”，没登记的就报不出来，这个盲区要写明（A6）。
- **与 G09 的分工**：pin 住的切片照样要有处置。只靠 G09 的话，改了代码、刷新摘要就能通过，留不下任何处置。所以 G09 管摘要相等，G16 管登记路径上的每项变更都有处置，两者同时适用。
- **处置**：按接口或变更组登记，不逐文件填表。二选一：关联到已核对的文档段落；或者写明“无需改文档”及理由。
- **绑定**：处置写明责任人，并绑定差异摘要；差异一变，处置即失效。责任人确认即可，只有治理变更或策略明确规定的才要 owner 批准。
- **观察**：首期先做报告，观察它是否沦为例行填表，再决定是否阻断。
- **与 `codeToDocs` 的区别**：“代码改了文档没动”是启发式提醒，继续做 aid；“每项受管变更都有绑定差异的处置”是精确的流程门禁；“处置一定正确”，谁也保证不了。

**始终只能做 aid 或人工审计的**：散文与行为是否一致；某次改码是否必须改文档；演化措辞；理由是否充分；owner 的话是否被理解对了。LLM 可以提出带出处的 finding，但不能做阻断语义的门禁（A7、M2）。

### 8. 前置条件与源码改造

参考文档第三节第一批（缺陷 4、1、3、2、5、10）是地基。此外：

| 当前源码事实 | 必要改造 |
|---|---|
| `project()` 直接读磁盘和 Git 工作树列表；可达性检查直接调用 `lstatSync` | 统一的快照读取接口：列路径、读内容、查类型、算 B→C 差异。工作树模式用于开发，提交模式用于正式验收；正式模式不再回落到宿主磁盘 |
| Git 调用失败被转成 `undefined`，有的调用方把它当成无差异 | 区分成功的空集和命令失败；正式验收必须显式给出 B 和 C |
| profile 同时控制扫描范围、忽略项、扩展和基线 | 加 schema；把已批准的执行策略和候选内容分开传入，候选不能自行减少必需规则 |
| projectChecks 从工作目录动态导入；不完整的结果会被归一化成空 | 从已批准的版本加载，在运行器里执行，汇总器核对结果 |
| `--report` 让发现不影响退出码 | 保留它作开发用；新增正式验收入口，输出完整的机器结果（区分阻断与报告），交给闸门签发 |
| `init`、`update` 写模板和 core | 系统服务、密钥、权限的安装由独立的配套程序完成，`init` 不隐式修改系统配置 |

**还要先定下的契约**：换行（缺陷 7）和预算的计量单位，要早于 G06、G13、G20 确定。现在的计量方式是：先 `trimEnd()` 再按 `\n` 切分，空文件算 1 行；字符数按 UTF-16 的 `length` 计。正式验收以 Git blob 的原始内容为准。

**实施顺序**：修检查器的输入和错误合同 → 提交快照接口 → 单机跨用户闸门 → 签名证据 → 平台适配 → 远端薄验签。

每个阶段都要在目标平台上看到实际的拒绝，才算完成：

| 场景 | 必须观察到的结果 |
|---|---|
| 用 `--no-verify` 推送坏提交 | 被拒绝，引用不变 |
| 直接修改闸门的引用、钩子、策略、检查器依赖，或读取它的密钥 | 操作系统拒绝 |
| 候选删掉规则、伪造 PASS、扩展提前退出、Git 出错 | 不签发凭据 |
| 候选程序访问凭据或签名接口 | 被隔离拒绝 |
| 签名时密钥不可用 | 拒绝接收，引用不变 |
| 并发推送、批准后又改动、策略更新、用一次触摸签多个请求 | 旧的绑定不能沿用；批量签名被拒 |
| 批准时用了用户在场标志为 0 的签名、软件密钥的签名 | 闸门拒绝 |
| 候选的 `.gitattributes` 加 `export-ignore`、提交里含符号链接 | 快照与 T 一致，或者明确拒绝 |
| 接收前后崩溃、转发失败、重启 | 三个状态不混淆；孤立凭据不生效 |
| 超大 pack、运行器超时 | 拒绝或 blocked，不当作通过 |
| notes 缺失、仓库或 ref 不对、密钥已撤销、重放 | 消费方拒绝 |
| 锁屏、重启、无人登录、硬件缺失 | 不会悄悄降级成另一把密钥 |

上线前不能挂一个“全流程通过”的总标签。

## 三、会话重启与中断恢复

### 1. 恢复的是“可以安全接着干的公开状态”

| 状态 | 位置 | 类别 | 谁写、何时写 |
|---|---|---|---|
| 任务目标、范围、完成条件、开放步骤、待 owner 决定的问题、未验证项 | 任务页（每个任务一页，入库） | 分段标注 K4、K3，引用的规范是 K2 | 领任务、范围变化、遇到阻塞、暂停时写；可由命令代写，经验收 |
| 项目层面的焦点、优先顺序、冻结期、全局阻塞 | `CURRENT.md`（手写，入库） | 分段标注 K3、K4 | 这些事实变化时写 |
| 未提交的改动、分支、HEAD | 不落文档，随时从 Git 查 | 现场观测 | Git |
| 已签名的验收记录 | 闸门证据库 | K1（闸门监督运行并签名） | 闸门 |
| 当前任务指针；本会话跑过的命令 | 本地、可丢弃，不入库 | 本机运行态，不进 M1 的分类，任何文档都不能拿它当依据 | 领任务时写；有成对钩子的 Agent 自动写 |

### 2. 核心机制：每次启动都做无状态核对

新启动、原生 resume、压缩后重新接管、换 Agent、换人，都走同一条命令。会话开始钩子会调用它；没有钩子的 Agent，由 AGENTS.md 要求手动调用。步骤：

1. 从 Git 现算 HEAD、暂存区、工作树和相关未跟踪文件的清单：记录路径和内容摘要，而不是 `git status` 的文字输出。
2. 读 `CURRENT.md` 和当前任务页。
3. 配了闸门时，查闸门证据库：哪些提交已经验收过；当前这棵树和最近一次验收相比改了什么。没配闸门时跳过这一步，简报里写明“没有验收记录”。
4. 生成二十行左右的简报注入上下文：任务和下一步、差异摘要、待 owner 决定的问题、未验证项、项目焦点。

**判定中断的信号**：
- 工作树有改动，但任务页里没有暂停记录；
- 或者任务页写着“进行中”，却找不到对应的改动。

出现这两种情况时，简报的第一项就是“先对账：继续、回滚还是收尾”，由人或 Agent 决定。

**恢复只做观察和归因**，绝不自动 reset、覆盖脏工作树，也不无条件重跑命令。

### 3. 裁决与理由

- **不用“写前事件日志 + 恢复凭据拦截写入”。** shell、持久终端、Ctrl+C、钩子超时都会让日志不完整；用它拦截写入会造出假中断，进而锁死会话，逼人关掉钩子（A7）。
- **文件监听守护进程也不改变这个结论。** 三个平台的内核事件都会丢失，看不到命令，也看不到退出码。它只能做缓存，以及在发现事件缺口时让缓存失效、重新扫描。
- **闸门签名的验收记录可以当依据**（G17），因为它是闸门监督运行的，而且针对不可变的提交。Agent 自己的日志和文件事件只能补充信息。
- **任务状态的唯一所有者是任务页（M3）。**
  - `CURRENT.md` 只写项目层面的事实，不列任务。full 档为它提供新模板，分段标注 K3、K4。
  - 冻结期这类没有代码可以 pin 的事实，靠复核日期加 garden 防止过时（A2）。
- **任务页本身也可能陈旧。** 这一点由启动核对和 G19 兜底。

### 4. 关闭任务的顺序

关闭记录、把任务页移进 history，这些改动要和代码放在同一个候选里，再验收这个最终候选：配了闸门时由闸门正式验收，没配时对它跑普通验证。否则验收的 T₁ 和最终落地的 T₂ 不是同一棵树。

### 2. 适配器的组织

**位置**：`adapters/<产品>/`，与 `templates/` 并列，不进 `core/`。`package.json` 的 `files` 白名单要同步更新，并用打包测试验证。

**manifest**：每个产品一份，声明：
- 产品、形态和版本范围；
- 入口路径和导入方式；
- 技能的发现路径；
- 实际支持的事件，以及拒绝、出错、超时时的行为；
- 信任模型；
- 哪些能力查过文档，哪些在安装版上探测过；
- 已知缺口。

**四种能力分别探测**：发现入口、导入内容、阻断操作、恢复会话。模型回答“我读过了”不算证据。

**防止副本（A4）**，按优先级选择：
1. 原生读 `AGENTS.md`：不生成副本。
2. 能可靠导入：生成一行桥接。
3. 只能按路径或按需加载：生成规则文件，并写明加载条件。
4. 以上都不行：从同一来源生成限长内容。

生成的文件都登记在 profile 里，由 G20 校验；从链接、路径、命令、决策引用、演化措辞、pin 检查和 garden 中排除，也不落入可达性检查的范围。现在只有模板里的 `CLAUDE.md` 从 garden 中豁免了，其他检查照样会扫它。

**钩子只做转发**，转给 `docaxioms hook <事件>`：
- fail-closed，总是输出合法结果；
- 用 matcher 只挂在写文件和 shell 工具上；
- 先走快速路径：优先查监听进程的缓存，其次做零依赖的文件判断，与受保护文件无关就立即退出；
- 直接调用本地安装的 CLI，不经过 `npx`；
- 一个产品加载另一个产品的钩子时，按调用 ID 去重。

**钩子在本地终审下的定位**：钩子只负责提前提醒。即使所有钩子都被绕过，坏提交也进不了权威分支，因为最后一道是闸门。

**按需规程**：工作、审计、恢复三个技能，按各产品的发现路径生成，并受检。只有通过加载探测的产品，才把 GUIDE 改为按需读取。`AGENTS.md` 保留几条底线：验证命令、禁止事项、启动核对；配了闸门时再加“只能经闸门推送”。

**分级**：
- Tier 1，有契约测试：Claude Code、Codex CLI、Cursor、Copilot（只限本地 IDE 和 CLI 形态，云端 agent 连不上本机闸门）、Gemini CLI；
- Tier 2：只提供模板；
- 已归档的产品标为旧版。

**接入与升级**：`init` 遇到已有的入口文件时，给出冲突报告；`update` 迁移适配器，并提示需要重新信任的钩子。

**供应链**：克隆来的仓库自带的钩子也可能是恶意的。闸门只运行基线中已经受信任的扩展。

## 五、文档体系

### 1. 两档预设

- **minimal**：保留现有 9 个模板。必读链缩短，决策前缀改为 `D-`，本地运行态加入忽略规则。`CURRENT.md`、`plan.md`、`log.md` 照现行 GUIDE 手写。闸门可选。
- **full**：下表全部。`requirements.md`、`operations.md`、`ownership.md` 按需启用。

文档档位和闸门是两个独立的选择：minimal 也可以配闸门，full 也可以不配。下表中与闸门有关的内容（设备登记、允许签名者名单、只经闸门推送）只在配了闸门时适用。

单一仓库是默认场景；monorepo 下的嵌套作用域还没有设计。

### 2. full 档文档清单

原则：
- 高频、并行改动的事实（任务、研究、审计），一事一文件，状态由所在目录表达，不维护汇总表。
- 低频的决策，保留一份入库的薄索引。

固定文档（路径相对项目根）：

| 文档 | 类别 | 唯一负责 | 谁读、何时读 |
|---|---|---|---|
| README.md | K3 | 项目是什么、怎么用、支持范围 | 人首次接触时 |
| AGENTS.md | K2 路由 | 必读顺序、验证命令、禁止事项、启动核对；配了闸门时加上只经闸门推送 | Agent 每次启动，≤100 行 |
| CURRENT.md | 分段标注 K3、K4 | 项目层面的焦点、优先顺序、冻结期、全局阻塞 | 每次接手，≤45 行 |
| docs 下的 README.md | K3 | 现行文档和各条目目录的总索引 | 找文档时 |
| docs 下的 requirements.md | K2 | 已接受的行为要求及验收 ID | 需求、实现、审查时 |
| docs 下的 architecture.md（超预算时拆到 design/） | 分段标注 K2、K3 | 结构、边界、不变量、接口，带 code pin | 改相关模块之前 |
| docs 下的 limits.md | K3 | 已知限制、不支持的场景 | 设计、使用、验收时 |
| docs 下的 operations.md | 分段标注 K2、K3 | 构建、验证、发布、回滚；协作流程；闸门的安装、恢复和设备登记 | 发布、接入时 |
| docs 下的 ownership.md | K2 | 角色、授权身份、批准规则、接替规则；允许签名者名单由它生成 | 批准、交接、权限变更时 |
| docs 下的 decisions/README.md | 生成的索引 | 每条决策的 ID、标题、当前状态 | 追溯理由、核对规范时 |
| docs 下的 history/README.md | 路由 | 历史入口和阅读边界 | 追溯时 |
| docaxioms/ 下三份 core 文件 | K2 | 公理、指南、审计协议 | 接入时；其余按需 |

项目侧固定 11 份（其中决策索引是生成的），core 副本 3 份，另有 core 许可证。

项目自己的生命周期差异（批准角色、合法转换、关闭条件）：机器可读的部分放在 profile，说明放在 operations 和 ownership。GUIDE 只写一份通用流程。

**条目目录**（都在 docs 下，每条一个文件）

条目 ID 带类型前缀和日期，例如 `D-20261126-cache-ttl`、`T-20261126-pin-crlf`。前缀必须保留，原因是现在的决策引用检查靠“前缀加数字”来识别引用。这条匹配规则要相应改写，并且同时识别 legacy 文件里登记的旧 ID。

| 目录 | 类别 | 规则 |
|---|---|---|
| decisions/ | 授权记录是 K1，规范效力是 K2 | 写完就永不再改。推翻、部分推翻或撤回时，新增一条记录，写明替代谁、作用范围多大，它是替代关系的唯一权威（M3）。索引里的当前状态由生成器算出，经 G20 校验。改公理的决策，按锁文件和 AD-6 的规定引用 owner 原话。未发布的决策能否删除，交给 owner 决定 |
| tasks/ | K4 | 在这个目录里，就代表任务是开放的。关闭时写入关闭记录，再移到 history/tasks/；完成日志就是 history/tasks/ 本身 |
| research/ | K4 | 必须有真实链接指向开放任务 |
| reviews/ | K1 | 带日期的 garden 审计报告及其处置 |
| history/ | K1 | 退役文档、关闭的任务和研究 |

**引擎改动**
- **可达性**：目录链接现在的行为不一致：可达性检查把它展开成目录下的 README.md，链接检查只要目录存在就放行，落地点检查则直接跳过（缺陷 9）。改为：只有登记过、受 schema 校验的条目目录，才算“链接目录即视为目录下的文件可达”，而且每个文件都要通过条目结构校验。决策目录另外接纳生成的 README.md 和登记过的 legacy 文件，两者都不当作单条决策校验；整个决策目录不算描述文档。
- **单文件假设**：决策表解析、描述文档集合、落地检查、garden 等多处假设“一类东西就一个文件”，需要同时兼容两种模式。

**M1 按段标注**：同一份文档里同时有 K2 契约和 K3 现状时，分段标出。garden 只审 K3 段，不能拿代码现状去覆盖 K2。

## 六、人类阅读与审查

**文档影响报告**：配了闸门时，闸门每次验收都生成一份，本地批准界面和远端 PR 评论共用；没配闸门时，由本地 check 生成，只是报告，没有签名。内容按顺序：
1. 规范变化：谁批准、影响范围；
2. 行为与描述变化：源码差异对应哪些声明；
3. pin 变化：只是行号平移，还是内容变了（内容变了要核对旁边的散文）；
4. 验证证据：针对哪棵树、哪个环境，哪些没跑；
5. 机器守不住的部分；
6. 本次批准绑定的是哪份差异。

**降噪**：
- 生成物默认折叠；
- 刷新 pin 时禁止顺手格式化整份文档；
- 一事一文件。

**三问清单**：人只回答机器回答不了的三件事。
1. K2 的变化是不是 owner 的意思？
2. 被点名的 K3 描述与这次 diff 的行为一致吗？
3. 有没有把历史混进现状、把别处的事实再抄一遍？

**批准记录可信**：
- 批准记录是 owner 硬件密钥的签名，绑定仓库、ref、B、C、策略摘要和用途；作者自己写的 `reviewed: true` 只算声明。
- 候选一变，批准即失效。
- Agent 拿不到批准密钥：验签端强制要求签名时物理触摸。但 Agent 仍可能替换批准界面，让 owner 签错候选，所以批准界面要受保护（第二节第 3 条）。
- 有远端时，平台审批是额外的一层。CODEOWNERS 的一条规则列了多个人时，其中任一人批准即算通过；“两类角色都批准”须由闸门另行检查。
- AD-6 的隐私边界保留：只记录授权来源和摘要。

**延续性**：
- 权限分给可接替的角色，不绑定个人；设备密钥的登记和撤销都是治理变更。
- 交接包由这几样组成：ownership、`CURRENT.md`、tasks/、最近的审计报告，以及闸门的设备登记和恢复说明（写在 operations 里）。即使没有 CLI，在网页上浏览仓库也能看全。
- 新人阅读路径的总量受预算约束。
- 写下“为什么”（A8）有外部证据支持（2608.11095，见参考文档第四节）。

## 七、检查的自发性

### 1. 触发矩阵

| 时机 | 自动做什么 | 绕过面 |
|---|---|---|
| 开机 | 闸门服务和监听进程随系统启动 | 服务停止时无法推送或发布，但工作区照常可以编辑 |
| 接入、升级 | 检查入口冲突、策略、适配器版本、生成物；提示需要重新信任的钩子 | 当前 init 和 update 都不做这些 |
| Agent 启动、resume、压缩后 | 启动核对，注入简报 | 钩子没启用或没被信任；这时只能靠 AGENTS.md |
| 文件变化 | 监听进程让缓存失效，并做快速检查 | 事件丢失时重新扫描，不影响正式验收 |
| 写文件和 shell 工具调用前 | 拦截对受保护文件的修改 | shell 和持久终端；钩子超时放行。最后仍有闸门兜底 |
| 推送到闸门 | 正式验收（G22），签名，转发 | 只能通过第二节第 5 条列出的缺口绕过 |
| 发布 | 闸门签名，绑定身份 | 同上 |
| 定时（launchd、systemd timer、计划任务） | 统计受管契约面自上次审计以来的变更；按配置提醒，或登记审计义务 | 离线也能跑，没有托管平台“60 天不活动即停用”的问题 |
| 重启、唤醒、监听事件缺口 | 对账：转发队列、缓存、证据库 | — |

### 2. 审计的自发性，分两档

- **默认档**：受管契约面在上次审计之后有了实质变更，就提醒责任角色。有远端时，同时更新一条去重的漂移 issue。不阻断。
- **可选档（G21）**：审计登记为义务，过期时闸门拒绝签发发布许可，也可以配置为拒绝接收。
  - 到期按受管契约面的变更代次计量，不按日历算；“实质变更”要先定成精确谓词，满足 M2 之后才谈阻断；
  - 热修有一个受审计的豁免，按次数计，不按时间窗（A7）。
  - 首版只提醒。

“该审了”不等于“文档错了”。

### 3. 三类写入，只允许前两类自动发生

1. **确定性生成**：决策索引、产品入口和钩子、允许签名者名单、CODEOWNERS。由 G20 校验。
2. **显式触发的脚手架命令**：领任务、关任务、新增决策、`pin --relocate`。由人或 Agent 调用，结果经闸门验收；没配闸门时，经普通的 check 和评审。机器人能自发提议的只有一种：内容摘要不变的 `pin --relocate`，并以待审补丁的形式提出。
3. **后台自发改写语义散文**：一律禁止（A0）。

**待 owner 决定**

参考文档第五节已有的五项照旧：换行、被 gitignore 的目标、决策退役、非 Markdown 落地点、是否拆 GUIDE。新增的有：

1. **闸门的保护对象。** 闸门只做跨用户一种，需要一次管理员安装；同一用户下的闸门仓库不做成产品档位，防手滑用客户端钩子。要定的是：只保护权威分支，还是同时保护发布制品？是否检查新引入的全部历史提交？建议首版只验收权威分支的最终 C，制品和逐提交另立合同。
2. **打包边界（AD-4）。** 主包保持纯 JS 的 npm CLI；闸门和平台辅助程序拆成独立、可选的配套包，特权安装由用户显式执行。AD-4 只规定了 CLI 形态和代码锚定方式，没有决定配套程序的形态，所以这需要一条新的决策。
3. **密钥。** 建议首版闸门用隔离的软件密钥，owner 批准默认用 FIDO2。没有硬件时能否退回到系统管理员口令？退回时它不等价于硬件批准，G12 要改为认策略允许的批准方式，并记录实际方式。哪些操作必须由人确认？
4. **远端的去留。** 可选的模式有：本地权威（可选镜像）、薄验签、复验，后两者可以叠加。建议首版用单一权威闸门加受限镜像。多台机器的设备密钥如何登记和撤销？
5. **平台优先级。** 建议首期先做 macOS，再做 Linux，Windows 放到第二期；WSL2 不能代替原生 Windows 的验收。
6. **full 档的结构。** 任务和研究一事一文件、状态由目录表达；决策一事一文件，加一份生成的索引。这要改 GUIDE 里关于决策表、log、plan、阶段卡的操作规则，不改公理。GUIDE 只写抽象的操作语义：不在 core 里出现工具和路径（AD-2），也不写门禁编号。一并要定的还有：
   - 一份 GUIDE 如何同时描述两档；
   - 从 minimal 迁到 full 时，旧的决策表和 log 怎么办。建议在切换日冻结它们，旧内容不改写（A5）：旧 log 整体转为 history；旧决策表里仍然有效的决策不能进 history（history 下的文件必须带过期横幅，会误标现行规范），整表冻结为决策目录下的一份 legacy 文件，由 G13 锁住原文，保留原 ID，在新的决策索引里链接，照常参与授权和引用解析。冻结时在文件开头加一行说明：表内状态是切换日的快照，现行状态以决策索引为准；之后旧决策被替代，由新的决策记录表达，G11 按替代关系判定，不改旧表。
7. **条目 ID 的格式**，以及决策引用匹配规则怎么改写。
8. **G16。** 是否新增；契约路径怎么登记；“无需改文档”由谁批准。建议首期先只报告，处置按接口或变更组登记，责任人确认即可。
9. **适配器。** 是否正式维护 `adapters/`，以及 Tier 1 的名单。
10. **冷启动必读。** 是否改为“公理、`CURRENT.md`、AGENTS 底线”，GUIDE 改为按需读取。
11. **G21。** 是否提供，默认阻断发布，还是同时阻断接收。建议首版只提醒，实证后再考虑只阻断发布。
12. **本仓库自己是否改用 full 档和闸门。** 建议本仓库保持轻量，另选一个外部试验项目，同时完成 AD-7 的实证、full 档的验证和闸门的原型。无论选哪条路，新门禁都要按 AD-7 逐项升格。

## 九、对上一轮总结的更正（各方都提出，已核实）

- **AD-7 管的是本仓库，不管消费项目。** 上一轮把预发布状态、具体缺陷和 AD-7 三件事混为一谈；“外部实证为零”应改为“未见合格的升格登记”。
- **上一轮写的阅读顺序是本仓库的，不是模板的。** 模板的顺序是：公理、GUIDE、`CURRENT.md`，然后是从 docs 下 README.md 链接出去的、与任务相关的文档。
- **收尾四件套恰恰是中断时最可能没做的事**，不能当作恢复协议。
- **garden 只生成清单，不做语义审计。** `pin --write` 只是刷新哈希，不能当作“已核对”的证据。
- **静默失效的来源，上一轮漏列了几项**：Git 失败与空差异混同、扩展结果缺字段、候选自己修改检查和策略、工作树与提交不是同一个对象。
