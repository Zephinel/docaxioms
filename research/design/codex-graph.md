1. **技术可行，但应承诺“找到影响、安排复核”，不能承诺“自动保持全文正确”。**

   自动查找可以覆盖已声明依赖的直接和间接影响；未登记的依赖、外部条件变化仍会漏掉。自动更新适合有明确输入和规则的生成内容、机械迁移；散文可由 agent 起草，正确性仍须对照权威来源复核。

   “只更新一份基础文档”可以是操作入口，但任务完成、行为变化、owner 决策是不同事实，不能强行归入同一个源。K1 历史记录不能随现状重写，K2 规范不能由代码变化自动改写，这由 A0、A5、M1 约束。

2. **边应以显式依赖为准，链接和映射用于补充候选。**

   | 来源 | 精度与边界 | 维护成本 |
   |---|---|---|
   | 显式文档 pin | 精确检测所选内容是否变化；不证明依赖完整或语义相关 | 需要选段、维护定位、复核刷新 |
   | 普通链接 | 精确表示引用和可达；推断内容依赖容易误报 | 声明成本低，筛选成本高 |
   | 现有 code pin | 能确定具体切片影响哪些文档位置；不能补全未声明依赖 | 细粒度准确，但行号漂移需要维护 |
   | `codeToDocs` | 适合粗粒度召回；文档随便改一处也会消除提醒 | 配置简单，大 glob 容易过宽 |

   一个关键源码事实：现有 pin **没有限制目标必须是代码**，已经支持 Markdown 文件及其行段；讨论稿的 `#cache` 标题选择器则尚不支持。我用内存调用确认了这个区别。参见 [pins.mjs](src/pins.mjs:24)。

3. **合并的是依赖数据和报告入口，各机制仍守各自的谓词。**

   从现有 pin、映射、链接和决策落点派生一个带边类型的索引，无需再手写一份图清单。reachability 继续检查阅读路径；pin 检查内容摘要；`codeToDocs` 提供弱关联提醒；决策落点保持授权追溯关系，不能一概当成自动改写依赖。

   G16 管“每项受管变更是否有绑定差异的处置”，G20 管“生成结果是否等于重新计算的输出”。它们与 pin 互补：**刷新摘要不等于完成复核**，现有 `syncPins()` 并不验证复核是否发生。[源码](src/pins.mjs:324)、[方案](research/全流程文档系统方案.md:262)

   G16/G20 目前是提案；新增传播报告先做 aid，也不能顺势扩大 AD-7 规定的本仓库阻断面。

4. **主要风险是传播过宽，以及把“没有检测到变化”误当成“仍然有效”。**

   - **粒度：**整文件 pin 容易受无关修改影响；过细切片又可能漏掉上下文。先选能独立表达契约的小节或行段，缺失、歧义、移动分别报告。
   - **提前截断：**对于 `A → B → C`，须先完成 B 的复核，并确认 C 所依赖的 B 输出未变，才能停止。B 尚待复核、或者 C 也依赖 A 时，不能截断。
   - **元数据级联：**现有哈希包含 pin 注释，单纯刷新 B 的 pin 也可能使 C 失效；内存调用已确认。若以后实现截断，应分开计算正文输出与复核元数据，依赖边的增删另行触发复核。[哈希实现](src/pins.mjs:77)
   - **环与漂移：**导航链接成环很正常；严格生成子图应拒绝环，人工复核环可以成组报告。移动、删除、漏登记的边，以及 Git 比较失败，都必须显式呈现；定期 garden 补查机器无法发现的遗漏。

5. **可确认、值得借鉴的先例有三类。**

   - **Bazel Skyframe：**记录依赖，沿反向传递闭包失效；重算后的节点值不变，可以撤销后续失效。可借鉴其传播与截断条件，但散文复核并不是确定性构建函数。[官方说明](https://bazel.build/reference/skyframe)
   - **DITA：**`conref` 复用内容片段，`keyref/conkeyref` 通过逻辑键间接寻址。可借鉴“一处维护、多处引用”和定位解耦；它解决内容复用，不证明摘要语义正确。[内容引用](https://docs.oasis-open.org/dita/dita/v1.3/os/part1-base/archSpec/base/conref.html)、[逻辑键](https://docs.oasis-open.org/dita/dita/v1.3/os/part1-base/archSpec/base/key-based-addressing.html)
   - **Sphinx：**显式标签支持跨文件引用和标题变更；`note_dependency()` 则明确登记“文件变化时重建文档”的关系。可借鉴其引用与重建依赖的区分。[交叉引用](https://www.sphinx-doc.org/en/master/usage/referencing.html)、[依赖 API](https://www.sphinx-doc.org/en/master/extdev/envapi.html)

6. **总体同意 Claude 的方向，但会收紧 DAG、截断和复核确认三个说法。**

   同意依赖不同于链接、减少转述优先于扩大传播、确定性生成优先、新提醒先测信号。不同意整个文档图必须是 DAG；只有需要拓扑执行的派生关系才需要这个约束。也不能把“文案没改”直接当作安全截断，更不能把 `pin --write` 当成复核证据。

   第一版我会这样做：

   - 选少量 K3 描述，用现有 Markdown 文件／行段 pin 试点，暂不新增标题语法。
   - 复用 `inspectPins()` 建反向索引，在现有 check/garden 报告中区分“直接失效”和“间接影响候选”，附触发位置、原因和传播路径。
   - 保留显式刷新流程；先不做后台散文改写或语义截断。确有生成需求时，先接一个确定性生成物，用 G20 式重算比较验证。
   - 用切片变化、无关修改、定位移动、多上游和环等样例检验报告，再记录有效提醒比例与复核成本，决定是否扩展。
