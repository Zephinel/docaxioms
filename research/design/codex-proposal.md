本文区分三类结论：

- **已核实事实**：直接来自当前源码、只读运行或官方资料。
- **设计方案**：建议新增的机制，不代表当前已经实现。
- **保证边界**：检查能够证明什么，以及证明不到什么。

总体判断：**构建全流程系统可行；把文档正确性全部变成自动硬门禁不可行。** 可以强制保证配置有效、检查没有空跑、证据对应当前输入、记录没有被偷偷改写、必需审查确实发生、未恢复的任务不能通过验收；不能仅凭这些机制证明自然语言描述完整、正确，或模型真正理解并遵守了它。

最关键的改造不是增加更多提示词，而是建立四个相互独立的边界：

1. **文档边界**：区分规范、描述、计划和记录，每个事实只有一个维护位置。
2. **执行边界**：检查读取明确、不可变的输入，失败、跳过和无法检查不混同。
3. **恢复边界**：每次启动重新核对任务状态、实际改动和证据，不能只信上次总结。
4. **验收边界**：受保护的合入、发布流程只接受可信执行器针对当前版本生成的结果。

## A. 门槛加硬：精确谓词与执行强度

### A1. “硬”的可行上限

应当区分三个问题：

- **谓词是否精确**：例如“某链接目标存在”。
- **检查是否真的执行**：有没有配置遗漏、空跑、错误或降级。
- **检查结果是否能被绕过**：失败后还能否合入、发布或继续受控操作。

只有三个问题都回答清楚，才能称为某个边界上的硬门禁。

| 层级 | 能保证什么 | 没守住什么 |
|---|---|---|
| 入口文件、规则、技能 | 提供可达的要求与操作方法 | 不保证读取、理解、遵守 |
| 手动 CLI、项目 verify 命令 | 在被调用时检查给定输入 | 不保证调用，也不保证随后提交的是同一输入 |
| 本地 Git hook | 在支持的 Git 操作中自动调用 | 可禁用、跳过；其他客户端和远端写入不一定经过它 |
| Agent 生命周期 hook | 在该产品、版本实际发出的事件上执行逻辑，部分事件可拒绝操作 | 不一定覆盖 shell、持久终端、子进程、其他宿主和故障路径 |
| 受控工作区与独立执行代理 | 对经过该代理的操作强制恢复、记账、校验与拒绝 | 需要操作系统权限隔离；同权限外部进程仍可能绕过 |
| 受保护的远端验收 | 对指定分支或发布目标强制要求可信检查和审批 | 管理员改规则、显式 bypass、凭据失陷仍属于信任根 |
| 签名与外部审查记录 | 证明指定身份对指定内容作过指定声明 | 不证明声明正确，也不证明身份背后的判断充分 |

GitHub 官方明确区分 required checks、预期结果来源、过期审批失效和管理员绕过；required check 还可能接受 `skipped`、`neutral`。因此不能只配置一个同名绿色 job，必须由汇总器验证完整结果。[分支保护](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-protected-branches/about-protected-branches)、[规则集](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-rulesets/available-rules-for-rulesets)。

**建议的目标强度**：

- 合入与发布：远端强制验收。
- 本地工作：自动接入检查和恢复，尽早发现问题。
- 若要求“没有恢复就连写入都不能开始”：提供受控工作区模式；不能用普通 hook 宣称已经达到。

### A2. 所有门禁共享的输入模型

以下均为设计。

定义：

- `B`：由验收服务确定的比较基线提交。
- `T`：本次被验收的不可变候选树；合并队列中为实际组合后的候选。
- `P`：已获授权的策略版本。
- `U(T,P)`：策略规定的文档、源码、配置、记录与依赖对象集合。
- `Δ(B,T)`：包含新增、修改、删除、重命名的完整差异。
- `E`：执行环境身份，包括运行器、依赖锁、工具版本和已声明的外部输入。
- `R`：结构化检查及审查结果。
- `F(I)`：对输入清单 `I` 的稳定摘要；清单包含路径、对象类型、内容摘要、选择器及其实际匹配集合。

最终验收绑定：

```text
(repository, B, T, policyDigest, evaluatorDigest, environmentDigest)
```

不得只绑定分支名、任务名或一段手写的 commit 字符串。

结果状态至少区分：

```text
pass / fail / blocked / not-applicable / disabled
```

其中：

- `blocked`：应检查但无法完成。
- `not-applicable`：策略的适用条件经计算为假。
- `disabled`：没有启用，必须可见。
- 必需门禁的 `blocked`、`disabled` 不得汇总为成功。
- 合法空集合允许通过，但要输出适用原因与计数；显式必需目标缺失则失败。

### A3. 门禁谓词目录

下表定义的是**拟新增或修正后的契约**。当前实现不能被视为已经满足这些谓词。

#### 配置、执行和快照

| 编号 | 精确谓词 | 保证边界 |
|---|---|---|
| **G01 配置有效** | `P` 符合指定 schema；无未知普通键；类型、枚举、正则、路径和相互引用合法；扩展键只能进入规定命名空间 | 保证配置可解释，不保证配置覆盖了所有应管内容 |
| **G02 检查完整执行** | 每个适用的必需规则 ID 恰有一条合法终态结果；执行器成功结束；其声明对象集合与调度集合一致；无未处理错误 | 防漏跑和伪空结果，不证明规则实现正确 |
| **G03 输入与基线有效** | `B`、`T` 存在且满足指定比较关系；读取内容全部来自 `T` 或具名构建产物；Git 错误不被解释为空差异；必需比较没有 fallback | 保证比较对象明确，不保证选定基线适合业务判断 |
| **G04 执行身份有效** | 检查器、策略及必要依赖摘要属于获授权版本；最终结果由可信执行身份提交，且绑定本次输入元组 | 保证身份与关联，不保证可信执行器没有缺陷 |

当前 `resolveBase` 的降级 note 可保留为交互诊断，但在要求历史比较的验收场景，缺 base 应为 `blocked`。主分支 push 不能继续默认与自身 HEAD 比较；应使用事件的前后提交，首次接入则显式登记基线。

#### 文档结构、引用和依赖

| 编号 | 精确谓词 | 保证边界 |
|---|---|---|
| **G05 目标边界与可重建性** | 每个受检目标按对应语法解析后位于允许的仓库或产物命名空间内；类型符合关系要求；目标属于 `T`，或属于具备有效生成记录的产物清单 | 保证目标可定位、可重建；不保证内容正确 |
| **G06 core 身份** | core 的文件集合与已批准 manifest 完全相等；每个文件内容摘要相等；未通过未授权策略变更替换预期摘要 | 比当前“文件和本地 profile 一致”更强；仍依赖批准链 |
| **G07 入口、可达性与预算** | 必需入口存在；每个要求可达的现行文档能沿允许边到达；必读路径不经过已退役内容；各预算均满足声明计量方法 | 保证能找到、大小受限，不保证读者真的读完 |
| **G08 链接、路径、命令与引用有效** | 对支持语法识别出的每个引用，目标文件、锚点、ID、行范围或命令名在相应权威集合中存在，且类型匹配 | 不支持的语法要列出；不保证命令能成功运行 |
| **G09 pin 一致** | 每个要求存在的 pin 均能唯一解析；目标和范围合法；按指定归一化规则计算的完整摘要等于登记摘要 | 证明选定内容一致，不证明文字与代码语义一致 |
| **G10 登记声明的证据绑定** | 对每个被策略要求验证的声明，其正文摘要、依赖清单摘要、验证方法版本与有效验证记录完全匹配；适用的外部证据未超过约定期限 | 证明“这段话在这些依赖上经过这次核对”，不证明依赖登记完整 |

G05 的路径处理应集中实现：

1. 区分 URL、仓库路径、文档相对路径和产物路径。
2. 明确前导 `/` 表示仓库根。
3. 解码与分离 query、fragment 后再判断。
4. 在不可变 Git 树中识别符号链接对象；不能靠 `existsSync` 跟随本机链接。
5. 对允许的构建产物，核对生成步骤、输入摘要和产物摘要。
6. 不允许通过修改 `ignore` 或豁免字段，在同一次变更中未经批准撤掉覆盖范围。

G07 的预算必须明确单位。建议新 schema 使用 Unicode 码点数、明确的物理行数和必要的 UTF-8 字节数；旧版 JavaScript `text.length` 语义应保留迁移说明，不能静默更换。

G09 可继续允许明确声明的 CRLF→LF 归一化，不能顺便删除行尾空白。现有短哈希可作为旧格式兼容；新的证据与身份记录使用完整 SHA-256。

#### 决策、记录与生命周期

| 编号 | 精确谓词 | 保证边界 |
|---|---|---|
| **G11 决策引用与落地** | 决策 ID 唯一；显式决策引用全部可解析；生效决策有合法落地点；指定落地段落引用该 ID；替代关系无悬空引用和非法循环 | 不证明段落正确表达了决定 |
| **G12 决策授权** | 每个需要 owner 授权的变更，存在来自授权身份、绑定决定内容摘要与作用域的接受记录；公理变更另满足原文引用要求 | 证明授权事件发生，不证明模型没有误解其他未记录意图 |

决策建议采用不可变决定记录、后续替代事件和生成的当前状态视图。这样不必反复改旧记录的状态字段。它需要调整 GUIDE 的操作规则，但不需要改 A5。

#### 任务、验证与恢复

| 编号 | 精确谓词 | 保证边界 |
|---|---|---|
| **G16 变更处置完整** | `Δ(B,T)` 中每个受管源码路径恰有有效处置：关联已检查的文档、具名的无需改文档说明，或已批准的范围豁免；处置绑定当前差异摘要与责任人 | 只保证影响经过处置；“无需改文档”是否合理仍由人判断 |

| **G20 生成物一致** | 每个登记生成物等于指定版本生成器对当前权威输入的确定性输出；输入及输出集合完整 | 不证明生成器或源内容正确 |
| **G21 审计义务满足** | 对策略规定的审计对象，存在未过期、覆盖指定对象摘要的审计记录；要求处理的 finding 均有有效处置 | 证明审计与处置有记录，不证明没有漏查 |
| **G22 最终验收一致** | G01–G21 中适用的必需项均满足；当前审批及报告绑定同一候选和策略；合入、发布时对象未被替换 | 最终保证只覆盖这些已登记谓词 |

G16 与现有 `codeToDocs` 的区别必须公开：

- “代码改了，但文档没改”：是启发式提醒。
- “每项变更必须有绑定当前差异的处置记录”：可以是精确流程门禁。
- “处置一定正确、文档一定完整”：仍不能自动保证。

不能把第二条的实现包装成第三条。

### A4. 必须继续作为 aid 或人工审计的事项

以下内容不应直接按关键词或模型判断失败：

- 文档是否完整描述行为。
- 所有依赖是否登记齐全。
- 某次代码修改是否必然需要修改某段文字。
- 一段解释是否足够清楚。
- 决策理由是否充分。
- 是否存在未标记历史、隐含重复和遗漏边界。
- owner 的自然语言是否被完整、正确理解。

LLM 可以提出带出处的 finding；只有经过核实的结果才能进入修复。不得自动改写规范迎合代码。

## B. Session 重启、中断与恢复

### B1. 恢复的对象

恢复应当恢复**可继续工作的公开状态**，而不是承诺重建某个 Agent 的全部会话。

| 状态 | 权威位置 | M1 类别 | 写入者与时机 |
|---|---|---|---|
| 任务目标、范围、完成条件、开放步骤 | `docs/tasks/<id>/task.md` | K4；引用的已接受要求为 K2 | 任务建立及范围变化时，由负责人维护 |
| owner 决定与待决问题 | 决策记录；任务中的问题 ID、依赖范围 | 已发生授权为 K1；规范为 K2；待决为 K4 | 授权服务记录事件；负责人登记问题 |
| 实际 staged、unstaged、untracked 内容 | 当前工作区；必要时有内容快照 | 当前观察为 K3；已保存快照为 K1 | 执行代理自动观察 |
| 操作开始、完成、失败、被中断 | session 事件日志 | K1 | 执行代理在操作前后写入 |
| 命令、结果、输入和环境身份 | 验证记录 | K1 | 运行器自动写入 |
| 当前恢复结果、活动操作、可复用证据 | `checkpoint.json` 缓存 | K3 | 从日志与当前磁盘重新计算 |
| 本次接手摘要 | `RECOVERY.md` 生成视图 | K3，引用 K1/K4 | 恢复器生成 |
| 项目当前任务与下一步 | `CURRENT.md` | 分区标注 K3/K4 | 从任务集合生成 |
| 已完成步骤摘要 | `docs/log.md` | K1 生成视图 | 从完成事件生成 |

**checkpoint 不是另一份手写 CURRENT。** 前者回答“这个工作区目前能否安全接着工作”；后者回答“项目有哪些活动任务、下一步指向哪里”。

### B2. 最小状态结构

设计示意：

```text
session
  repositoryId
  worktreeId
  sessionId
  taskId
  agentProduct / agentVersion
  policyDigest
  journalSequence
  operationEpoch

workspaceObservation
  HEAD
  indexManifest
  worktreeManifest
  relevantUntrackedManifest
  preExistingChanges

execution
  pendingOperationIds
  completedEvidenceIds
  failedOrInterruptedOperations
  unresolvedQuestionIds
  nextTaskStepId
```

文件清单应记录路径、类型、模式和内容摘要。不能只存 `git status` 的文字，也不能仅存 HEAD：同一 HEAD 可以有完全不同的未提交内容。

初次接手时应登记既有改动，避免把其他人的工作归到新 session，并防止恢复过程覆盖它。

### B3. 写前记账，写后确认

对受控操作采用以下顺序：

```text
持久化操作意图
→ 执行操作
→ 观察结果与文件变化
→ 持久化完成/失败事件
→ 更新可丢弃的 checkpoint 缓存
```

操作意图至少包含作用域、输入摘要及可识别的操作 ID。命令运行记录包含启动和终止状态；没有终止事件的命令不得登记为成功。

日志追加应有序号、校验和及恢复规则。尾部不完整记录只能作为不完整尾部隔离，不能默默丢掉后继续宣称日志完整。原子替换 checkpoint；checkpoint 丢失时从日志和当前磁盘重建。

哈希链只能帮助发现日志结构损坏。如果写日志和重算整条链的是同一不可信主体，它不能提供身份或外部防篡改保证。较强模式需要由独立身份持有日志或定期锚定摘要。

### B4. 启动时一律核对

每次新启动、原生 resume、压缩后重新接管、切换 Agent，都经过：

1. 确认仓库、工作区、任务和策略身份。
2. 读取任务及被引用的生效规范。
3. 重新计算 HEAD、index、工作树及相关未跟踪文件清单。
4. 对照上次 checkpoint 和事件日志。
5. 将每项证据分类为可复用、已失效、未完成或无法确认。
6. 生成恢复视图，列出差异、未决项、未验证项和下一步。
7. 消除未处置的操作后，签发绑定当前状态的恢复凭据。

判断中断的信号包括：有开始无完成、上次 session 未暂停或关闭、持有者不再存在、日志损坏、实际内容与已知结果不一致。

心跳过期只能说明“持有者状态可疑”，不能单凭超时认定崩溃并夺取写权限。即使上次正常退出，新启动也必须核对实际文件。

状态关系建议为：

```text
新建/重新接手
    → 待恢复
    → 就绪
    → 工作中
    → 验证中
    → 已暂停 / 已关闭

身份、内容或日志出现无法解释的变化
    → 待恢复
```

暂停与关闭不同：暂停允许保留开放步骤和未验证项，但必须明确记录；关闭必须满足 G19。

### B5. 如何强制恢复

分两种承诺：

**普通接入模式**：启动 hook 自动运行恢复；后续工具 hook 在未恢复时拒绝其覆盖到的操作。远端拒绝缺少必需处置和验证的候选。无法承诺所有本地修改都被阻止。

**受控工作区模式**：Agent 对受管源码只有读权限，修改通过独立代理提交；构建输出写入隔离目录。代理只接受具有有效恢复状态的操作。通用 shell 不能另获对受管源码的直接写权限，否则统一边界立即失效。

仅给 `Edit` 工具加 deny，再允许 shell 任意写入，不能构成这个保证。shell 字符串匹配也不能解决脚本、重定向和持久进程问题。

并行工作建议每个工作区只有一个受控写入者；不同 Agent 使用独立工作区，在合并时重新验收。锁须由独立代理执行，本地可删除锁文件只能防误操作。

### B6. 能恢复到什么程度

- 仓库和本地磁盘仍在：可重新识别已记录与未记录的文件差异。
- 换机器或磁盘丢失：只有摘要不能恢复内容，必须另有获准保存的内容快照。
- 未记录的对话、推理、外部服务修改：不能凭 checkpoint 重建。
- 操作跨越外部服务：需服务端操作 ID、幂等或查询机制；否则标为结果未知，再核对。

不得将恢复实现为自动 `reset`、覆盖 dirty tree 或无条件重跑命令。恢复首先是观察和归因。

### 适配器组织

适配器位于 core 之外：

```text
adapters/
  <product>/
    manifest.json
    templates/
    probes/
    README.md
```

manifest 至少声明：

- 产品、形态与版本范围。
- 入口路径、作用域和内容导入方式。
- 实际支持的生命周期事件。
- 拒绝、错误、超时的行为。
- 需要授予的权限。
- 哪些能力经过文档核实，哪些经过安装版测试。
- 已知覆盖缺口。

必须分别检测四种能力：

```text
发现入口
≠ 导入内容
≠ 阻断工具
≠ 恢复任务
```

### 避免入口副本分叉

通用规范只维护一次。适配器入口采用以下顺序：

1. 产品有可靠内容导入：生成薄桥接。
2. 只有路径规则或按需读取：生成该产品支持的规则，并明确其加载条件。
3. 没有可靠导入：从同一权威源生成有预算限制的必要内容。
4. 所有生成入口都由 G20 校验，禁止手工维护第二套通用规则。

当前 `CLAUDE.md` 的 `@AGENTS.md` 是有效的桥接思路，但 `init` 跳过已有文件后必须给出接入冲突报告。适配器更新也应输出可审查迁移，不得无声覆盖用户配置。

安装版探测至少覆盖：加载、导入、直接编辑、shell 修改、hook 故障、超时、原生 resume 后重新核对。模型回答“我读过了”只能算观察，不能成为理解证明或权限凭据。

## D. 全流程文档体系

### D1. 数量与职责

建议完整体系有 **17 份固定 Markdown 文档**：项目侧 14 份，固定 core 副本 3 份。另有 core 许可证、机器配置及按实际任务增长的记录。

这不是每次启动都读 17 份。固定文件承担稳定职责，任务与记录按需进入阅读路径。

### D3. 阅读预算

保留现有模板作为初始上限参考：AGENTS 100 行/6000 当前计量字符，CURRENT 45 行/4000 字符，见 `templates/docaxioms.json:10–13`。新计量单位须显式迁移。

建议冷启动路径限定为：

```text
产品入口
→ 通用路由与必要规范
→ CURRENT
→ 当前任务
→ 任务引用的规范、描述与证据
```

- 历史、全部日志、全部研究不进入默认必读链。
- task 页只保留目标、范围、完成条件、开放步骤、阻塞和链接。
- 原始命令输出、长论证和审计逐条证据按需打开。
- 能按产品可靠导入的内容可统一打包；不能可靠导入时不得仅凭链接宣称已加载。
- 已接受任务不能被模型上下文限制静默截断；超预算应拆分路由或任务，而非截掉末尾。

这些是可试验的初始预算，不是已验证的最优 token 数。

### D4. 全生命周期

| 阶段 | 改动位置 | 守住的检查 |
|---|---|---|
| 接收需求 | 新建任务，引用既有要求；新增意图先等待 owner 接受 | G11、G12、G14 |
| 形成决定 | 更新规范落地点，新增决定记录；保留原决定及替代关系 | G11–G13 |
| 调研和计划 | 任务列开放步骤，研究绑定任务 ID | G14、G07 |
| 实现 | 修改代码；对影响文档的声明核对；登记变更处置 | G09、G10、G16 |
| 验证 | 对固定输入运行必需命令，生成证据 | G03、G04、G17 |
| 暂停或交接 | 完成操作记账，保存恢复条件；保留未验证项 | G18 |
| 人类审查 | 审查意图、描述与行为的差异；接受绑定差异的审查记录 | G12、G16、G21 |
| 合入 | 验证实际候选树及最新审批 | G22 |
| 发布 | 绑定源码、文档构建、产品制品和发布身份 | G17、G22 |
| 关闭任务 | 完成或移交开放项；生成日志、计划和 CURRENT | G19、G20 |
| 退役 | 将仍生效内容迁到权威位置，其余归档、修复引用 | G13、G15 |
| 周期审计 | 对登记声明、限制和入口执行只读核对 | G10、G21 |

代码和文档可以分开提交，但最终候选必须一起通过。仍被支持的旧版本文档不能仅因版本旧就判为历史废弃；应有清晰的版本与支持身份。

## E. 人类阅读、审查与延续性

### E1. PR 中展示“需要判断的内容”

生成一份绑定候选树的审查报告，顺序为：

1. **规范变化**：哪些要求变了，谁授权，影响范围。
2. **行为与描述变化**：源码差异对应哪些声明。
3. **依赖变化**：pin 平移、内容变化、依赖集合变化分别展示。
4. **验证证据**：针对哪个输入、运行了什么、哪些未运行。
5. **未覆盖内容**：aid、无法确认的行为、保留限制。
6. **审批对象**：本次审批所绑定的差异及策略摘要。

审查员可以直接跳到具体段落、代码和证据。报告不能用“文档已更新”替代实际差异。

### E2. 减少 diff 噪声

- 生成报告以制品和 PR 视图展示，避免每次检查都写回时间戳。
- 生成索引使用稳定排序，不因无关对象变化重排。
- pin 平移与正文修改分开显示。
- 禁止为刷新 pin 顺便格式化整份 Markdown。
- 每任务、每决定独立记录；索引生成，减少多人争改同一表格。
- 不让大量运行日志进入 CURRENT 或 README。

### E3. 审查记录如何可信

审查记录至少包括：审查身份、角色、对象摘要、结论、范围、时间和来源事件 ID。

作者提交的 `reviewed: true` 只能是声明，不能充当已完成审查的证据。接受记录应来自托管平台事件或独立授权服务，并在输入变化时按策略失效。

CODEOWNERS 需要保护自身；同一条规则列出多个 owner，通常是其中一个批准即可，不能据此声称“两类角色都批准了”。如要求双角色独立审查，应由策略另行验证。[GitHub CODEOWNERS](https://docs.github.com/en/repositories/managing-your-repositorys-settings-and-features/customizing-your-repository/about-code-owners)。

AD-6 的隐私边界应保留：普通决定不要求公开 owner 全部原话；记录可访问的授权来源、摘要和归属。公理变更仍遵循锁文件要求，不能用一个匿名布尔值替代原文授权。

### E4. 人员更替

交接包应包含：

- 生效要求与对应决定。
- 当前任务和未决事项。
- 最近有效证据及其失效条件。
- 已知限制与没有覆盖的检查。
- 角色接替和授权来源。

权威分配到可接替的角色，身份成员变化有授权记录。离职人员的聊天记录或个人记忆不能成为唯一可访问的设计理由。

## F. 检查的自发性与绕过面

### F1. 自动触发矩阵

| 触发时机 | 自动动作 | 绕过面与补足 |
|---|---|---|
| 新接入、升级 | 检查入口冲突、策略、适配版本与生成物 | 当前 init/update 不具备；需要显式接入验收 |
| Agent 启动、resume、重新接管 | 执行恢复并生成接手视图 | hook 可能未启用；受控代理才可在操作边界强制 |
| 受控操作前后 | 写前意图、写后结果，失效相关证据 | 普通旁路进程不可见；隔离权限或启动时重新核对 |
| 本地 pre-push | 提前发现结构和证据问题 | 可跳过，最终依赖远端 |
| PR 创建、更新、重新进入审查 | 检查候选、影响与审批 | workflow 与策略不得由候选自行削弱 |
| 合并队列 | 检查实际组合候选 | 必须接入对应事件 |
| 发布 | 核对源码、文档和制品身份 | 发布身份及目标也必须受控 |
| 定期调度 | 生成审计清单、执行可重复核对、登记待审项目 | 定时任务可能停跑；需检查到期义务与调度健康 |
| 外部依赖变化 | 失效相关证据并触发复核 | 未登记外部依赖无法自动发现 |

合并队列需要对应的 `merge_group` 事件，现有 workflow 没有该事件。不能把普通 PR 的绿灯直接延续到队列组合。[GitHub 规则排障](https://docs.github.com/en/enterprise-cloud%40latest/repositories/configuring-branches-and-merges-in-your-repository/managing-rulesets/troubleshooting-rules)。

### F2. 不把“有 cron”当作自发性保证

定时运行与最终完成是两件事。应登记审计义务：

```text
对象集合 + 输入摘要 + 责任角色 + 到期条件 + 最近完成记录
```

调度器负责启动；验收器负责在需要时拒绝过期义务。独立健康检查发现任务长期未启动、未完成或无人处置。

GitHub 定时任务可能延迟或丢弃；公共仓库长期无活动还可能自动停用。因此只安装 schedule 不能保证持续审计。[调度排障](https://docs.github.com/en/enterprise-cloud%40latest/actions/how-tos/troubleshoot-workflows)、[工作流停用规则](https://docs.github.com/en/actions/how-tos/manage-workflow-runs/disable-and-enable-workflows)。

“超过期限”只证明审计义务过期，不能写成“文档已错误”。对无法精确判定的语义问题，系统可以保证产生待审项、分配责任和检查处置；不能保证无需人的判断就完成真实修复。

### F3. 检查不能由被检查对象自行取消

较强的验收部署应满足：

- 必需策略从可信基线或独立策略源取得。
- 候选修改策略时，原策略继续适用；新策略走独立授权及生效过程。
- 汇总器及发布凭据不运行在候选可改写的进程中。
- 候选项目扩展在无签发凭据的隔离进程执行。
- 汇总器验证扩展结果的规则 ID、类型、对象数、终态和输入绑定。
- 缺结果、进程提前退出和非法 JSON 都不能产生绿色验收。
- 拒绝普通 `--report` 结果作为门禁通过凭据。

执行候选代码的任务不应同时持有能签发最终成功或访问高权限资源的身份。GitHub 官方也明确指出，特权 workflow 检出不可信 PR 内容会破坏安全边界。[GitHub Actions 安全说明](https://docs.github.com/en/actions/reference/security/secure-use)。

## G. 可行性、源码改造、验收与 owner 决策

### G1. 改造落点

| 位置 | 建议改造 |

| `src/check.mjs` | 引入严格 profile 校验、稳定规则 ID、结构化状态和计数；以统一快照读取；区分 Git 错误、空差异和降级；修复扫描范围 |

| `test/` | 保留良性对照和故障见证，增加边界、崩溃、旁路与完整执行验证 |
| `.github/` 与外部配置 | 接入实际 required checks、保护规则、合并队列、审计调度和发布身份 |

所有新增 CLI 名称都属于待设计接口，不能在现有文档中写成已可运行命令。

应先解决参考报告中的底层缺陷：profile 校验、路径作用域、仓库边界、history 比较、缺失文件诊断和显式选择器未命中。不能在这些边界仍不可靠时，叠加一个“完整流程通过”的总标签。

### G2. 验收应验证失效路径

关键验收包括：

- 拼错配置、删除规则、必需目标为零时不伪装成功。
- 合法空集合不误报。
- 缺 base、Git diff 错误、读取失败输出 `blocked`。
- 仓外路径、编码路径、query、符号链接不能逃逸。
- 干净环境不接受本地偶然存在的目标。
- history 中修改代码、标题或链接标题会失败，合法 URL 修复能通过。
- 重新计算 pin 不能替代要求的语义核对或授权。
- 对执行前、执行中、执行后、checkpoint 替换时分别中断，恢复结果正确。
- 证据记录后再次改代码、测试、规范或策略，旧证据正确失效。
- 持久终端、外部文件修改、并行工作区不会继承无效恢复状态。
- 扩展 `exit 0`、不返回结果或伪造计数，不能骗过汇总器。
- 修改 workflow、豁免或策略不能在同次候选中自我放行。
- 审批后候选变化、队列组合变化，必须重新满足对应条件。
- 原生 Agent checkpoint 恢复文件后，必须重新核对实际状态。

这些是后续实现的验收要求，本轮未执行，不能标为通过。

### G3. AD-7 的准确适用

AD-7 原文说的是**本仓库自身尚未全面执行自己的检查**，并规定逐项恢复阻断的条件，见 [docs/decisions.md:12](docs/decisions.md:12)。

实际落实也符合这个区分：

- 普通 CLI 按各检查的 `level` 决定失败。
- 本仓库 `npm run check` 先跑测试，再运行自身 `check --report`。
- `test/self.test.mjs` 只把指定集合纳入自身阻断，并另外检查缺失或越界的 pin 目标。

因此：

1. 不能推导出所有消费项目的门禁都受同一升格开关控制。
2. 本仓库新增阻断规则必须尊重 AD-7，不能改名为“基础设施检查”就视为豁免。
3. 若 owner 希望立即扩大自身阻断面，需要明确改变该决定。
4. 外部记录应按规则分别登记：至少 10 次相关变更、3 条各自值得修改文档的发现、实际处置与 owner 接受事件。
5. 扫描对象数、同一变更中的多个匹配、合成故障测试，不能冒充 10 次真实相关变更。

本轮未发现足以证明新规则已经满足升格条件的登记材料；这不等于证明仓库之外从未做过试验。

### G4. 可行性评级

| 方案 | 评级 | 主要条件 |
|---|---|---|
| schema、完整结果、精确引用、预算、pin、生成物一致性 | **可行** | 明确语法、对象集合与失败状态 |
| 记录保留、决定状态投影、授权关联 | **可行** | 区分记录内容与生效状态，具备可信授权来源 |
| 工作区核对、事件日志、跨 Agent 接手 | **可行** | 对已保存状态负责，不承诺隐藏上下文 |
| 每次操作前强制恢复 | **有条件可行** | 独立代理及权限隔离覆盖所有受管写入 |
| 自动运行和验收时强制审计义务 | **可行** | 调度与到期检查分开，责任有人接手 |
| 合入、发布强制检查 | **有条件可行** | 远端权限、身份、策略和结果来源真实受保护 |
| 所有主流 Agent 原生一致接入 | **有条件可行** | 按产品、形态和版本适配，能力不足时明确降级 |
| 自动证明所有文档未过时、完整且正确 | **不可行** | 自然语言语义、未知依赖和外部变化无法被现有谓词穷尽 |
| 普通本地 hook 完全不可绕过 | **不可行** | 同权限进程可以绕开 |
| 从摘要恢复丢失的文件或未记录的思考 | **不可行** | 摘要不包含原始内容 |
| 仅靠签名证明 owner 的判断或文档内容正确 | **不可行** | 签名证明身份与声明关联 |

### G5. 需要 owner 决定的事项

1. 是否批准目录式决定记录、生成索引，以及对应 GUIDE 操作规则。
2. 是否采用严格验收配置；哪些规则必需，哪些仅报告。
3. 本仓库新阻断规则继续按 AD-7 推进，还是修改 AD-7。
4. core 换行身份采用 LF 属性约束还是文本归一化；如何迁移现有 pin。
5. 构建产物如何登记，哪些场景允许非提交文件成为目标。
6. 非 Markdown 决策落地点允许哪些类型和反向引用方式。
7. 未发布决定如何撤回、是否存在允许删除的明确例外。
8. 是否需要受控工作区；接受哪些平台与权限前提。
9. 哪些审查必须由 owner、其他角色或多个独立身份完成。
10. 哪些内容需要跨机器保存，保存位置、范围与保留期限。
11. 哪些语义审计具有期限，以及过期阻断合入还是仅阻断发布。
12. 支持哪些 Agent 版本，旧版和已归档产品承诺到什么程度。

上述多数属于派生规则和项目决定，不要求修改锁定公理。Agent 名称、路径、配置、适配逻辑全部留在 core 外；core 如调整，只表达可移植原则和流程。不能为自动迎合代码而改变 A0，也不需要为了恢复与执行机制改写 A0–A8、M1–M4。

## H. 对上一轮总结的批驳

1. **“不改 harness，只改冷启动内容”不足以满足新要求。**  
   它可以描述当前工具，但无法提供不依赖记忆的恢复和动作前强制。新系统至少要增加执行器、生命周期接入或远端验收；更强的本地保证还需要权限边界。

2. **“读过入口链”不能当作已执行的系统事实。**  
   Markdown 链接不必然导入正文。不同产品、目录和版本的入口行为不同；`init` 还会跳过已有入口。

3. **把收尾写 log、清 plan、重写 CURRENT 当作恢复协议，遗漏了异常退出。**  
   这些步骤恰恰在中断时最可能没有发生。应使用写前意图、自动结果记录和启动时实际核对。

4. **把 `garden` 纳入流程，不等于自动完成语义审计。**  
   当前命令输出的是清单。自动生成清单、执行审计、核实 finding、完成处置应分别记录。

5. **“A5 旧决策行不删没有执行”方向正确，但不能据此直接判历史删除违规。**  
   参考报告已经说明该次删除涉及未发布决定的规范空缺。应明确退役规则；更完整的缺口还包括 K1 日志和授权记录的保留。

6. **“所有新项目都是已知有缺陷的预发布门禁”混合了不同结论。**  
   预发布状态和具体缺陷需要公开；但某个谓词仍可能有效。AD-7 是本仓库的自我阻断决定，不能用来笼统否定所有消费项目的门禁。

7. **“AD-7 外部实证为零”超出了本轮可证范围。**  
   可以说目前未见合格的升格登记，不能据此证明所有外部活动不存在。

8. **对静默失败的归因仍不完整。**  
   profile 拼错、零匹配之外，还有 Git 失败与空差异混同、扩展结果缺字段、候选自行修改检查器或策略、工作树与提交对象不同等问题。

9. **pin 更新不是“已核对文档”的证据。**  
   当前命令可以刷新哈希，但不验证谁审查、审查了哪段文字、依据什么输入。更强的方案必须绑定正文、依赖和审查记录。

10. **可靠性需要被写成有限承诺。**  
    方案能够保证：规定对象经过规定检查、记录与证据绑定明确、缺失不能冒充成功、受保护验收不能由普通候选自行取消。文档的语义正确性仍需以 owner 意图、源码、测试和运行作逐项比较，并把未守住的部分放在读者实际会读到的位置。
