# 研究简报（第二题）：把最终门槛留在本地

背景：research/全流程文档系统方案.md 当前结论是“最终验收放远端（L3 远端必需检查 + L4 平台治理），本地钩子只是提前暴露”。owner 的新要求：**最终门槛 / 校验尽可能留在本地；需要的话可以做一个程序。** 不计实现成本。只读，不要改仓库文件（除了被告知的输出文件）。

必读：research/全流程文档系统方案.md、research/调研校验与迭代参考.md、core/AXIOMS.lock.md、core/GUIDE.md、docs/decisions.md（AD-1..AD-7）、README.md；源码按需（src/、bin/）。

## 要回答
1. **本地能做到多硬。** 列出本地可用的强制机制并逐一评估守住/没守住什么（A6），至少考虑：
   - git 客户端钩子（pre-commit / pre-push）——已知可 `--no-verify`；
   - **本地“闸门仓库”**：一个本机上的 bare 仓库作为唯一推送目标，由它的 pre-receive / update 钩子在接收端对被推送的提交树做验收（接收端钩子不能被 `--no-verify` 跳过，且天然读不可变提交而非工作树），通过后再由它转发到托管平台；
   - **操作系统级权限分离**：闸门进程/仓库归另一个系统用户所有，开发者与 Agent 进程没有写它的引用、改它的钩子或读它的签名密钥的权限；对托管平台的推送凭据只由闸门持有；
   - **本地签名 attestation**：闸门对 (提交树, 策略摘要, 检查器版本, 环境身份) 签名，密钥放 OS 钥匙串 / Secure Enclave / 硬件密钥，结果存为 git notes 或 trailer；远端如果还在，只需验签（极薄），最终判断仍在本地；
   - **常驻守护进程**：监视文件系统事件（不依赖 Agent 钩子）记录工作区变化，用于会话恢复，以及给钩子提供快速判断（避免每次冷启动）；
   - 其他你认为更合适的方案（例如本地容器 / 沙箱运行 Agent、只读挂载、受控写入代理）。
2. **给出推荐的本地程序架构**：组件、各自权限、数据流、信任根在哪、对 macOS/Linux/Windows 的可行性、单人 vs 多人仓库、离线可用性。说明与远端的关系（完全不要远端 / 远端只验签 / 远端保留兜底）。
3. **对现方案的改动**：第二节分层、验收器契约（策略取自基线、治理文件、凭据隔离）、G17 证据载体（改为本地签名？）、G22、第三节会话恢复（守护进程能否让事件记录完整到可以作为依据）、第七节自发性，分别怎么改。
4. **本地方案根本守不住的**：例如同一 OS 用户下的绕过、root/管理员、owner 自己、密钥泄露、直接改托管平台、多台机器之间如何互信；以及“本地门禁 + 远端只验签”是否能把这些缺口补上。
5. **与公理和决策的关系**：A6/A7、AD-2（程序放 core 外）、AD-4（npm CLI 纯 JS，守护进程/签名是否越界）、AD-7。
6. **可行性评级与需要 owner 决定的问题。**
