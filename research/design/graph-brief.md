# 讨论：用图论组织 docaxioms 的文档，让一次更新沿依赖传播

## owner 的设想

把项目文档建成一棵文档树（或图），按结构层级排列各个节点。某个阶段或任务完成时，只更新一个最基础的文档，工具就沿着文档树自动找到与这次改动相关的其他文件，并做相应的更新。

## 现状（仓库 main，读代码核实）

文档之间已经有几种边，引擎已在用其中一部分：

- 链接：`links and anchors resolve` 检查目标存在；`every current document is reachable from an entry point` 从 `entries` 做广度优先遍历（src/check.mjs）。
- 决策落点：决策行链接到落地段落，检查该段落提到决策编号。
- code pin：文档段落 → 代码片段的哈希锚（src/pins.mjs），代码变了门禁失败，`pin --write` 复核后刷新。
- `codeToDocs`：代码 glob → 文档的映射，review aid，代码变了而文档没动时提醒。
- 方案 research/全流程文档系统方案.md 里还有 G16（受管契约路径上的变更要有处置）、G20（生成物等于生成器对当前输入的输出）。

公理见 core/AXIOMS.lock.md，尤其 A2（依赖）、A4（手抄副本会分叉，生成或检查的副本不会）、A6（门禁只保证其谓词）、A7（门禁要精确）、M3（一事一主）。

## Claude 的初步看法

1. 可行，但应是有向无环图（DAG），不是树：一份文档常依赖多个来源。边的含义是“依赖”（A2），不是“链接”：链接只表示可达，不表示内容依赖。
2. 机制可以照搬 code pin 和构建系统：
   - 文档对文档的段落级 pin：`<!-- pin: docs/design.md#cache@hash -->`，上游段落一变，下游即标为待复核。
   - 按拓扑序给出受影响的传递闭包，先复核上游。
   - “提前截断”（build system 的 early cutoff）：下游复核后内容没变，它的下游就不再被标脏，否则一次改动会淹没全图（A7）。
3. 能“自动更新”的只有生成内容（A4、G20）：索引、状态表、阶段卡里的计数、任务列表等，可由生成器从源头重算，检查生成物与重算结果一致。
4. 散文描述不能自动改写并当作正确（A0、A6）：工具能做的是精确列出“哪些段落因为哪处上游变化而需要复核”，可交给 agent 起草，但由人或 agent 复核后用 `pin --write` 式的显式动作确认。
5. 更根本的是减少需要传播的边：M3 要求一事一主，下游应链接而不是转述；只有确实要转述或摘要的地方才需要依赖边。
6. 先做 review aid，衡量误报后再考虑升为门禁（M2）。
