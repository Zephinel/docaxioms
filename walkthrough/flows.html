接入与开发流程

下面的命令和输出全部是在临时目录里实际运行 d840742 的 CLI 得到的。为了简短，check 的输出只保留不是 ok 的行，[exit N] 是命令的退出码。

A. 从零开始的新项目

一个只有一次空提交的 git 仓库，运行 init：

$ docaxioms init .
made AGENTS.md
made CLAUDE.md
made CURRENT.md
made docs/README.md
made docs/decisions.md
made docs/history/README.md
made docs/log.md
made docs/plan.md
docaxioms/ is pinned to v0.1.0-alpha.0 (d8407429); run: npx --no-install docaxioms check
Nothing runs the check for you yet: call `docaxioms check` from the project's verify command, require it
in CI, and optionally run it from a pre-push hook. "Run the check" in the docaxioms README says what each holds.
[exit 0]

init（src/manage.mjs:85）做三件事：

  1. 把 templates/ 下项目还没有的文件逐个复制过来，已有的一个都不碰（!existsSync(target)）；
  2. 把 core/ 的四个文件复制到 docaxioms/，公理文件设为只读（0o444）；
  3. 以模板的 docaxioms.json 为底，写入 core 一节：来源、版本、docaxioms 的提交号，以及每个 core 文件的 SHA-256。
生成的 docaxioms.json 
{
  "entries": ["AGENTS.md", "README.md", "docs/README.md"],   ← 候选入口，有一个存在即可
  "reachable": "^docs/",                                      ← 这些文档必须能从入口走到
  "codeExtensions": [],                                       ← 默认不扫代码
  "pathPrefixes": ["docs/"],                                  ← 行内代码里以这些开头的当作路径检查
  "decisions": { "file": "docs/decisions.md", "id": "D" },
  "log": "docs/log.md",
  "research": { "dir": "docs/research", "items": "docs/plan.md" },
  "history": { "dir": "docs/history", "banner": "Out of date", "erratum": "## Erratum ", "base": "origin/main" },
  "card": { "file": "CURRENT.md", "maxLines": 45, "maxChars": 4000 },
  "budgets": [{ "files": "AGENTS.md", "maxLines": 100, "maxChars": 6000 }],
  "garden": { "exempt": ["CLAUDE.md"] },
  "core": {
    "dir": "docaxioms",
    "source": "https://github.com/Zephinel/docaxioms",
    "version": "0.1.0-alpha.0",
    "commit": "d8407429f6bb829ce65696b67d38758d48baf3a5",
    "files": {
      "AXIOMS.lock.md": "0ebfe50e…",
      "GARDEN.md": "0fd7fe58…",
      "GUIDE.md": "ff106834…",
      "LICENSE": "1a336a47…"
    }
  }
}

第一次检查：

$ docaxioms check
ok   the profile has only known keys and valid values (A6)
… 另外 13 项 ok …
note a history file changes only in link targets, or grows by a dated erratum (A5)
       note: base "origin/main" was not found, or it shares no history with HEAD, so HEAD was used instead (committed changes were not compared)
ok   code changed, but the documents mapped to it did not (A2, A6, M2)
ok   current descriptions narrate past changes (A3, M1, M2)
[exit 0]
这条 note 很重要：仓库没有 origin/main，history 检查找不到比较基线，就和 HEAD 比——已提交的改动没被比较。它不让命令失败，但会明说“这一项少检查了什么”（A6）。接入后应把 history.base 改成实际的主分支，或在 CI 里拉全历史（本仓库 CI 用 fetch-depth: 0）。

故意加一个断链：

$ docaxioms check
FAIL links and anchors resolve (A2, A4): 1
       docs/README.md: design.md leads to a file that does not exist
[exit 1]

至此新项目就接好了。docaxioms 不会自己运行：init 最后一句提醒的就是这个。要把 docaxioms check 接到项目的验证命令、CI 和（可选的）pre-push 钩子里，它才真正起到门禁作用。

B. 已有项目接入

一个已有的小项目：README.md、AGENTS.md、docs/architecture.md、一篇没人链接的 docs/notes.md、src/cache.py、一个 Makefile（目标 test、lint）。

$ docaxioms init .
made CLAUDE.md
made CURRENT.md
made docs/README.md
made docs/decisions.md
made docs/history/README.md
made docs/log.md
made docs/plan.md
…
[exit 0]

$ git status --short
?? CLAUDE.md
?? CURRENT.md
?? docaxioms.json
?? docaxioms/
?? docs/README.md
?? docs/decisions.md
?? docs/history/
?? docs/log.md
?? docs/plan.md

和 A 比较：AGENTS.md 没有被创建，因为项目已经有了；git 状态里只有新增，没有一个已有文件被修改。这是 init 的契约：项目自己的文件永不覆盖。如果项目已经有 docaxioms.json 或 docaxioms/ 目录，init 直接拒绝。

第一次检查，找出一篇孤立的文档：

$ docaxioms check
FAIL every current document is reachable from an entry point (A3): 1
       docs/notes.md
note a history file changes only in link targets, or grows by a dated erratum (A5)
       note: base "origin/main" was not found, …
[exit 1]

docs/architecture.md 没报，因为 README.md 链到了它；docs/notes.md 从任何入口都走不到（A3：读者只能读到从入口能走到的东西）。

按项目调 profile

默认 profile 对代码一无所知。按这个项目调整：

"codeExtensions": [".py"],                              ← 扫 Python 文件里的决策号和文档路径
"pathPrefixes": ["docs/", "src/"],                      ← 行内代码里的 src/… 也要存在
"commands": [{ "prefix": "make ", "makefile": "Makefile" }],  ← `make xxx` 必须是 Makefile 里的目标
"history": { …, "base": "main" }                        ← 本地主分支叫 main

再把 docs/notes.md 和 docs/architecture.md 挂到 docs/README.md，让 AGENTS.md 链到 CURRENT.md 和 docs/README.md：

$ docaxioms check
（全部 ok）
[exit 0]

调好之后，文档里写错的路径和命令会被抓住。在 README 加一句 “Deploy with make deploy; config is in src/config.py”：

$ docaxioms check
FAIL paths named in current documents exist (A2, A7): 1
       README.md: `src/config.py` does not exist
FAIL commands named in current documents exist (A2, A7): 1
       README.md:6: `make deploy` is not a defined command
[exit 1]
接入已有项目的要点：先跑一遍看哪些文档孤立、哪些链接已断；再按项目的语言和工具配 codeExtensions、pathPrefixes、commands；最后把检查接进 CI。现有文档不必一次改完，可以先用 --report 只看报告。

profile 由谁来调，能不能自动

现在全靠手工，人或 agent 直接编辑 docaxioms.json。init 只把模板里的 profile 原样写进去（manage.mjs:102），不看项目里有什么文件；之后的 update 只改 core 一节，其他键都不动。

能不能自动，要分两类看：

设置能从仓库推出来吗依据
codeExtensions能git ls-files 里各种扩展名的数量
commands能有没有 package.json 的 scripts、Makefile、justfile
pathPrefixes大致能顶层目录里被跟踪的那些
history.base能git symbolic-ref refs/remotes/origin/HEAD，没有远端时用本地主分支
entries能候选入口里实际存在的那些
reachable、budgets、ignore、决策前缀、哪份文件是日志和计划不能这些是项目的约定，只能由 owner 决定

比较稳妥的做法是：工具只提出建议，比如加一个打印建议 profile 的命令，由人确认后再写入；不要在 init 里悄悄写进去。原因有两个：猜错的设置会让检查漏报，而且不会有任何提示（A6）；迭代方案第九节也把写入限定为“确定性生成”和“显式命令”两类。目前代码里没有这个功能，迭代方案里也没有单独列出这一项。

接入时文档已经超出预算

把一个故意不规范的项目接进来，实际运行的结果如下：根目录的 AGENTS.md 有 152 行，项目原有的 CURRENT.md 有 62 行，另外有 frontend/AGENTS.md、frontend/docs/、backend/docs/，还有一篇没人链接的 docs/old.md。

$ docaxioms init .        （AGENTS.md、CURRENT.md 已经存在，所以不复制、不修改）
$ docaxioms check
FAIL every current document is reachable from an entry point (A3): 1
       docs/old.md
FAIL the stage card stays within its size limits (A3): 1
       CURRENT.md: 62 lines, more than the 45 allowed
FAIL documents with a size budget stay within it (A3, M4): 1
       AGENTS.md: 152 lines, more than the 100 allowed
[exit 1]

结论：不会被豁免，也没有“接入时的基线”，超出预算就是 gate 失败。init 写入的模板 profile 里带着预算，并且直接套用到项目原有的同名文件上。可以这样处理：

  • 精简（GUIDE 推荐的方向）：把细节挪到专门的文档里，入口只保留路由和链接（M4）。
  • 调整 profile：放宽 maxLines，或者暂时删掉这条预算，等文档整理好再加回来。
  • 过渡期用 check --report：发现照常打印，但不让退出码失败，运行出错仍然失败。
  • 如果项目原有的 CURRENT.md 写的根本不是阶段卡，就把 card.file 改成另一个文件；否则阶段卡的预算会套到一份不相干的文件上。

历史检查不同：它有比较的基线（history.base），只管这个分支上改了什么。预算和可达性只看当前的样子，不区分哪些超出是接入前就已经存在的。

目录结构很乱：到处都有 docs、AGENTS.md 不止一份

还是上面那个项目。用默认 profile 时，frontend/docs/ui.md、backend/docs/api.md、frontend/AGENTS.md 都没有被报出来，原因是：

  • reachable 默认是 ^docs/，只要求根目录 docs/ 下的文档必须可达；
  • 预算的 files: "AGENTS.md" 是 picomatch 模式，只匹配根目录那一份。

它们仍然算作现行文档，链接、路径、命令这些检查照样会扫，只是不要求它们可达，也不限制大小。把范围放宽之后：

"reachable": "(^|/)docs/",
"budgets": [{ "files": "**/AGENTS.md", "maxLines": 100 }]

$ docaxioms check
FAIL every current document is reachable from an entry point (A3): 3
       backend/docs/api.md
       docs/old.md
       frontend/docs/ui.md
FAIL documents with a size budget stay within it (A3, M4): 2
       AGENTS.md: 152 lines, more than the 100 allowed
       frontend/AGENTS.md: 132 lines, more than the 100 allowed

所以对待结构很乱的项目，docaxioms 的态度是：不去猜结构，只按 profile 的声明去查。范围写多宽，管到哪里。它也有管不到的地方：

  • 它不理解“每个子目录有一份自己的 AGENTS.md”这种层级关系。有些 agent 会按目录去读最近的那份，docaxioms 只把它当成一份普通文档。
  • 同一件事在两份文档里各写了一遍（违反 M3，“一个事实只有一个所有者”），没有任何一项检查能发现。这要靠 garden 的人工审计。
  • 目录要不要合并、合并成什么样，它不会提议。接入前最好先整理一遍：子目录的文档挂到根目录的索引下，或者把子目录也列进 entries。

C. 完成一个功能：可配置的缓存过期时间

接着 B 的项目，在分支 ttl-config 上做一个功能：缓存过期时间改为由环境变量 WEATHER_TTL 控制。下面按 GUIDE 的“Which document owns what”表一步步走。

C1 计划与调研

在 docs/plan.md 加一个开放条目，链到它的调研；调研文件头部写 Status: open (…)：

docs/plan.md:          - Make the cache TTL configurable: [research](research/ttl.md)
docs/research/ttl.md:  # Cache TTL
                       Status: open (configurable TTL)
                       Options: environment variable, or config file.

$ docaxioms check
[exit 0]

如果写了一篇调研、却没有开放条目链接它：

$ docaxioms check
FAIL open research is linked from an open item, and every history file has its banner (A3, A5): 1
       docs/research/retry.md: no open item in docs/plan.md links to this research
FAIL every current document is reachable from an entry point (A3): 1
       docs/research/retry.md
[exit 1]

调研不会成为没人管的孤儿：要么有开放条目指着它，要么已经完成、该进 history。（这项关联目前是按文件名子串匹配的，迭代方案缺陷 8 说要改成真实链接。）

C2 owner 拍板：先改段落，再加决策行

GUIDE 规定的顺序：先改受影响的段落，写上决策号；再在决策表里加一行，带状态和落地点。同时在段落里钉住它依赖的那两行代码：

docs/architecture.md:
  ## Cache
  Responses are cached on disk for `TTL` seconds, read from the environment variable `WEATHER_TTL` (D1).
  <!-- pin: src/cache.py#L1-L2 -->

docs/decisions.md:
  | D1 | Should the cache TTL be configurable? | Yes, by the environment variable WEATHER_TTL | active | [cache](architecture.md#cache) |

$ docaxioms check
FAIL code pins match the current source (A2, A6, A7): 1
       docs/architecture.md:7: src/cache.py has no hash yet (it would be @b0753e25db87); review the passage, then run docaxioms pin --write --file docs/architecture.md
[exit 1]

没写哈希的 pin 是故意的失败：要先有人对照代码读过这段，才允许写上哈希。决策这边已经通过了：D1 有落地点 architecture.md#cache，那一节确实提到了 D1。

C3 复核后写上哈希

$ docaxioms pin --write --file docs/architecture.md
wrote docs/architecture.md:7 src/cache.py#L1-L2 (@b0753e25db87)
       1 | import os
       2 | TTL = int(os.environ.get("WEATHER_TTL", "3600"))
[exit 0]

$ docaxioms check
[exit 0]

注释变成 <!-- pin: src/cache.py#L1-L2@b0753e25db87 -->。--write 必须指定范围（--file、--pin 或 --all），并打印被钉住的代码，让人最后再看一眼（A7）。

C4 代码移动：上面多了两行

$ docaxioms check
FAIL code pins match the current source (A2, A6, A7): 1
       docs/architecture.md:7: src/cache.py#L1-L2 moved to #L3-L4 unchanged (hash @b0753e25db87); run docaxioms pin --relocate to update the line numbers
[exit 1]

$ docaxioms pin --relocate
moved docs/architecture.md:7 src/cache.py#L1-L2 -> #L3-L4 (@b0753e25db87 unchanged)
       3 | import os
       4 | TTL = int(os.environ.get("WEATHER_TTL", "3600"))
[exit 0]

内容没变、只是位置变了：引擎在文件里找到唯一一处哈希相同的两行，判为“移动”。--relocate 只改行号、不改哈希，所以不需要复核，可以放心批量运行。如果相同内容出现在不止一处，判为 ambiguous-move，要人手动定行号。

C5 被钉住的代码本身变了

把默认值从 3600 改成 600：

$ docaxioms check
FAIL code pins match the current source (A2, A6, A7): 1
       docs/architecture.md:7: src/cache.py changed (pinned @b0753e25db87, now @659682712335); review the passage, then run docaxioms pin --write --file docs/architecture.md
[exit 1]

这时要做的不是直接刷新，而是先看段落还对不对。这里补上“ten minutes unless set”，再刷新：

$ docaxioms pin --write --file docs/architecture.md
wrote docs/architecture.md:7 src/cache.py#L3-L4 (@b0753e25db87 -> @659682712335)
       3 | import os
       4 | TTL = int(os.environ.get("WEATHER_TTL", "600"))
[exit 0]
工具分辨不出你有没有真的复核：pin --write 只是刷新哈希。它能做到的是让每次代码变化都停下来，并指出是哪一段（A2、A6）。迭代方案第四节第 6 条讨论的就是这个边界。

C6 收尾：从计划删掉，调研进历史，记日志

docs/plan.md:          删掉那一条
docs/history/ttl.md:   # Cache TTL
                       > Out of date: decided as D1; see [architecture](../architecture.md#cache).
                       Options: environment variable, or config file.
docs/research/:        删掉
docs/log.md:           ## 2026-11-28
                       - Cache TTL configurable by WEATHER_TTL (D1). Ran `make test`.

$ docaxioms check
[exit 0]

历史文件开头必须有横幅（profile 里的 banner，这里是 “Out of date”），告诉读者现在的情况在哪里。然后提交，合入 main。

C7 历史记录不可改写

在功能分支上，这份历史文件是新加的，相对基线 main 还不算“已有的记录”，所以改它不会报错。合入 main 之后，在新分支上改它的正文：

$ docaxioms check
FAIL a history file changes only in link targets, or grows by a dated erratum (A5): 1
       docs/history/ttl.md: a history file may change only in its link targets, or by adding a dated erratum at its end
[exit 1]

只改链接目标（../architecture.md#cache 改成 ../architecture.md）可以；在末尾追加一段带日期的勘误也可以：

## Erratum 2026-11-29

A config file was also considered and rejected.

$ docaxioms check
[exit 0]

原理见 核心机制 · 历史比较：把基线版本和现在的版本都去掉链接目标，现在的必须以基线开头，多出来的部分只能是一段以 ## Erratum 日期 开头的勘误。

C8 定期审计：garden

$ docaxioms garden
Doc-gardening manifest (5 K3 description documents):
Protocol: docaxioms/GARDEN.md
Stage card: CURRENT.md (15 lines)
  - AGENTS.md (5 lines, 0 pins)
  - README.md (4 lines, 0 pins)
  - docs/README.md (9 lines, 0 pins)
  - docs/architecture.md (7 lines, 1 pins)
  - docs/notes.md (3 lines, 0 pins)

garden 只列清单：哪些是现行描述、各有多长、钉了几处代码、映射了哪些代码。真正的审计由人或 agent 按 GARDEN.md 逐条对照代码去做，结果是一份带日期的报告。机器检查保证不了“文字说的是对的”，garden 补的就是这一块。

D. agent 怎么知道要更新这些文档

templates/docs/ 下的决策、计划、日志、索引，以及 CURRENT.md，都不会自己更新，也没有任何后台程序去改它们。agent 去更新，靠的是下面这条链：

1. agent 读入口文件大多数 agent 原生读 AGENTS.md；Claude Code 读 CLAUDE.md，模板里这份只有一行 @AGENTS.md，作用是把它导入进来
↓
2. AGENTS.md 指路按顺序读公理、GUIDE、CURRENT.md，再从 docs/README.md 读和任务有关的页面；提交文档前和推送前运行 docaxioms check
↓
3. GUIDE 的 “Which document owns what” 表每发生一类改动，该改哪份文档、怎么写。agent 靠读懂这张表，才知道要去改
↓
4. check 抓一部分遗漏前提是它被接进了验证命令、CI 或钩子

前三步都只是文字，agent 读了不一定照做。第 4 步能抓住的遗漏是有限的：

漏做了什么会被发现吗
owner 的决定没有落到段落里，或者段落没提决策号会（落地点检查）
新文档没挂到索引会（可达性，限 reachable 的范围）
事项删了，调研还是 open；或者调研没有对应的事项会（开放调研检查）
钉住的代码变了，段落没复核会（pin）
改了代码，映射的文档没动只提醒（codeToDocs 是 aid）
完成一步没写日志不会
CURRENT.md 没改写，内容已经过时不会（只查长度）
该加计划条目却没加不会
行为变了，没有 pin 的描述没改不会，只有 garden 审计时才可能发现
接入已有项目时还有一个缺口：如果项目原来就有 AGENTS.md，init 不会改它（上面那个不规范的项目就是这样），所以第 2 步的指路根本不存在，agent 连 docaxioms 都不知道。要手工把那几行加进去。

目前缺的东西：没有技能（skill），没有钩子，也没有在 agent 启动或恢复会话时自动注入的简报。GUIDE 是唯一的说明书，每次都要整份读完。迭代方案第六节第 2 条提出了“工作、审计、恢复”三个按需技能，钩子只负责把调用转给 docaxioms hook <事件>；第九节列了各个时机自动做什么。这些都还没有实现。
