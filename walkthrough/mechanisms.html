核心机制

检查的判定逻辑都建立在下面这几块上。读懂它们，17 项检查基本就是在组合这些部件。

1. 仓库视图与边界：project()

src/check.mjs:93。所有检查都通过它返回的对象 p 访问仓库，不直接碰文件系统。这样“哪些东西算仓库里的、能不能读”只在一处决定。

成员作用
inside(path)这个路径真的在仓库里吗。路径名看起来在里面，也可能经符号链接通到外面，所以取路径上离它最近的、实际存在的那一段，用 realpath 求真实位置，判断是否在仓库根之下。断掉的符号链接可能指向任何地方，算在外面。整个过程不会去碰仓库外的东西
read(file)所有读取的唯一入口：先过 inside()，不在仓库里就抛错；读过的缓存起来
has / isFile / isFolder存在性和类型判断，都先过 inside()：仓库外的路径永远“不存在”
all文件清单：优先用 git ls-files --cached --others --exclude-standard，所以被 .gitignore 忽略的不算；没有 git 时遍历目录。两种方式都跳过符号链接和 profile 的 ignore
currentDocs、code见 各检查看哪些文件
markdown(file)解析结果（第 4 节），每份文件只解析一次
links(file)、targetOf(file, target)链接解析（第 2 节）
profile、given可用的 profile（出错的设置已剔除）和原始 profile（只给 profile 检查报问题用）
“边界只在一处”的好处：第一批修复之前，链接、落地点、pin、配置文件各自解析路径，../ 能让链接检查读到仓库外的 Markdown。现在任何人通过 p.read 读仓外文件都会失败。

2. 链接怎么解析

targetOf(file, target) check.mjs:163 → resolveTarget() :46：

  1. 带协议（https:、mailto:）或以 // 开头：外链，返回 undefined，不检查；
  2. 按第一个 # 分出锚点，去掉 ?query；
  3. URL 解码（%20 → 空格），反斜杠转成 /；
  4. / 开头：从仓库根算；否则从当前文档所在目录算；
  5. 规范化后如果是 .. 或以 ../ 开头，或经符号链接通到外面：标为 outside。
docs/guide.md 里写           解析为
[a](setup.md)                docs/setup.md
[b](../README.md#install)    README.md，锚点 install
[c](/src/app.py)             src/app.py（从仓库根）
[d](design.md?plain=1#x)     docs/design.md，锚点 x
[e](../../other/x.md)        outside（报错，且不读）
[f](https://example.com)     外链，不检查

锚点按 GitHub 的规则生成（github-slugger）：## 1. Cache 的锚点是 1-cache，同名标题依次加 -1、-2；也认 <a id="x"> 和 <a name="x">。

注意 pin 的路径规则和链接正好相反：pin 默认从仓库根算，./、../ 开头才相对当前文档，/ 开头直接拒绝（第 5 节）。迭代方案第十二节第 16 项讨论要不要统一。

3. profile 校验：src/profile.mjs

两张表定义了 profile 能写什么：

  • KINDS :20：值的类型及其判定函数和错误说明，如 text（非空字符串）、dir/file（从仓库根写起、没有空段/./../首尾 / 的路径）、regex（能编译）、count（≥1 的整数）、patterns（非空 glob 列表）。
  • SCHEMA :41：每个键用什么类型。后缀 ! 表示必填；后缀 ^ 表示“限定范围”的可选项（如 core.dir、exempt）：它写错时整个对象都丢掉，否则只丢掉它会让对象管得比本意更宽。数组里放一个形状，表示“这种形状的对象列表”。

validate() :69 递归比对，每个问题记成 { path, drop, text }：path 是位置（如 ["commands", 0, "prefix"]），drop 是要剔除的部分，text 是给人看的话。

usableProfile() :123 按 drop 精确剔除：

问题出在剔除什么例子
一个可选的设置只剔这个设置core.foo 是未知键 → 只去掉 foo，core.files 照用
必填项缺失或写错，或 ^ 项写错剔掉它所在的对象history.banner 为空 → 整个 history 不用，history 相关检查不运行
列表里的某一项只剔这一项commands[1] 没有前缀 → 去掉这条规则，commands[0] 照用
整个 profile 不是 JSON 对象所有检查都不运行，全部报 error[]

同时，profile 检查（第 1 项）把每个问题报成 FAIL。所以拼错一个键：会被报出来，但不会让别的检查一起失效，--report 也仍然只是报告。pin 和 garden 会写文件或据此列清单，遇到任何问题直接拒绝运行。

docaxioms.json: commmands is not a key docaxioms knows (a project's own keys must start with "x-")
docaxioms.json: card.maxLines must be a whole number of 1 or more
docaxioms.json: commands[0] must set exactly one of jsonFile, makefile or list

JSON 的 null 等于“没写”（withoutNulls() :105），项目自己的 x- 键原样保留、不复制。

4. Markdown 解析：src/markdown.mjs

parseMarkdown(text) :19 用 remark（CommonMark + GFM）解析一次，得到一棵语法树，再算出检查要用的各种视图：

输出是什么谁用
sections每个标题：级别、原始行、GitHub 风格锚点、起止行、这一节的文本（到下一个同级或更高级标题为止）锚点检查、章节引用、openUntil
passage(anchor)锚点对应的文本：标题锚点取那一节；<a id> 取它所在的段落、列表项、表格行或引用块链接锚点、决策落地点
links()、linksIn(node)所有链接和图片的目标，包括引用式 [文字][标签] 经定义 [标签]: 目标 解析后的；脚注不算链接、可达性、决策落地点
inlineCodes行内代码片段和行号（围栏代码块不在内）路径、命令
htmlComments围栏代码块之外的 HTML 注释，带精确偏移code pin
withoutFences、withoutCode把围栏代码块（及行内代码）换成空白、保留行号的文本决策号引用、开放调研
proseSegments正文文本节点演化措辞

例如代码块里的 <!-- pin: … --> 只是示例，不会被当作 pin；代码块里的 D9 不算引用了决策 D9。这些都靠“语法树知道哪里是代码”，而不是正则猜。

withoutLinkTargets：只去掉链接目标

:187。history 比较要回答“除了链接目标，什么都没变吗”。它直接用 micromark（remark 底层的解析器）的事件流，找出这几类 token 的精确位置并删掉：

  • resourceDestination：[文字](目标 "标题") 里的目标，连同 <…>；
  • definitionDestination：[标签]: 目标 里的目标；
  • autolinkProtocol、autolinkEmail：<https://…> 尖括号里的地址，但图片说明文字里的不算（那是说明文字）。
原文:   See [the plan](../plan.md "Plan") and <https://example.com>.
去掉后: See [the plan]( "Plan") and <>.

链接文字、标题、代码、正文都留着。正文里直接写的网址（不带尖括号）是看得见的文字，也留着。早先这里用正则扫描，曾被多行标题、代码块里的 ](、图片说明里的 HTML 绕过；改成取解析器自己的 token 后，这类问题一并消失。

5. code pin：src/pins.mjs

写法

<!-- pin: src/cache.py#L3-L4@659682712335 -->   行范围（含首尾），12 位哈希
<!-- pin: src/cache.py#L3@… -->                  单行
<!-- pin: src/cache.py@… -->                     整个文件
<!-- pin: src/cache.py#L3-L4 -->                 还没写哈希：失败，等复核后 pin --write
<!-- pin: ./sibling.md#L2-L5@… -->               ./ 或 ../ 开头才相对当前文档

解析用两个正则 :19-20：PIN_ATTEMPT 判断“这是想写一个 pin”（有 pin:，或 pin 后跟像路径的东西）；PIN_PATTERN 判断写对了没有。想写但没写对，判为 malformed；像 <!-- pin the version here --> 这样的普通注释不当 pin。

哈希怎么算

hashSourceSlice() :77：先把 CRLF 换成 LF，按行切开，取第 L起 到 L止 行，用 \n 连起来，求 SHA-256，存前 12 位。整个文件则对全文求哈希。所以只改换行风格不会让 pin 失效；改任何一个字符都会。

每个 pin 的状态

inspectPins() :115 给每个 pin 定一个状态：

状态条件check 的处理怎么修
ok当前位置的哈希一致通过—
unpinned还没写哈希失败，报出它将来的哈希复核后 pin --write
moved当前位置不一致，但文件里恰好有一处同样长度、哈希一致的窗口失败，报出新位置pin --relocate（只改行号）
ambiguous-move一致的窗口不止一处失败，列出所有位置手动改行号
changed哪里都找不到一致的窗口：内容真的变了失败复核段落后 pin --write
invalid-range行范围超出文件末尾（且找不到移动后的位置）失败手动改
missing、outside-root、malformed目标不存在或是目录、出了仓库、写法不对失败手动改
为什么“只是移动了”也算失败：如果允许自动跟着走，很短的窗口（比如一行 return None）可能在别处恰好出现，就会悄悄钉到不相干的代码上。所以移动也要停下来，由人确认后 --relocate（A6、A7）。

pin --write 的范围

syncPins() :248：--write 必须指定 --file、--pin 文档:行 或 --all。指定范围后，只打开范围内的文档；范围里有一项一个 pin 都没匹配到，就报错并且什么都不写；匹配到但都已是最新，正常退出。写入后打印被钉住的代码行（目前只有带行范围的 pin 会打印，整文件的不打印，这是迭代方案里的缺陷 14）。

6. 历史比较

第 15 项检查 check.mjs:644：

  1. 找基线 resolveBase() :72：git merge-base <history.base> HEAD。找不到就退到 HEAD 并打 note（已提交的改动没被比较）；连提交都没有就什么都不比、打 note。
  2. 列出改动：git diff --name-status --no-renames --diff-filter=MD 基线 -- history目录，只看修改（M）和删除（D）。新增的文件不在内：所以功能分支上新放进 history 的文件，在合入主分支前都还能改。
  3. 删除：一律失败。
  4. 修改：基线版本（git show 基线:文件）和现在的版本都用 withoutLinkTargets 去掉链接目标、去掉末尾换行，然后要求：现在的 = 原来的；或者现在的以原来的开头，多出的部分是一段以 ## Erratum 加日期（YYYY-MM-DD）开头的新段落。

这个“以原文开头”的比较是整篇比较，所以不能在中间插一行、再在末尾加个勘误蒙混过去。

已知缺口（迭代方案缺陷 17）：runGit() :60 在 git 命令失败时返回 undefined，有的地方把它当成“没有改动”。也就是说 git 出错时，这项检查可能静默放行。

7. 决策表解析

decisionRows() check.mjs:205 先从语法树里找 GFM 表格行：第一格匹配 前缀+数字（如 D1）的就是一行决策，第 4 格是状态，第 5 格是落地点（取其中的链接）。再用纯文本兜底，找没有表头的 | D3 | … | 行（跳过代码块和 HTML 注释里的）。设了 landedSection 时，只有那个标题之后的行才要求状态和落地点，之前的老行不管。

8. 出错处理：一项出错，其余照跑

runCheck() check.mjs:768 把每项检查包在 try/catch 里：返回值经 normalizeOutcome() 统一成 { problems, notes }；抛出的任何东西（包括 null、没有原型的对象）都经 why() 转成文字，记进 errors。CLI 只要看到 errors，连 --report 也退出 1。

已知缺口（缺陷 18）：项目检查返回 {} 或 undefined 时，normalizeOutcome 把它当成“没有发现”，不会报错。

9. init 与 update：src/manage.mjs

一句话区分：init 一个项目只运行一次，用来放入模板和规范副本；update 在 docaxioms 本身升级之后运行，只换规范副本。两者都不碰项目自己写的文档。

项目里属于 docaxioms 的东西有两类：

  • 模板（AGENTS.md、CURRENT.md、docs/ 下几份空文档）：复制进来以后就归项目所有，项目可以随意改，docaxioms 以后再也不碰。
  • 规范副本（docaxioms/ 下的公理、GUIDE、GARDEN、许可证）：一直属于 docaxioms，项目不能改，用哈希钉住。

init 两类都放；update 只管规范副本。所以新版 docaxioms 即使加了新模板，update 也不会把它补进已经接入的项目。

什么时候要运行 update：项目升级了 docaxioms 的 npm 版本以后，第一次 check 就会失败，并告诉你去运行它。实际输出：

$ docaxioms check
FAIL core files are the pinned version (A4, A6): 1
       docaxioms.json pins docaxioms version 0.0.9, but the docaxioms running is version 0.1.0-alpha.0: run docaxioms update, or run version 0.0.9
$ docaxioms update .
docaxioms/ is pinned to v0.1.0-alpha.0 (e45fec29); run: npx --no-install docaxioms check
$ docaxioms check
ok   core files are the pinned version (A4, A6)

如果项目改过规范副本，update 会拒绝。它不会覆盖掉项目的改动，而是要求先把改动提交到 docaxioms 本身：

$ docaxioms update .
docaxioms/GUIDE.md was changed in the project: make that change in docaxioms first, then update
[exit 1]

细节对比：

init :85update :106
前提项目没有 docaxioms.json，也没有 docaxioms/ 目录项目有 docaxioms.json
模板复制 templates/ 下项目没有的文件不碰
core复制到 docaxioms/，公理文件只读拒绝的情况：副本被项目改过（哈希对不上）；core 目录里有不是 core 的文件；公理变了而没有 --accept-axioms。都通过才覆盖成新版本，删掉新版本不再有的文件
profile以模板 profile 为底，写入 core 一节只更新 core 一节，其余键原样保留
提交号从 docaxioms 的 git 检出运行时，记下它的提交号；检出有未提交改动就拒绝（项目钉的必须是一个确定的提交）。从 npm 安装运行时只记版本

检查第 2 项在每次 check 时核对这些哈希、版本和提交号：项目里的规范副本和正在运行的工具，必须是同一个版本。
