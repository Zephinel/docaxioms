测试与门禁

一共 221 项测试，用 Node 自带的测试运行器（node --test），不依赖测试框架。

夹具项目：一个和本仓库毫不相干的项目

check.test.mjs 开头定义了一个虚构的 Python 天气工具（FILES :18、PROFILE :42），故意用不同的名字、不同的决策前缀（ADR-）、不同的目录（law/ 放 core、NOW.md 当阶段卡）。目的是证明检查不依赖本仓库的习惯，换一个项目照样成立。

每个用例都由 runFixture(change, profile) :61 运行：

在系统临时目录建一个新仓库写入 FILES，git init，提交到 main，再切到 work 分支（这样 history 检查有基线可比）
↓
执行 change一个小函数，用 add（追加）、swap（替换一段文字，原文必须存在）、put（写文件）、drop（删文件）改动工作树
↓
运行 check(root, profile)，返回所有结果结束后删掉临时目录

failing() :76 再把结果筛成“有 gate 发现的检查名”列表；并且先断言没有任何一项运行出错：出错的检查没有发现可比，不能让它看起来像通过。

FAULTS：每项检查都要见过自己失败（120 条）

GUIDE 的要求：“Give it its own seeded fault: a check that was never seen to fail proves nothing.” FAULTS :88 是一张表，每行是 [检查名前缀, 改动, 可选的 profile]，期望这项检查报出问题：

["links and anchors", ({ add }) => add("docs/index.md", "\n[x](/docs/gone.md)\n")],
["a history file",    ({ swap }) => swap("docs/old/first.md", "Old text,", "New text,")],
["commands named",    ({ add }) => add("README.md", "\nRun `make -s deploy`.\n")],
["the profile",       () => {}, { ...PROFILE, commmands: PROFILE.commands }],   // 拼错的键

第 224 行把每行展开成一个测试，名字形如 caught: links and anchors (add("docs/index.md", …))；只改 profile 的用例，括号里显示改了哪些设置。表里按时间分段追加：每一轮审查发现的漏洞，都先在这里加一条复现，再去修代码。

ALLOWED：合法的改动必须通过（49 条）

只测“会失败”不够：一项检查如果什么都报，也能通过 FAULTS，却会让人对它习以为常、视而不见（A7）。ALLOWED :228 列的是不该报错的改动，期望没有任何 gate 发现、也没有运行错误：

["a dated erratum", ({ add }) => add("docs/old/first.md", "\n## Erratum 2026-11-23\n\nIt was two hours.\n")],
["a link target fixed in history", ({ swap }) => swap("docs/old/first.md", "../todo.md", "../design.md")],
["a command after an option", ({ add }) => add("README.md", "\nRun `make -s test`.\n")],
["a pin example inside a fenced code block", …],

另有一条基线测试：什么都不改，连 aid 也要全部通过。

单独的测试

不适合放进表里的情况，写成单独的 test(…)，例如：

  • code pin：嵌套在列表和引用块里的 HTML 中写 pin，pin --write 不破坏 Markdown；代码移动、一行的 pin 撞上别处相同的行、重复窗口时的处理；
  • 符号链接：链接、入口、目录的 README、配置的文件、code pin 经符号链接指到仓外时，都报错且不读取（测试在系统临时目录里真的建一个仓外文件）；
  • profile：一个设置出错只剔掉这个设置；不是对象时所有检查都不运行；x- 值原样传递；
  • 出错隔离：项目检查抛出 null 或没有原型的对象，仍被记成 error，下一项照跑；
  • history：找不到基线、没有提交时，打出说明而不是静默；
  • core 不点名任何项目 :705：用一个正则检查 core/ 的三份文件里没有本机路径、网址、邮箱、工具名（Claude、npm、git……）、汉字、决策编号之类（AD-2）。

CLI 与 init/update 测试

test/docaxioms.test.mjs 在临时目录里真的运行 init、update 和 bin/docaxioms.mjs 子进程，断言输出和退出码：

  • 新项目 init 后自己的检查就通过，钉住的版本和 core 哈希正确；
  • update 不覆盖项目改过的 core 文件；公理变了必须 --accept-axioms；core 目录在项目外时拒绝；
  • check 的 gate/aid 退出码、--strict-aids、--report；一项检查出错时，加 --report 或 --json 也退出 1；
  • pin --write 不指定范围时拒绝；范围没匹配到 pin 时报错；profile 有问题时 pin、garden 拒绝运行。

本仓库的门禁（AD-7）

docaxioms 用自己检查自己的文档，但在开发期只让一部分检查阻断合并。决策 AD-7：“只有链接、路径、命令和 axiom pin 阻断；其余是报告；运行出错仍然失败”。理由是：一项检查要先在外部真实项目上跑够（10 次相关改动、3 条值得改文档的发现），证明它精确，才配阻断（M2、A7）。

test/self.test.mjs 把这条决策变成测试：

const BLOCKING = [
  "core files are the pinned version",
  "links and anchors resolve",
  "documents named in code exist",
  "paths named in current documents exist",
  "commands named in current documents exist",
];
  1. 直接计算 core/AXIOMS.lock.md 的 SHA-256，必须等于 docaxioms.json 里钉的值（不经过 profile 的容错处理，避免 profile 里一个错字让这项保护失效）；
  2. 对本仓库跑 check，上面五项必须没有发现；
  3. 本仓库文档里的 code pin，目标必须存在、不出仓库（pin 的内容变了只报告，不阻断）。

本仓库的 docaxioms.json 自己的设置也很说明问题：codeExtensions: [".mjs"]，pathPrefixes 是 bin/、core/、docs/、src/、test/，命令检查 npm run … 对照 package.json 的 scripts；codeToDocs 把 src/** 映射到 GUIDE 和 README，所以改了源码而没动这两份文档，会出现一条 aid 提醒。

npm run check 与 CI

"check": "node --no-warnings --test test/*.test.mjs && node bin/docaxioms.mjs check --report"

先跑全部测试（包括 self.test 的阻断），再对本仓库跑一遍完整检查并打印报告。--report 让非阻断检查的发现只打印、不失败；运行出错仍然失败。

CI（.github/workflows/check.yml）在每个 PR 和推到 main 时，用 Node 22（package.json 支持的最低版本）跑 npm ci 和 npm run check。检出时用 fetch-depth: 0 拉全历史，这样 history 检查在 PR 上能找到 origin/main 作基线；否则只会打一条 note。

怎样确认一个修复真的被测住

这次开发反复用的一个做法：写好新测试后，把测试文件复制到修复前的提交的临时 worktree 里再跑一遍。新测试在旧代码上失败、在新代码上通过，才说明它测到了这次修的东西；在旧代码上也通过的测试，只能算防回归。

git worktree add /tmp/old <修复前的提交>
ln -s "$PWD/node_modules" /tmp/old/node_modules
cp test/*.test.mjs /tmp/old/test/
(cd /tmp/old && node --test test/check.test.mjs)   # 期望：新加的用例失败
git worktree remove --force /tmp/old
